# I/O 调度器与 read_ahead 对照 —— 2026-09-30 结案：测不出差异

## 一、要判的问题
换 I/O 调度器（bfq/kyber/none/mq-deadline）或调 `read_ahead_kb`，在这台 GT5 Pro 上有没有可测收益。

## 二、三条前置依据（全部本机/本树实测，不引网页）

1. **本机 UFS 是多硬件队列**（从完整开机日志 `logs/boot11-run2/dmesg.txt`）
   `ufshcd-qcom 1d84000.ufshc: MCQ configured, nr_queues=9, io_queues=8, read_queue=0, poll_queues=1, queue_depth=64`
   ⇒ 8 个 IO 队列各自一份调度器实例，且 `queue_depth=64 < nr_requests=126` ⇒ **软件队列很难积压**，而调度器的价值恰在"积压时怎么排队"。**机理上就预期无差异。**
2. **厂商对 UFS 根本没设调度器**：`/vendor/etc/init/hw/init.qti.kernel.rc:100-106` 只对 `mmcblk0/1`（eMMC/SD）设 `bfq` + `slice_idle 0`。我们是 `sda` ⇒ 当前 `[mq-deadline]` 是**内核内建默认**，不是厂商策略。
3. **无法烙成默认值**：`block/Kconfig.iosched` 里 `MQ_DEFAULT_*` **命中 0** ⇒ 换调度器只能运行时或开机脚本，想靠 config 固化做不到。
4. 内核自带文档的定位（`Documentation/block/`，与本机同为 6.1）：bfq＝"默认延迟优先于吞吐，为降延迟可牺牲吞吐"；kyber＝只有读/同步写两个目标延迟旋钮；deadline＝保证起始服务时间。

## 三、实测：4 调度器 × (写 / 3 档 read_ahead 读) × 交替 3 轮

数据 `logs/io-sched-bench.txt`，统计 `tools/io_bench_stat.py`。

| | 各档最优值差 | 同一档三轮内部极差 |
|---|---|---|
| 写 512MB | 562~689ms（23%） | 最大 **1021ms** |
| 读 512MB | 390~627ms（38%） | 最大 **761ms** |

读测全局最快 390ms、最慢 1239ms ＝ **3.2 倍噪声**；写测 2.8 倍。**同档自身波动远大于档间差** ⇒ 判"**测不出差异**"。看着像"kyber 比 mq-deadline 快 14%"，但那 14% 完全落在 mq-deadline 自己的波动带（极差 414ms ≈ 其 min 的 60%）之内。

## 四、结论

- **"换 I/O 调度器"这条永久划掉**：机理（MCQ 浅积压）与实测（噪声 3 倍、无档间差异）同向。
- 即使测出差异也无处固化：`MQ_DEFAULT_*` 不存在 ⇒ 要么改源码刷机，要么开机脚本（两者代价都不匹配"零收益"）。
- 手机真实 I/O 体验的决定权在 **f2fs 挂载参数（vendor `fs_mgr`）＋ UFS 固件/WriteBooster（厂商 `ufs_qcom.ko`）＋ 机主自己的 zram 模块**，均不在我们控制面内。

## 五、第二轮（修正方法后，定量结论）

第一轮没有噪声标尺，所以只能说"测不出"。第二轮改为：样本 128MB（总量约 5GB，非 24GB）、交替轮次、**先连测 5 次同一配置标定噪声带**。数据 `logs/io-bench2.txt`，统计 `tools/io_bench2_stat.py`。

```
P0 噪声标定 (mq-deadline @ ra512 读 ×5): 167~204ms → 中位 187ms, 波动带 37ms = 20%
   ⇒ 判据: 档间中位数差 < 20% 不算差异
```

写 128MB（三轮中位）：

| 调度器 | 中位 | 相对 mq-deadline |
|---|---|---|
| **mq-deadline** | **174ms** | 基准，且**最快** |
| none | 190ms | +9.2% |
| kyber | 194ms | +11.5% |
| bfq | 199ms | +14.4% |

读 128MB（四轮中位）：

| ra_kb | mq-deadline | kyber |
|---|---|---|
| 128 | 170ms | 183ms |
| 512 | 172ms | 159ms |
| 1024 | 186ms | 178ms |

**定量结论：**
1. **换调度器无收益，且现默认已是最优档**——其余三档全部更慢，且差值（9~14%）**都在 20% 噪声带内**，故只能表述为"不会更好，最多持平或略差"。
2. **`read_ahead_kb` 无收益**：128/512/1024 差 ≤9.7%，仍在带内；且**调大反而最慢**（1024=186ms），与机理一致——128MB 顺序读、1M 块大小下预读窗口不是瓶颈，UFS `queue_depth=64` 已把请求喂饱。
3. 唯一"看起来更快"的 kyber@512=159ms（−6.5%）**小于噪声带，不能算数**；要压出显著性需 15+ 轮，而那点量级对日常体验无意义。

⇒ 三层理由闭环：**机理**（MCQ 8 队列 + depth 64 ⇒ 软件层积不起来）、**实测**（默认档即最快）、**固化**（无 `MQ_DEFAULT_*`，改不动默认）。**"I/O 调度器/read_ahead 优化"到此永久划掉。**

## 六、方法错误（第一轮，记下来别再犯）


- 样本总量过大：12×512MB 写（≈6GB）＋36×512MB 读（≈18GB）⇒ 跑完 `loadavg` 冲到 **21.68**、f2fs 要追 GC；**基准要按总字节数预算**（该用 128MB 或减轮次）。约 2 分钟后 `loadavg` 降至 9.91、`Dirty` 1.2MB、`Writeback` 0，自行排空。
- 另有一条目录级递归 `grep -r` 把设备打到卡顿——设备侧取证一律"先 `ls` 到单文件，再 `cat` 到电脑侧查"。
- 收尾核对：`[mq-deadline]`、`read_ahead_kb=512` 已还原，`svc power stayon false`，测试文件已删除。
