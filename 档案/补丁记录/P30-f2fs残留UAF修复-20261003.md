## 一、修的是什么

`f2fs_free_dic()` 里解引用 `dic->inode` 查询压缩 layout：

```c
static void f2fs_free_dic(struct decompress_io_ctx *dic, bool bypass_destroy_callback)
{
	int i;

	if (f2fs_compress_layout(dic->inode) == COMPRESS_FIXED_INPUT)      /* ← 2474 */
		f2fs_release_decomp_mem(dic, bypass_destroy_callback, true);
	...
```

而它会被 **workqueue** 调用：

```c
static void f2fs_late_free_dic(struct work_struct *work)
{
	struct decompress_io_ctx *dic = container_of(work, struct decompress_io_ctx, free_work);
	f2fs_free_dic(dic, false);
}
```

`f2fs_compress_layout()` 是 `fs/f2fs/f2fs.h` 的 `static inline`，在
`CONFIG_F2FS_FS_COMPRESSION_FIXED_OUTPUT=y`（**本树确实开着**）时会真的读
`F2FS_I(inode)->i_compress_flag` 和 `F2FS_I_SB(inode)`。
而 `dic` 上**没有任何 `igrab`/`ihold`** 持有 inode ⇒ 晚释放路径上的 **use-after-free 风险**。

### 为什么是"残留"
`struct decompress_io_ctx` 里**已经缓存**了 `sbi` 和 `compress_algorithm`
（上游补丁 `74cbeeca4f16` 做的一半，我们 **P28 已落地**），**唯独 layout 没缓存**。
这次把最后一块补齐。

### 本机确实走得到这条路径（功能级证据）
```
/dev/block/dm-76 on /data type f2fs (... compress_algorithm=lz4, compress_log_size=2,
                                      compress_mode=user ...)
/sys/fs/f2fs/dm-76/compress_layout      ← layout 特性存在，FIXED_OUTPUT 生效
```
⇒ `/data` 就是 f2fs 且压缩开着，**这个修复在本机真的用得上**。

## 二、改动（3 处，成套）

1. **`fs/f2fs/f2fs.h`** —— `struct decompress_io_ctx` 加字段
   ```c
   unsigned char dic_layout;	/* cached compress layout, safe on late-free path */
   ```
2. **`fs/f2fs/compress.c` `f2fs_alloc_dic()`** —— 在任务上下文提前缓存
   ```c
   dic->dic_layout = f2fs_compress_layout(cc->inode);
   ```
3. **`fs/f2fs/compress.c` `f2fs_free_dic()`** —— 改用缓存值
   ```c
   if (dic->dic_layout == COMPRESS_FIXED_INPUT)
   ```

### ⚠️ 两个差点改错的陷阱（务必记住）

**陷阱 1：`f2fs.h:231` 已有一个【同名但不同归属】的 `compress_layout`**
```c
struct f2fs_mount_info {          /* ← 挂载选项，不是 dic */
#ifdef CONFIG_F2FS_FS_COMPRESSION_FIXED_OUTPUT
	unsigned char compress_layout;	/* compression layout */
#endif
```
⇒ 加字段时必须**认准 `struct decompress_io_ctx`**（其 `compress_algorithm` 在 1799 行，
而 `f2fs_mount_info` 的在 223 行）。**我一度差点加错结构体**，故新字段特意取名 `dic_layout` 以区分。

**陷阱 2：树里共 4 处 `f2fs_compress_layout(dic->inode)`，但只有 1 处该改**

| 行 | 所在函数 | 上下文 | 处置 |
|---|---|---|---|
| 340 | `f2fs_decompress_cluster` | 任务上下文 | ❌ 不动 |
| 1376 | `f2fs_decompress_pages` | 任务上下文 | ❌ 不动 |
| 2315 | `f2fs_alloc_dic` | 任务上下文 | ❌ 不动 ——**改了会在赋值前引用缓存（真 bug）** |
| **2474** | **`f2fs_free_dic`** | **晚释放（workqueue）** | ✅ **唯一该改** |

**我一开始以为"2315 和 2474 都是同类"，判断错了** —— 2315 在 `alloc_dic` 内部，
正是我加赋值那个函数，属于任务上下文。**改 4 处会引入真 bug。**

## 六、本轮新的方法论沉淀

1. **"全树同类排查"要先分清上下文** —— 同一个表达式在任务上下文和晚释放路径上性质完全不同，
   改错会引入 bug。判据：**看调用链上有没有 workqueue / IRQ / 下半部**。
2. **同名不同归属的字段是真实的坑** —— `compress_layout` 在 `f2fs_mount_info` 和（拟加的）
   `decompress_io_ctx` 之间只差一个结构体。新字段取名要能自证归属。
3. **子代理/队员额度会耗尽** —— 本轮出现代理失败、队员消息"accepted"但不唤醒。
   **小且精确的改动（3~4 处）自己做更快**，不必等代理。
