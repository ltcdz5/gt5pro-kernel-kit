## 一、【1】f2fs 压缩：`log_cluster_size` 上界与数组维度不一致 ⇒ 栈 + slab 越界

### 事实（我方逐条复核过）
```
fs/f2fs/f2fs.h:1706   #define MAX_BLKS_PER_CLUSTER (1 << 3) = 8
                      （注释却写着 "// MAX_COMPRESS_LOG_SIZE" ⇒ 原值应是 1<<MAX）
fs/f2fs/f2fs.h:1817   #define MAX_COMPRESS_LOG_SIZE 8   ⇒ cluster_size 允许到 256
```
而 `struct decompress_io_ctx` / `struct compress_ctx` 的
**`rpages[8]` / `cpages[8]` / `tpages[8]` / `di[8]` / `inplace_io[8]` 全是 8 项**。

**三条入口都只卡到 8、没按 8 夹紧**：
```
fs/f2fs/super.c:1204   挂载参数 compress_log_size
fs/f2fs/file.c:6240    F2FS_IOC_SET_COMPRESS_OPTION
fs/f2fs/inode.c:318    磁盘 inode 的 i_log_cluster_size（随后 inode.c:505 i_cluster_size = BIT(...)）
```

**越界写点**（都用 `cluster_size` 当下标）：
```
compress.c:2312   dic->rpages[i] = cc->rpages[i]     ← slab 越界
compress.c:2338   dic->di[i] = cc->di[i]
data.c:2722       cc->di[i]（cc 是【栈】变量）        ← 内核栈越界
```

**本树自证作者预期 cluster_size 可 >16**：`data.c:3533` 用
`1 << cc.log_cluster_size > F2FS_ONSTACK_PAGES(=16)` 判断是否改用 kmalloc。
⇒ 作者知道 cluster_size 会超过 16，**但解压侧数组只有 8 项**。

### 触发条件（如实记录）
默认 `compress_log_size = MIN(2)`（4 页）**不炸**。要触发 log≥4 需要：
1. 挂载参数 `compress_log_size=4..8`，或
2. `F2FS_IOC_SET_COMPRESS_OPTION` 传 4..8，或
3. 磁盘上已存在/损坏的 `i_log_cluster_size≥4` 的 inode（bit rot / 恶意镜像）

⇒ **f2fs 的设计目标是"遇到损坏不崩"，这条正好违背。**

### 修法（最小、不碰中枢结构体、零导出变化）
```
f2fs.h   新增 MAX_SUPPORTED_COMPRESS_LOG_SIZE = 3（= ilog2(MAX_BLKS_PER_CLUSTER)），
         并修正 MAX_BLKS_PER_CLUSTER 的误导注释
super.c / file.c / inode.c   三处上界改用 MAX_SUPPORTED_COMPRESS_LOG_SIZE
```
⇒ **log>3 的压缩文件将不再被接受**（这类文件今天一读就崩，本就不存在；厂商默认 2）。
**更正统的修法是恢复动态分配**（`f2fs_kzalloc` 按 cluster_size 分配 + `compress_ctx.di` 动态化），
但那会改 `sizeof(...)` ⇒ 影响 `dic_entry_slab` 尺寸与多处**栈帧**，**必须单独一版过闸门**（留 P33/P34）。

## 二、【2】f2fs：磁盘来的 `decompress_index` 零校验 ⇒ 索引越界

### 事实
```
data.c:2718-2726   只做 deserialize 就直接使用
compress.c:2385    blkidx = dic->di[i].blkidx;    ← di->blkidx 是【8 位】(0..255)
                                                  而 cpages[] 只有 8 项
compress.c:2395-2398
    if (dic->di[i].cross_block) { prev_blkidx--; f2fs_bug_on(sbi, i == 0); }
    ← f2fs_bug_on 只 WARN 不返回；i==0 且 cross_block 时 prev_blkidx = -1
    ⇒ 写 &dic->cpages[-1]（按结构体布局正好砸到 `unsigned int nr_cpages`）
```

### 修法
`data.c` 反序列化循环内加校验，越界即
`f2fs_handle_error(sbi, ERROR_INVALID_BLKADDR)` + `-EFSCORRUPTED` + `goto out_put_dnode`。
判据：`blkidx >= MAX_BLKS_PER_CLUSTER` **或** `(i == 0 && cross_block)`。

## 三、【3】SSG 电梯：`rcu_read_unlock()` 之后解引用 blkg 的 pd ⇒ **真 UAF**

### 事实
```c
unsigned int ssg_blkcg_shallow_depth(struct request_queue *q)
{
	rcu_read_lock();
	blkg = blkg_lookup(css_to_blkcg(curr_css()), q);
	ssg_blkg = BLKG_TO_SSG_BLKG(blkg);
	rcu_read_unlock();                                  ← 解锁了

	if (atomic_read(&ssg_blkg->current_rqs) < ssg_blkg->max_available_rqs)   ← 解锁后解引用
		return 0;
	return ssg_blkg->shallow_depth;                                          ← 同上
}
```
- blkg 的释放路径：`call_rcu(&blkg->rcu_head, __blkg_release)` →
  `blkg_free_workfn()` → `pd_free_fn` → `ssg_blkcg_pd_free()` → **`kfree(ssg_blkg)`**
- **本树有明文禁令**（`block/blk-cgroup.c`）：
  > "having an rcu lock does not mean that one can access all the fields of blkg …
  > Having a reference to blkg under an rcu allows accesses to only values local to groups"

### 为什么本机是**活的**
设备上 `sda`~`sdf` 的调度器**就是 `[ssg]`**（ColorOS 的 `ssgtzd` 守护进程自动切换），
且 Android 的 io/blkio cgroup 在运行时不断建/删 blkg ⇒ 释放路径是活的。

⇒ 这条的额外意义：**在修好之前，绝不能把 SSG 切为默认**（虽然厂商已经切了，但我们现在修好了）。

### 修法
把两处读取**搬进 rcu 段**，用局部变量带出（3 行级）。

## 四、【4】SSG 电梯：sysfs STORE 用未初始化的 `__data`

### 事实
```c
static void ssg_var_store(int *var, const char *page)
{
	long val;
	if (!kstrtol(page, 10, &val))     ← 吞掉失败
		*var = val;
}
```
`STORE_FUNCTION` 宏里 `int __data;` 未初始化 ⇒ 往 sysfs 写**非数字**
（`echo x > /sys/block/sdX/queue/iosched/read_expire`）时，**垃圾值**被写进
`ssg->fifo_expire[]` / `front_merges`。

**对照**：`block/mq-deadline.c` 的同类宏有 `if (kstrtol(...)) return -EINVAL;` —— **SSG 这份漏了**。

### 修法
`ssg_var_store` 改返回 `int`，宏里检查返回值并 `return -EINVAL`。
