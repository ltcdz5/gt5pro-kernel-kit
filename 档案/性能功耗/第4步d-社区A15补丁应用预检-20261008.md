## 3. `cpufreq_walt.c` 专项结论

### 3.1 会不会「初始化器塌方」？—— **不会**

三条硬证据：

1. **补丁集里没有这个文件。** 对 6 条补丁全文检索 `cpufreq_walt` ⇒ **0 命中**；检索 `__ATTR_RW` / `__ATTR_RO` / `__ATTR` / `governor_attr` ⇒ **全部 0 命中**。补丁根本没有能触发该塌方的构造。
2. **我们树里没有 WALT。** `find . -name '*walt*'` 在 `kernel/`、`include/` 下**零命中**；无 `kernel/sched/walt/` 目录，无 `include/linux/sched/walt.h`，无 `cpufreq_walt.c`。没有「既有文件」可供 hunk 上下文错配。
3. **塌方的成因是 hunk 落进既有初始化器内部**。本补丁集里 19 个新文件是**整文件新建**（`@@ -0,0 +1,N @@`），不存在上下文错配；而对既有文件的 16+13 条 hunk **全部 CONTEXT_FAIL**，一条也打不进去 —— 没有东西被插入，自然没有塌方。

### 3.2 那起事故的原始现场（已定位）

1416: static struct governor_attr pl                  = __ATTR_RW(pl);
1417: static struct governor_attr boost               = __ATTR_RW(boost);

共 9 处 `__ATTR_RW` + 1 处宏内 `governor_attr`。**若把这份文件当补丁往我们树上打**，由于我们树**没有 WALT 核心**（`walt/walt.h`、`walt.c`、`walt_cfs.c`、`sched_avg.c`、`walt_halt.c`、`walt_lb.c`、`walt_rt.c`、`walt_gclk_cycle_counter_driver.c`、`Kconfig`，共 11 个文件 ≈ 400 KB），会先死在更早的阶段（缺 `struct walt_task_struct` / `walt_rq` / WALT 时钟接口），**根本走不到塌方那一步**。

### 3.3 最小修法（若将来真的引入 WALT）

不适用于本次预检（不会发生），仅备查：`__ATTR_RW(X)` 必须与其 `static struct governor_attr X` **保持在同一逻辑行**，任何自动合并/重排工具不得把 `= __ATTR_RW(...)` 与前面的声明拆开；若必须插入新属性，插在**相邻属性之间**（如 1418 行之后），而不是插进 `=` 与 `__ATTR_RW` 之间。

本补丁集里唯一形似 `__ATTR_RW` 的宏生成初始化器是 `HMBIRD_PROC_OPS`：

```c

        static const struct proc_ops name##_proc_ops = { \
```

它位于**新建文件**（`kernel/sched/hmbird_sched_proc.c` 等），整文件落地、无上下文错配 ⇒ **无塌方风险**。

### 4.2 但另有两类真实「遮蔽」必须登记

#### (a) 头文件保护宏碰撞 —— 3 组 ⚠️

补丁新建 `include/linux/sched/*.h`，与**本树已有的** `kernel/oplus_cpu/sched/sched_assist/*.h` **用了完全相同的 include guard**：

| guard 宏 | 补丁路径（新建） | 本树已有路径 | 内容差异 |
|---|---|---|---|
| `_OPLUS_SA_COMMON_H_` | `include/linux/sched/sa_common.h` | `kernel/oplus_cpu/sched/sched_assist/sa_common.h` | 相似度 **0.899**，237 行差异 |
| `_OPLUS_SA_COMMON_STRUCT_H_` | `include/linux/sched/sa_common_struct.h` | `kernel/oplus_cpu/sched/sched_assist/sa_common_struct.h` | 相似度 **0.770**，151 行差异（补丁多出 `struct scx_entity`、`struct scx_task_stats`、`struct task_record` 等） |

**副作用**：同一编译单元里若先包含本树那份，再包含补丁那份（或反之），**后者会被 guard 静默跳过**。结果是「声明缺失」或更隐蔽的「结构体布局静默分叉」—— 编译期可能只报 `implicit declaration`，运行期则是 ABI 错配。这是**比文件覆盖更难查的一类遮蔽**，必须显式改名（例如补丁侧统一加 `HMBIRD_` 前缀）后才能共存。

| 符号 | 补丁定义处 | 本树已有定义 | 本树导出 | 后果 |
|---|---|---|---|---|

### 5.2 配置面结论

1. **两个最关键的开关（`SLIM_SCHED`、`SCHED_CLASS_EXT`）本树已开** —— 补丁在这两项上没有增量价值。
2. **`CONFIG_SCHED_WALT` 缺失反而是好事**：它把补丁里唯一的 WALT 依赖整段编译掉，消除了「移植 WALT」这个无底洞。
3. **`CONFIG_OPLUS_FEATURE_SCHED_ASSIST` 未开**是个**大坑**：补丁大量引用该子系统（`sa_common.h`、`sa_oemdata.h`、`sa_common_struct.h`）的类型与符号，但本树对应目录当前**不参与编译**。要打开它，等于把一个从没在本机构建过的 OPPO 子系统重新拉进构建 —— 风险与工作量都不小于移植 hmbird 本身。
4. **没有任何配置组合会引出 §4.1 的硬遮蔽**：因为补丁的内核导出名与厂商模块导出名交集为空。

## 6. 结论与建议

### 6.1 哪个补丁最值得作为移植主线？

**都不适合作为「直接应用」的主线。** 若必须选一条取材，选 **`fengchi_OP-PAD-3-SM8750_A15.patch`**（即 `up_pad3_a15`），但**只取其 19 个新建文件**作为参考实现。

理由：

- 它是 6 条里**信息量最大、结构最完整**的一条（19 个新文件、4,313 行的 `hmbird.c`、完整的 `/proc/hmbird_sched/` 接口面）。
- 它的 19 个新文件在本树**零冲突**落地，可以安全地放进树里作对照物（甚至编译进独立目录）而不影响现状。
- 但它的 16 条既有文件 hunk **全数冲突**，必须逐条人工重写。
- 更要命的是它引入**第二套 hmbird 实现**（`kernel/sched/hmbird/`），与本树已有的 `kernel/oplus_cpu/sched_ext/` + `kernel/sched/hmbird_export.c` 是**竞争关系**，会撞出 §4.2(b) 的 3 处重复全局定义。

**`loc_61sched_ext` 明确不建议**：它要覆盖我们已审计的 `kernel/sched/hmbird_export.c`（丢 2 个 factory 符号 `iso_masks`/`scx_get_md_info` ⇒ `oplus_bsp_sched_ext.ko` 拒载），且有 3 个目标文件在本树根本不存在。这与 kit 已归档的 step4c 结论一致（`95bb5c0`：*do not port the hmbird sched_class*）。

### 6.2 预计需要人工处理多少处？

若以 fengchi 为主线：

| 类别 | 处数 | 处理方式 |
|---|---|---|
| 新建文件直接落地 | **19** | 零改动，但需**先解决 §4.2(a) 的 3 组 guard 碰撞**（改名） |
| 同补丁内增量 hunk | 1 | 合并进新建文件 |
| 既有文件 hunk 冲突 | **16 个文件 / 55 个 hunk** | 逐条重写（`core.c` 31 hunk 与 `sched.h` 4 hunk 是重灾区） |
| 重复全局定义 | 3 | 删掉补丁侧定义，改为引用本树已有符号 |
| 头文件 guard 改名 | 3 | 补丁侧统一加前缀 |
| 缺文件 | 0（fengchi）/ 3（61sched_ext） | — |
| 配置开关 | 约 15 个补丁假定已开的 OPPO 特性开关本树未开 | 需要逐一决定是否引入 |

**量级判断：≥ 60 处人工决策点**，其中 `core.c` 的 31 个 hunk 单独就是高风险区（本树 `core.c` 已因 opt54 回移大改）。这不是「打补丁」，而是「按补丁重写一个 hmbird 移植层」。

### 6.3 「不建议做」的判据

满足以下任一条即应判定**不建议直接移植**（本次**全部命中**）：

1. ✅ 补丁对既有文件的 hunk 冲突率 > 50%（实测 fengchi 16/36 冲突、61sched_ext 13/25 冲突，且 61sched_ext 另有 3 处缺文件）。
2. ✅ 补丁会覆盖本树**已审计且与 factory kernel 对齐**的导出枢纽（`hmbird_export.c`，10 符号 vs 补丁 8 符号）。
3. ✅ 补丁引入与本树既有实现**平行的第二套实现**，产生重复全局定义（`slim_for_app`/`hmbird_dir`/`non_ext_task`）。
4. ✅ 补丁新建头文件与本树已有头文件**保护宏碰撞**（3 组，其中 1 组内容逐字节相同）。
5. ✅ 补丁依赖本树**未开启**的子系统（`CONFIG_OPLUS_FEATURE_SCHED_ASSIST` 未开、9+ 个 OPPO 特性开关缺失）。
6. ✅ 补丁依赖本树**不存在**的子系统（WALT），虽被 `CONFIG_SCHED_WALT` guard 掉，但说明补丁的基线树与本树不同源。

### 6.4 建议的下一步

1. **不做全量移植**，保持 opt55 现状（本树已导出 factory 的 10 个 hmbird 符号，`oplus_bsp_sched_ext.ko` 的缺口按 gate2 既有计划推进）。
2. 把 fengchi 的 19 个新文件**仅作为参考资料**归档到 lab，**不进入构建**。
3. 若确有功能需求，从补丁里**按符号逐个摘取**（而非按文件打补丁），每摘一个都跑一次 `refs/mod-exports-622mods-4623.txt` 交集检查。
4. 若将来要引入 WALT：**先补 WALT 核心**（11 文件 ≈ 400 KB），再谈 `cpufreq_walt.c`；并且**永远不要**把 `static struct governor_attr X = __ATTR_RW(X);` 拆行。
