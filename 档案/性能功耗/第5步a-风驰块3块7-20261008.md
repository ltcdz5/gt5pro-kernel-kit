### 1.2 接入构建的方式（**不是** Makefile obj-y，是 factory 的 build_policy.c include）

`kernel/sched/Makefile` 里 **没有**加 `obj-$()`，理由（两条都是硬约束）：

1. `slim_sysctl.c` **自己一个 `#include` 都没有**（只 `#include "slim.h"`），却用 `struct file`/`copy_from_user`/`seq_printf`/`proc_create_data`/`EXPORT_SYMBOL`/`pde_data`/`ARRAY_SIZE` —— 它只能活在 `build_policy.c` 已经把 `linux/fs.h`、`linux/proc_fs.h`、`linux/seq_file.h`、`linux/uaccess.h` 全拉进来之后。
2. `hmbird_sched_proc_main.c` 要打印 **ext.c 的 file-static** `scx_exit_type` / `scx_nr_rejected`，只有同一编译单元可见。

于是按 factory 布局写进 `kernel/sched/build_policy.c`：

```c
#ifdef CONFIG_SCHED_CLASS_EXT
# include "ext.c"

# ifdef CONFIG_HMBIRD_SCHED
#  include "slim_sysctl.c"
#  include "hmbird_sched_proc_main.c"
# endif
#endif
```

### 1.5 编不过 ⇒ 摘掉并登记（1 处）

**问题**：`hmbird_sched_proc_main.c` 原本 `#include "ext.h"`。本树 `kernel/sched/ext.h` 是**官方上游版，没有 include guard**（`grep -c ifndef = 0`），而 `build_policy.c` 已经通过 `ext.c` 把它拉进来一次 ⇒ 20 个 `redefinition of 'scx_wake_flags'` / `SCX_ENQ_*` 报错。

- **factory 的 `ext.h` 是有 guard 的**（`#ifndef __SCX_EXT_H`，见 lab `scx-step5/base/ext.h` 第 1-2 行），所以 factory 那份文件这样 include 没问题。
- 本轮**不动 ext.h**（它是块1 材料，任务明令"本轮不要动"）⇒ 摘掉 `hmbird_sched_proc_main.c` 里的 `#include "ext.h"`，改成注释说明。同单元里 `ext.c` 已经把 `enum scx_exit_type` 和那两个 static 对象带进来了，**功能零损失**。
- **真正的修法属于块1**：给 `kernel/sched/ext.h` 加 `#ifndef __SCX_EXT_H` guard（factory 就是这样），或把 `scx_exit_type` 变成全局（factory 的 ext.h 里有 `extern atomic_t scx_exit_type;`）。已登记为块1 待办。

**基准**：`kernel/sched/hmbird_export.c`（本树 10 个导出 = `oplus_bsp_sched_ext.ko` 装载命门）。**该文件一行未改**。

### 2.1 去重清单

| # | 符号 | 补丁版（factory 文件） | 处理 | 依据 |
|---|---|---|---|---|
| 1 | `slim_for_app` | `hmbird_sched_proc_main.c` 里 `int slim_for_app;`（**定义**） | **删定义**，改 `extern int slim_for_app;` → 解析到 `hmbird_export.o` | 两个非 static 定义会在 vmlinux 链接期 multiple definition |
| 2 | `highres_tick_ctrl` / `_dbg` | `slim_sysctl.c` `= true` **和** `hmbird_sched_proc_main.c` `;`（**两处定义**） | `hmbird_sched_proc_main.c` 删掉定义，靠 `slim.h` 的 `extern unsigned int` 引用；**所有者 = `slim_sysctl.c`** | 同一 TU（build_policy.c）内两处定义 = 硬报错；`slim_sysctl.c` 是初始化值(`true`)所在处，按"谁初始化谁拥有"归它 |
| 3 | `hmbird_dir` | `hmbird_sched_proc_main.c` 的 `hmbird_proc_init()` 里有个**函数局部变量**同名 | **局部删掉**，改用 `extern struct proc_dir_entry *hmbird_dir;`（= `hmbird_export.c` 的导出） | 见 §2.3，这不是"洁癖"，是功能必需 |

### 2.2 `non_ext_task` 类型冲突：`u64` vs `atomic_t`

- 补丁侧的 `u64 non_ext_task` **不是全局符号**，而是 **`struct snap_misc_t` 的一个字段**（`norm/up_pad3_a15.patch:424`、`norm/loc_fengchi.patch:424`，该结构属于 ext.c 的 panic snapshot，**块1 材料**）。它不可能和全局符号冲突，但会诱导块1 写成 `snap_misc.non_ext_task = non_ext_task;` —— 把 `atomic_t`（`struct { int counter; }`）直接赋给 `u64` 是**编译错误**，必须写 `atomic_read(&non_ext_task)`。
- 本轮在**自己可控的 4 个文件**里把类型钉死：
  - `hmbird_export.c`（未改）：`atomic_t non_ext_task = ATOMIC_INIT(true);` + `EXPORT_SYMBOL_GPL` ⇒ `out/vmlinux.symvers` 里 `0xfd0701e9`。
  - `slim.h`：`extern atomic_t non_ext_task;`（**atomic_t，不是 u64**）。
  - 另外 2 个新文件：不定义、不引用 `non_ext_task`。
- **与厂商模块实测对齐**：`oplus_bsp_sched_ext.ko` 的 `__versions` 里 `non_ext_task crc=0xfd0701e9`，与本树导出**逐位相同**（`hmbird_dir crc=0x947ca90f` 同样相同）。**没有 CRC 拒载风险**。
- 留给块1 的待办：ext.c 的 `snap_misc.non_ext_task`（`u64` 字段）赋值时必须 `atomic_read()`。**类型冲突的真实位置在块1，不在本轮文件里**——本轮把它锁在"只有 atomic_t 一种写法"上。

### 2.3 为什么 `hmbird_dir` 必须用导出的全局（实测证据）

对**出厂真机模块** `vendor-ko/vendor_dlkm/oplus_bsp_sched_ext.ko`(87840 B) 做静态检查：

```
$ llvm-nm --undefined-only oplus_bsp_sched_ext.ko | grep -E 'hmbird_dir|non_ext_task|iso_masks|__scx_ops_enabled|ext_module_loaded|scx_get_md_info|task_is_scx'
                 U __scx_ops_enabled
                 U ext_module_loaded
                 U hmbird_dir            <-- 模块【引用】它（导入）
                 U iso_masks
                 U non_ext_task
                 U scx_get_md_info
                 U task_is_scx

$ strings -a oplus_bsp_sched_ext.ko | grep -c -x -F hmbird_sched      -> 0
$ strings -a oplus_bsp_sched_ext.ko | grep -c -x -F slim_freq_gov     -> 1
$ strings -a oplus_bsp_sched_ext.ko | grep -c -x -F slim_walt         -> 1
$ strings -a oplus_bsp_sched_ext.ko | grep -c -x -F scx_shadow_tick_enable -> 1
```

结论链：

1. 模块 **自己不创建 `/proc/hmbird_sched`**（`.ko` 里连 `"hmbird_sched"` 这个独立字符串都没有），它只创建 `slim_walt/`、`slim_freq_gov/`、`scx_shadow_tick_enable` 这些**子项**。
2. 它 **导入 `hmbird_dir`** ⇒ 子项挂在哪个父目录下，取决于**内核侧那个全局指针**。
3. 出厂内核 `Image.stock` 里 `"hmbird_sched"` 独立字符串 **存在**（=1）⇒ **是内核在创建 `/proc/hmbird_sched` 并把它写进导出全局**。
4. ⇒ 本轮让 `hmbird_proc_init()` 写**导出的全局**（而不是那个同名局部），与出厂语义一致；否则 `hmbird_dir` 恒为 NULL，模块的子项会掉到 `/proc` 根下。

> 附带发现（写进 §5 待办）：本树 `kernel/oplus_cpu/sched_ext/main.c`（DDK 模块源码，**不进内核构建**）是**旧版**：它自己有局部 `hmbird_dir` + 自己 `proc_mkdir("hmbird_sched")`，并且 `int slim_for_app;` 也是自己定义的。**真机在用的 `oplus_bsp_sched_ext.ko` 不是这份源码编出来的**（实测它 `hmbird_dir` 是导入、`slim_for_app` 既不导入也不导出）。这份旧源码不要当作权威。
