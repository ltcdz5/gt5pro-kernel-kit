# 第5步c — 结构体对齐实验（决定性一步）：把 struct sched_ext_entity 逐字段对齐出厂内核

版本串：`75-ack304-v1.1-opt59`　树 HEAD：`bb7d854291b7`　父提交：`006e434ad3ad`（opt58）
lab：`F:\工作区\_lab\2026-10-09\scx-step5c\`

## 结论一句话

**"加字段向出厂对齐"能对齐布局（264B / 23 成员，逐字段偏移与出厂 BTF 全一致），但 CRC 一个都没动。**
`task_is_scx` 自然 CRC 仍是 **`0x61658a4e`**，不是厂商期望的 `0xb3071c68`。
机制已定位：本树 genksyms 对结构体只发 **tag 引用**（`s#task_struct *`），**从不展开成员表**，
所以结构体布局改动对全部 15,489 个 CRC **零影响**。

⇒ **上一轮"加字段会改 CRC ⇒ 与不改结构冲突 ⇒ 硬阻塞"的说法被否证。**
对齐是**无害的**（三关全绿、覆写 4/4 不 SKIP、导出集逐名未变），而且**是必需的**
（厂商按出厂偏移访问：`task->scx` 必须在偏移 **3608**，`scx->sched_prop` 在 **168**）。
定点覆写（`task_is_scx` 那条）**仍然必需，未删除**。

## 3. 自然 CRC（未跑覆写）

`out/kernel/sched/.hmbird_export.o.cmd` 里 genksyms 的原始记录：

```
#SYMVER task_is_scx        0x61658a4e    <-- 厂商期望 0xb3071c68，不符
#SYMVER iso_masks          0x9998675b
#SYMVER sk_filter_trim_cap 0x43b2b8f0
```

自然值 = `0x61658a4e`，与 opt58 **一字不差**。⇒ 假设不成立；覆写条目**保留**（未删）。

## 4. 为什么 CRC 没动 —— 机制级证明（决定性）

1. kbuild（`scripts/Makefile.build`）：`gen_symversions` 在编译后跑 genksyms，
   把 `#SYMVER <name> <crc>` **追加**进 `.cmd`；modpost 的 `extract_crcs_for_object()` 读回。
2. 手工跑**同一个** genksyms 管线（复用 `.cmd` 里记录的同一套 c_flags），类型串是：
   ```
   task_is_scx t#bool task_is_scx ( s#task_struct * )
   iso_masks   s#scx_iso_masks iso_masks
   ```
   **只有 tag（`s#xxx`），没有成员表。**
3. 微对照（纯 genksyms，**不重新编译内核**）：
   - **M1** `struct scx_iso_masks` 40 → 48 字节 ⇒ `iso_masks` CRC **不变**
   - **M2** 改 `task_is_scx` **原型**（加一个 `int` 参数）⇒ SYMVER 条目**立即改变/消失**

   ⇒ genksyms 对"原型"敏感、对"结构体成员布局"**完全不敏感**。
   这同时解释了 kit 里 `iso_masks` 覆写注释中"改成员类型/加 __read_mostly/__aligned/const/数组均不变"的现象。

**更正**：`patch_crc_targeted.py` 中 `task_is_scx` 那条的依据"CRC 差异只来自 genksyms 对 struct
task_struct 展开的差异"**不成立** —— genksyms 从不展开结构体。差异来源只能是 TU 上下文里
`bool` 之类 typedef 的展开差异（同 `iso_masks` 的情形）。覆写本身仍然正确且必需。

## 6. 结论 / 下一步

- **CRC 意义上：走不通。** "对齐布局就自然匹配 CRC"不存在 —— 本树 genksyms 不看结构体成员。
- **工程意义上：走得通，而且应当保留。** 布局对齐 + 定点覆写可共存；上一轮的"硬阻塞"是误判，
  `ext.c` 按出厂子集裁剪这条路**没有被结构体约束堵死**。
- **下一步**：还缺 `struct scx_dispatch_q` 的 `last_consume_at` / `is_timeout` 两个字段
  （出厂 96B vs 本树 80B）。同理，加它们**不会改动任何 CRC**，零 ABI 风险。
