## 3. 出厂 vs 公开：OPPO 把 `hmbird_sched` 换成了上游 sched_ext（证据清单）

| 探针（`Image.stock` 35,695,104 B） | 出厂 | 公开 drop（本树） | 判定 |
|---|---|---|---|
| `<hmbird_sched>` 格式串 | **42** | **0** | 出厂是 OPPO fork |
| `<slim_sched>` | 2 | 0 | 同上 |
| `pcp_dsq` | 3 | 0 | 同上 |
| `gdsqs` | 1 | 0 | 同上 |
| `task_linked_on_dsq` | 2 | 1（上游同名函数） | — |
| `scx_dsq_priq_less` | **0** | 有 | 上游符号，出厂**无** |
| `scx_bpf_switch_all` | **0** | 有 | 上游 kfunc，出厂**无** |
| `switched_all` | **0** | 9 | 出厂无此 debug/sysfs 键 |
| `sched_ext: ` | 2 | 多条 | 出厂也保留少量上游消息 |

出厂里能读到的 OPPO 专属消息（节选，与社区补丁逐字吻合）：
```
<hmbird_sched> <timeout>dsq[%d] still timeout task-%s, jiffies = %lu, deadline = %lu, runnable at = %lu
<hmbird_sched> <move>:task-%s, gdsq idx = %d, move from cpu%d to cpu%d
<hmbird_sched> <non> : cpu[%d] pcp_dsq_round is full, rtime = %d
<hmbird_sched> <par>bmax = %llu, lmax = %llu
<hmbird_sched>!task_linked_on_dsq(p),task = %s
<hmbird_sched>!scx_rq->nr_running,task = %s
```

**结论**：出厂内核的 sched_ext 是 OPPO 的 `hmbird_sched/slim_sched` fork（含全局 DSQ `gdsqs`、per-CPU DSQ `pcp_dsq`、cgroup 层级、iso mask、heartbeat/watchdog），
而 OPPO 开源投放的 `kernel/sched/ext.c` 是**上游 sched_ext**（含 `scx_dsq_priq_less`/`scx_bpf_switch_all`，且 `//#include "./slim_walt.c"` 与 `//slim_walt_enable(true);` 只剩注释）。
**两者不是同一个调度器。**

> 这同时**解释了 opt43 的整机硬挂死**：我们拿上游 sched_ext 去承载一个为 OPPO fork 准备的厂商栈/BPF 调度器，API 与状态机都不匹配。

## 6. 风险与红线

1. **不要把 opt56 直接刷机后交给 Scene 去 enable**。本轮恢复的是**能力**（struct_ops 可注册 + enable 不再短路），但块1 未做 ⇒ opt43 的挂死条件仍在。刷机可以（`boot_a` + `set_active a`），但**不要主动 register 任何 scx 调度器**。
2. 回退：`git revert` opt56 的 4 个文件改动即可回到 opt55 可编状态；镜像回退用 `images/boot-v1.1-opt55-repacked.img`（md5 `aca40a5cc4c81f7516bf734bc1bdacaf`）。
3. `kernel/sched/hmbird_export.c` 的 10 个导出是**出厂契约**，任何合并都不得覆盖或减少。
4. `CONFIG_OPLUS_FEATURE_SCHED_ASSIST` 保持关闭（打开即触发 `register_hmbird_sched_ops`/`test_task_is_hmbird` 遮蔽 = 闸门1 判砖）。
5. 块1/块5 一旦落地会牵动 `kernel/sched/` 全部导出符号的 genksyms CRC ⇒ 每次必须跑 `gate_vko_crc` + `audit_all`（493 模块）。
6. 阶段0 只读普查未改任何东西；本轮只改了 4 个文件。
