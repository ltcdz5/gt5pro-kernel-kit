# App 冷启动基线 —— 协议（判据先写死，2026-10-02）

> 项目纪律：**判据必须在看数之前写死**，看完数不许改。

## 一、为什么用这个指标

项目已判定"功耗/吞吐"不可测（噪声带 I/O 20~46%、功率 CV 41%，待测效应 ≤1%）。
开机时长那条路**机主已明确放弃**（"20 多秒够快了"）。

⇒ 剩下的可测指标里，**app 冷启动时间**是最贴近"用户感知的快"、且方差最小的一个。

## 二、测量方法

对每个目标 app：

| 步 | 动作 |
|---|---|
| 1 | `am force-stop <pkg>`（保证不是热启动） |
| 2 | `sync; echo 3 > /proc/sys/vm/drop_caches`（清页缓存 ⇒ **真冷启动**） |
| 3 | 等 3 s |
| 4 | `am start -W -n <component>` ⇒ 抓 `TotalTime` / `WaitTime` / `ThisTime` |
| 5 | 等 5 s 再下一轮 |

## 三、目标 app 与入口

| app | 包名 | 入口 | 性质 |
|---|---|---|---|
| 抖音 | `com.ss.android.ugc.aweme` | `.splash.SplashActivity` | 重渲染 + 重解码 |
| 微信 | `com.tencent.mm` | `.ui.LauncherUI` | 重 I/O |
| 设置 | `com.android.settings` | `.Settings` | **轻量对照**（应最稳） |

## 四、判据（写死）

1. **每 app 跑 5 轮**，报 `TotalTime` 的**中位数 + 极差 + 极差/中位**。
2. **散布 = 极差/中位**。这是本指标在本机的"噪声带"。
3. 跨版本比较时：**|中位差| < 散布 ⇒ 报"测不出"**，不许硬解释。
4. 主指标 = `TotalTime`（`WaitTime` 含系统调度排队，仅参考）。

## 五、已知的测量条件（如实记录，不做控制）

- 机主已装 `extreme_gt`（去温控 + 去锁帧 + 电池计覆盖）⇒ **不会热降频**，对本指标是利好。
- 设备是机主日常机，**后台负载不空**（loadavg ~6）。因此：
  - ⚠️ 本基线**不是"安静环境"的绝对值**；
  - 但同机同状态的**配对比较**仍然有效（这是本基线的用途）。
- 电量 13%（`extreme_gt` 覆盖了电池计，读数仅供参考）。
