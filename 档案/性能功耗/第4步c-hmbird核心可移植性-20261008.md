### 1.1 方法学修正（上一轮的一处口径问题）

上一轮用 `strings` 方式从 `natsu_Image` 提取出"137 个 hmbird 符号"。
本轮复核：那是**裸字符串**（含日志前缀、注释、结构体成员名），**不是导出符号表**。
`natsu_Image` 里 `hmbird_dir`/`__scx_ops_enabled`/`task_is_scx`/`iso_masks` 等**反而 0 命中**。
⇒ 本报告**不使用**"137 符号"这一口径，改为：**出厂导出表 ∩ 厂商模块 UND ∩ 我们 symvers** 三方精确对账。

### 1.2 一条必须说明的解析陷阱（本轮踩到并已修正）

厂商 `.ko` 的 `__ksymtab_gpl` 节**在文件里是全 0 的**（`000000000000000000000000`），
真正的 value/name 偏移由 `.rela___ksymtab_gpl+<name>` 重定位在装载时填入。
⇒ 直接读 `.ko` 的 ksymtab 原始字节会得到 **0 个导出**（本轮第一次尝试的假结果）。
**正确口径**：读 `.symtab` 里 `__ksymtab_<name>` 的符号项（本轮第二次解析，得 4,592 名）。
下文所有"厂商模块导出"结论均以此为准。

> ⚠️ **本节是本报告最重要的一张表**。任务书给的例子（`register_hmbird_sched_ops`、`test_task_is_hmbird` 由 `oplus_bsp_sched_assist.ko` 导出；`get_hmbird_cpu_exclusive` 由 `oplus_bsp_game_opt.ko` 导出）**全部实测证实**，并且本轮又找出 5 个同类（`set_sugov_tl_scx`、`register_walt_ops`、`waltgov_cb_data`、`msm_minidump_add_region`，以及待确认的 `walt_rq`/`sched_ravg_window`）。

### 3.2 一条修正：`walt_rq` / `sched_ravg_window` 为什么标"能补"却仍危险

- 树内**已有定义**且**源码里已经写着 `EXPORT_SYMBOL_GPL`**（`osi_cpuload.c:871`、`perf_schedinfo.c:148`）；
- 出厂**不导出** ⇒ 说明出厂把这两个符号的提供权留给了厂商模块；
- 因此这两个名字的"能补"**只是语法上能补**：真正落地前**必须先实测**设备 `/proc/kallsyms` 里有没有它们（本轮用的 `dev53_ksymtab.txt` 已剔除模块符号，**看不到**）。
- 若 `sched-walt.ko` 已导出 ⇒ 立即降级为 **不能补**。
- **本轮实测缺口**：缺一份"含模块符号的 `/proc/kallsyms` 全量转储"。这是唯一还差的证据。

### 3.3 非遮蔽但需注意

- `__tracepoint_android_vh_scx_sched_lpm_disallowed_time`：出厂**不导出**，opt54 我们**主动新增导出**（`e018ffdcc140`）。它**不遮蔽任何东西**（出厂没有），是"宽容项"——为让 `oplus_bsp_game_opt.ko` 能装载而刻意补的。**不需要回退**，但要在台账里标注"我们比出厂多 1 个 scx tracepoint"。

## 4. CONFIG 门控分析

### 4.1 现役配置（`out/.config` 实测）

| 配置项 | 值 | 说明 |
|---|---|---|
| `CONFIG_OPLUS_FEATURE_SCHED_ASSIST` | **不存在（=n）** | ⇒ `sa_hmbird.c` / `sa_balance.c` / `sa_common.c` **不参与编译** |
| `CONFIG_HMBIRD_SCHED` | **不存在** | 出厂 =y；出厂是把 `SLIM_SCHED`+`SCHED_CLASS_EXT` **改名**成它（见 §4.3） |
| `CONFIG_SLIM_SCHED` | **=y** | sched_ext 机器已启用 |
| `CONFIG_SCHED_CLASS_EXT` | **=y** | 同上 |
| `CONFIG_SCHED_WALT` | 不存在 | WALT 由厂商模块 `sched-walt.ko` 提供 |
| `CONFIG_OPLUS_SCHED` | 不存在 | — |

### 4.2 打开 `CONFIG_OPLUS_FEATURE_SCHED_ASSIST` 会补上什么、有什么副作用

**会补上的（3 个）**

| 符号 | 来源文件 |
|---|---|
| `register_hmbird_sched_ops` | `kernel/oplus_cpu/sched/sched_assist/sa_hmbird.c:22`（`EXPORT_SYMBOL_GPL`） |
| `test_task_is_hmbird` | `sa_hmbird.c:32`（`EXPORT_SYMBOL`） |
| （连带）`task_is_scx` 的 `sa_hmbird.c` 版本 | `sa_hmbird.c:26`（会与 hub 的 `task_is_scx` 冲突） |

**副作用（逐条，全部是负面）**

1. **遮蔽 ⇒ 硬违反闸门1**：`register_hmbird_sched_ops` / `test_task_is_hmbird` 由 `oplus_bsp_sched_assist.ko` 导出 ⇒ 内核再导出即遮蔽（opt6/`test_task_ux` 致砖机制）。**直接否决。**
2. **重定义风险**：`sa_hmbird.c` 也定义 `task_is_scx`，与 `kernel/sched/hmbird_export.c` 的定义冲突（`hmbird_export.c` 里 `EXPORT_SYMBOL_GPL(task_is_scx)` 在 `CONFIG_SCHED_CLASS_EXT` 下编译）⇒ 链接期 `duplicate symbol`。
3. **ABI 漂移面放大**：`sa_balance.c`(115 KB)、`sa_common.c`(57 KB)、`sa_balance.h`、`sa_common.h`(24 KB) 会开始编译，这些文件引用的 `struct` 与 vendor hook 会牵动大量导出符号的 genksyms CRC ⇒ **493 模块 CRC 闸门风险成批上升**。
4. **缺依赖**：`sa_hmbird.c:10` `#include "sa_common.h"`，而 `sa_common.h` 依赖 `include/linux/sched/sa_common*.h`（出厂 OSS 侧有，本树**没有**）⇒ 大概率编不过，需要连带补头文件（又扩大改动面）。
5. **产出为 0**：即便编过，新增的也只是 3 个**必须遮蔽**的符号 ⇒ **净收益为负**。

⇒ **结论：`CONFIG_OPLUS_FEATURE_SCHED_ASSIST` 绝不能打开。**（与 opt55 台账 §十二 的结论一致，本轮用三方对照再次证实。）

### 4.3 为什么"补 `CONFIG_HMBIRD_SCHED` 底座"也不做

1. **底座已在**：出厂 `CONFIG_HMBIRD_SCHED=y` 且**没有** `SLIM_SCHED`/`SCHED_CLASS_EXT` ⇒ 是**改名**。我们 `SLIM_SCHED=y`+`SCHED_CLASS_EXT=y` ⇒ sched_ext 机器已启用。
2. **抄了是空壳**：本树全树仅 7 处 `CONFIG_HMBIRD_SCHED`，可用者只有 `sa_hmbird.c`(2) 与 `sa_balance.c`(3)；而 `CONFIG_OPLUS_FEATURE_SCHED_ASSIST=n` ⇒ 这两个文件不编译 ⇒ **加 `CONFIG_HMBIRD_SCHED=y` 零效果**。
3. **抄了是陷阱**：一旦有人顺手打开 `OPLUS_FEATURE_SCHED_ASSIST`，就触发 §4.2 的遮蔽。

### 4.4 若真要补 `walt_rq` / `sched_ravg_window`（推荐做法）

**不要**打开 `CONFIG_OPLUS_FEATURE_SCHED_ASSIST`；而是**把定义搬进已经参与编译的 hub**：

```c
/* 追加到 kernel/sched/hmbird_export.c —— 该文件已在 opt55 里编译并导出 10 个名字 */
/* 前置条件：先实测确认 sched-walt.ko / oplus_bsp_sched_assist.ko 未导出这两个名字 */
#ifdef CONFIG_SCHED_CLASS_EXT   /* 或直接无条件，按实测决定 */
u64 sched_ravg_window = 0;      /* 与 osi_cpuload.c/perf_schedinfo.c 的现有定义二选一 */
EXPORT_SYMBOL_GPL(sched_ravg_window);
#endif
```

**副作用**：
- 不新增结构体、不改布局 ⇒ **493 模块 CRC 不受影响**；
- 但 `walt_rq` 在 `osi_cpuload.c` 里是**结构体类型**（`struct walt_rq *`），搬到 hub 需要把 `struct walt_rq` 定义一并搬（来自 `sched-walt` 私有头，本树没有）⇒ **`walt_rq` 的搬运成本远高于 `sched_ravg_window`**；
- 若遮蔽复核不通过（设备 `/proc/kallsyms` 显示厂商模块已导出）⇒ **立即放弃，不得补**。

## 6. 定论

### 6.1 这个移植值不值得做

| 层 | 值得做吗 | 理由 |
|---|---|---|
| **补 10 个 hub 符号** | **已经做完了**（opt54+opt55） | 出厂导出面逐名一致，`oplus_bsp_sched_ext.ko` 已可装载 |
| **补 `sched_ravg_window`** | **边际价值，可做可不做** | 只减少 1 个未解析符号；且需先确认不遮蔽 |
| **补 2 个 scx tracepoint** | **对齐出厂，价值低** | 没有任何 493 模块引用它们 |
| **补 hmbird 调度类（核心）** | ⛔ **不值得，且不应该做** | 见 6.2 |

### 6.2 明确"不建议做"的判据（三条，任一成立即否证）

**判据 1（最硬）：出厂内核根本没有这个东西。**
`enqueue_task_hmbird` / `check_preempt_curr_hmbird` / `get_hmbird_ops` / `hmbird_sched_class` / `init_sched_hmbird_class`
在 `Image.stock`（35,695,104 B）里 **0 字节命中**，在出厂导出表（63,569 名）里 **0 命中**。
⇒ 移植一个"出厂都没有的调度类"，等于**在已验收的 opt55 上凭空引入一个未验证的调度类**，与"复刻出厂行为"的项目目标**方向相反**。

**判据 2：收益为零、风险为正。**
`oplus_bsp_sched_ext.ko` 在 opt55 上**已经能装载**（CHANGELOG §十二 上机核验 ①）。它需要的是**符号**，不是 hmbird 调度类。
hmbird 调度类对厂商模块的可装载性**零贡献**，却要动 `kernel/sched/core.c`（+269/−13）、`build_policy.c`、`fork.c`、`idle.c`、`tick-sched.c` —— 直接冲击"493 模块 CRC 全绿"这条最硬的验收线。

**判据 3：跨代且依赖缺失。**
补丁是 SM8750/MT6991 一代（`SCHED_PATCH` 只有 mt6991/sm8735/sm8750 三个分支，**无 sm8650**）；
且依赖 `CONFIG_DYNAMIC_WALT_SUPPORT`、`include/linux/sched/sa_common*.h`（本树没有）等一整套缺失件。
社区自己的结论同向（"SM8650 的风驰有点残废"）。

### 6.3 与既有档案的关系

- `archive/非本项目归档/hmbird缺口与第三方内核对照-20261004.md` §6.8 的结案（"SM8650 无公开风驰 ⇒ 不可实现"）**本轮维持**，但**理由更精确**：
  不是"找不到提供者"，而是 **"出厂内核的提供者就是那 10 个导出符号，我们已经补齐；再往上没有东西可补"**。
- opt55 台账 §十二 的"hmbird 核心本树缺失"表述**方向正确**，但需补一句：
  **"该核心在出厂内核里也不存在（是 OGKI 侧未投放件），因此它不是移植缺口，而是本就不该由 GKI 半边提供。"**
