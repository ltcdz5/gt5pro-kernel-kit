## 1. 块1：`ext.c` 换血的落地口径

### 1.1 为什么**不**逐字整体替换（关键决策）

ferstar 的 `ext.c`（90,463 B）与我们现版（117,063 B）不是同一文件的两个版本，而是**两套不同的 sched_ext 实现**：
`diff -u` 共 **79 个 hunk / 5,002 行**，其中最大的一个 hunk 是 `@@ -133,210 +151,1164 @@`（ferstar 多出约 950 行的 slim DSQ 机器）。

整体替换要求同时改两个结构体：

| 结构体 | ferstar 有、我们没有的成员 | 位置 |
|---|---|---|
| `struct sched_ext_entity` | `unsigned long sched_prop; unsigned long running_at; int gdsq_idx;` | **内嵌于 `struct task_struct`** |
| `struct scx_dispatch_q` | `u64 last_consume_at; bool is_timeout;` | `include/linux/sched/ext.h` |

**为什么这是硬阻塞（不是保守）**：

- `struct sched_ext_entity` 是 `struct task_struct` 的成员 ⇒ 加字段即改 `task_struct` 布局 ⇒ 改 `task_struct` 的 genksyms CRC。
- 本树 `task_is_scx` 实测 CRC = `0x61658a4e`，厂商 `oplus_bsp_sched_ext.ko` 期望 `0xb3071c68`；
  `kernel-kit/tools/patch_crc_targeted.py` 的 OVERRIDES 第 4 条**明文写着**这个差
  "只来自 genksyms 对 struct task_struct 展开的差异"，并且该覆写以 **"旧 CRC 在 Image 里恰好出现 1 次"** 为生效条件。
  ⇒ 结构体一变，旧值 `0x61658a4e` 在 Image 里消失，覆写直接 **SKIP**，闸门2 立刻出现拒载。
- 与任务纪律「不改核心结构布局（会破 493 模块 CRC）」正面冲突。

⇒ 本轮采取**等价整合**：把 scx 分支里**不依赖新结构体成员**的那部分搬进来（含块2 全部可搬的调用点），
把依赖新成员的部分逐条登记为未完成（§5）。

### 1.2 命名 / 配置映射表

| ferstar `scx` 分支 | 本树 | 落地方式 |
|---|---|---|
| `CONFIG_HMBIRD_SCHED`（"hmbird Scheduling Class(base on ext scheduler)"） | `CONFIG_SCHED_CLASS_EXT` + `CONFIG_SLIM_SCHED` | 不改 config 名；`build_policy.c` 里已由块3/7 完成 `#ifdef CONFIG_SCHED_CLASS_EXT` 外层 + `#ifdef CONFIG_HMBIRD_SCHED` 内层 |
| `kernel/sched/ext.h` 的 `#ifndef _EXT_H_` | 我们的无 guard 上游版 | **本轮补 `#ifndef __SCX_EXT_H`**（用出厂名） |
| `ext.h` 的 `#ifdef CONFIG_SCHED_CLASS_EXT` 外仍保留 `#else` 桩 | 我们保留 | ferstar 版**删掉了** `#else` 桩；照搬会让非 ext 配置编不过 ⇒ 不照搬，只做增量 |
| `ext.c` 里 `#include "slim.h"` | 本树已有 `kernel/sched/slim.h`（块3） | 本轮在 ext.c 顶部加同一行 |
| `hmbirdcore_debug / partial_enable / tracing_mark_write` 由 `hmbird_sched_proc_main.c` / `slim_sysctl.c` 定义 | 那两个文件只在 `CONFIG_HMBIRD_SCHED=y` 时编进 build_policy.c | **所有权迁移**到 `hmbird_export.c`（`obj-y` 无条件）—— 见 §1.4 |
| `CONFIG_HMBIRD_SCHED` 保持 **n**（纪律要求） | `out/.config` 里 `# CONFIG_HMBIRD_SCHED is not set` | 未打开 ✓ |

### 1.3 `ext.h` 的两处增量（+72 行）

1. **include guard**：`#ifndef __SCX_EXT_H / #define __SCX_EXT_H` 放在版权块之后，文件末尾 `#endif /* __SCX_EXT_H */`。
2. **OPPO/GKI 调试 + systrace 宏**（ferstar `ext.h` 原文移植）：
   `DEBUG_INTERNAL / DEBUG_INFO_TRACE / DEBUG_INFO_SYSTRACE`、`debug_enabled()`、
   `scx_debug / scx_err / scx_info_trace / scx_info_systrace / scx_internal_trace / scx_internal_systrace`，
   外加 `extern int hmbirdcore_debug;` 与 `extern noinline int tracing_mark_write(const char *buf);`
   （ext.c 在 build_policy.c 里先于 slim.h 被 include，这两个声明必须在 ext.h 里可见）。

> 唯一一处**有意偏离**：出厂写法是 `(unlikely(hmbirdcore_debug & DEBUG_INFO_TRACE | DEBUG_INFO_SYSTRACE))`，
> 因 `&` 优先级高于 `|` 而**恒真**。本树改成 `(hmbirdcore_debug & (DEBUG_INFO_TRACE | DEBUG_INFO_SYSTRACE))`。
> 影响面仅限 `set_next_task_scx()` 里那个 debug-only 的 `android_vh_get_util` 采样，已在代码注释里标注。

### 1.4 `ext.c` 的等价整合（+171 行）

新增（都在 `CONFIG_SCHED_CLASS_EXT=y` 下无条件编译）：

- `#include "slim.h"`、`#include <trace/hooks/sched.h>`
- `enum task_event { PUT_PREV_TASK=0, PICK_NEXT_TASK=1, TASK_WAKE, TASK_MIGRATE, TASK_UPDATE, IRQ_UPDATE }`（ferstar 原文）
- `struct scx_iso_masks` 声明 + `extern struct scx_iso_masks iso_masks;`
  （对象实体仍在 `hmbird_export.c`，布局 ex_free/exclusive/partial/big/little 逐字节不变）
- `enum cpu_type`、`is_partial_enabled()`、`cpu_cluster()`（ferstar 原文）
- `task_fits_cpu_scx()` 并接进 `task_can_run_on_rq()`
- `update_load_enable()` 并在 `scx_ops_enable()` / `scx_ops_disable_workfn()` 各接一次
- 5 处占位替换 + `scx_select_cpu_dfl` / `check_preempt_curr_scx` / set_next 调试块

**三个全局的所有权迁移（编译期硬约束，本轮实测踩到）**：
ext.c 在 `CONFIG_SCHED_CLASS_EXT=y` 下**无条件**编译，而 `hmbirdcore_debug` / `partial_enable` / `tracing_mark_write`
原先由 `hmbird_sched_proc_main.c` / `slim_sysctl.c` 定义，那两个文件只在 `CONFIG_HMBIRD_SCHED=y` 时编进 build_policy.c。
第一次构建正是在 `LD .tmp_vmlinux.kallsyms1` 阶段以 **rc=2** 失败：

```

ld.lld: error: undefined symbol: hmbirdcore_debug   (ext.c:1755 set_next_task_scx)
ld.lld: error: undefined symbol: tracing_mark_write (ext.c:1759 set_next_task_scx)
```

修法沿用 `hmbird_export.c` 自己的头注释所立的规矩
（"These variables must be defined outside of CONFIG_HMBIRD_SCHED MICRO"）：
把这三个定义搬到 `hmbird_export.c`（`obj-y` 无条件），并从原属主文件删掉重复定义。
**10 个导出一个都没动**，`hmbird_export.c` 的 diff 只有 +19 行纯新增。

## 5. 未完成项 / 留给后续轮次

1. **#4/#5 `consume_hmbird_global_dsq()` 的 2 个 `scx_consume_dsq_allowed` 调用点** —— 需要整条 slim 全局 DSQ 机器：
   `gdsqs[]` / `pcp_info` / `per_cpu(pcp_ldsq)` / `sinfo` / `slim_stats_record()` / `MAX_GLOBAL_DSQS`，
   以及 `struct scx_dispatch_q.is_timeout`、`struct sched_ext_entity.gdsq_idx` 两个**新结构体成员** ⇒ 触发 §1.1 的 CRC 阻塞。
2. **#2/#3 `partial_dynamic_ctrl()` 的 2 个 `get_util` 调用点** —— 该函数依赖
   `set_partial_status() / update_partial_idle() / is_partial_enabled() / is_little_need_rescue() / is_big_need_rescue()`，
   本树**只**有 `partial_enable`（块3 落地的 slim.h/hmbird_sched_proc_main.c 里没有前 5 个）。
   单独搬一个"只会调 hook 的壳"没有出厂语义，故不做。
3. **#8 `check_misfit_task_on_little()` 的 `get_util` 调用点** —— 依赖 `p->scx->sched_prop`
   （`SCHED_PROP_DEADLINE_MASK/LEVEL1..3`）与 `struct cluster_ctx / gen_cluster_ctx()`，前者是 §1.1 的新结构体成员。
4. **#15 的 cluster gate 是"缩水版"** —— 出厂版在 `check_result <= 0` 之后还要看 `p->scx->sched_prop` 的 deadline 级别；
   本树无该成员，只保留了 `cpu_cluster()` 的 EXCLUSIVE/PARTIAL 闸门 + `rq->curr->prio > p->prio` 比较，代码里已注释说明。
5. **#16 `update_load_enable()` 去掉了 tick 时钟部分** —— 出厂版还会 `WRITE_ONCE(tick_sched_clock, 0)` 并
   `atomic_set_release(&set_sched_clock_prepare, true)`；这两个静态变量属于 `scx_scheduler_tick()/scan_timeout()` 的 slim tick 机器，
   本树没有。只保留了状态去重 + 厂商回调。
6. **块1 的"整体替换"路径仍待裁决** —— 若将来要做，必须先证明 `struct sched_ext_entity` 加
   `sched_prop/running_at/gdsq_idx` 之后 `task_is_scx` 的 genksyms CRC 仍能对上厂商期望值（或同步更新
   `patch_crc_targeted.py` 的覆写键），并重跑 493 模块闸门。**建议单独立实验分支**，与本轮隔离。
