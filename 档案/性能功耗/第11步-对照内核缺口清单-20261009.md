## 0. 一句话结论

**对照内核（能跑）与出厂内核是同一套架构：`scx_*` 符号族 + `ext_sched_class` + `ext_module_loaded`；它同样没有 `hmbird_sched_class`、没有 `hmbird_ops_enable`、没有 `hmbird_ctrl`。**
我们把 **另一份血统的 `hmbird_sched_class` 家族**（19 文件，CORE=y 编进内核）当成启用路径，于是 `scx_enable=1` 走进的是一条**出厂与社区都从未验证过**的路。
本轮与第10步（静态反汇编）结论**独立互证**：社区内核是第二个、且是「跑得起来」的证人。

## 3. 精确缺口清单（名称 / 对照证据 / 我们现状 / 补法 / 风险）

> ABI 总原则：以下全部为**内核内部新增**，**任何一条都不得加 `EXPORT_SYMBOL*`**；导出集必须仍是 **15,489**；不得 `olddefconfig`。

### G1 `scx_scheduler_tick`（★最高优先）
* 对照证据：对照 kallsyms 有 `scx_scheduler_tick`；**出厂 `Image.stock` 也有**（stock=1 / ref=1 / ours=0）；对照另有一条专用串 `hmbird: scheduler tick did not initialize the load window`。
* 我们现状：`out-core/vmlinux` 中 `scheduler_tick` 只匹配到 tracepoint 名；家族侧只有 `hmbird_notify_sched_tick()`（hmbird.c:3052），**没有把 tick 接进 ext 调度类的 `.task_tick` 链路**。
* 补法：在 `kernel/sched/ext.c` 补 `.task_tick = task_tick_scx`，在其中推进 load window / `hmbird_sched_ravg_window`，并接上家族侧 `hmbird_notify_sched_tick()`。
* 风险：只改 ext 内部函数表，**不动 ABI**；风险在于本树 ext.c 版本与对照不同，须先逐指令核对该 slot 现值。

### G2 `scx_restore_governors` + `scx_gov_mutex`（调频联动）
* 对照证据：对照 kallsyms 二者皆在（stock=0 / ref=1）；字符串 `hmbird: CPU%d governor restore failed: %zd`。
* 我们现状：`hmbird.c:3767-3935` enable 路径全文**不含 `cpufreq`**；只有 disable 侧 `slim_walt_enable(false)`，enable 侧无对应 `(true)`（第10步 §1.3 第 8/9 条同结论）。
* 补法：补一对 `scx_save_governors()/scx_restore_governors()` + `scx_gov_mutex`，enable 前保存、enable 失败或 disable 时恢复；置于 `hmbird_ctrl()` 之前。
* 风险：涉及 cpufreq/opp 交互，是硬挂高发区；必须先在 E0/E1 档（见 §6）验证 governor 能原样恢复。

### G3 dsq 内部编号维护：`update_dsq_idx` / `cgrp_dsq_idx_init` / `SCX_BPF_DSQS_DEADLINE`
* 对照证据：`update_dsq_idx`、`max_ext_dsq_internal_id`、`SCX_BPF_DSQS_DEADLINE`（串 `DSCX_BPF_DSQS_DEADLINE`、`scx.deadline`、`scx_deadline_idx`）在**出厂与对照都有**；`cgrp_dsq_idx_init` 对照有。
* 我们现状：本树已有 `max_hmbird_dsq_internal_id`（改名），但 **`update_dsq_idx` / `cgrp_dsq_idx_init` 无任何同义实现**，也没有 `scx.deadline` / `scx_deadline_idx`。
* 补法：按对照补 `update_dsq_idx()`（internal id ↔ dsq 双向表）与 `cgrp_dsq_idx_init()`；若暂不启用 deadline 特性，至少补一条「表未建立即拒绝 enable」的前置检查。
* 风险：低（纯内部表）；漏补会让 gdsq/partial/pcp 的 id 越界——与候选 C3 直接相关。

### G4 per-cgroup SCX deadline 子系统：`cgroup_read_scx_deadline` / `cgroup_write_scx_deadline`
* 对照证据：对照串 `3<sched_ext> <cgroup_read_scx_deadline> i is %d, less than 0, name is %s`，符号 `cgroup_read_scx_deadline` / `cgroup_write_scx_deadline` / `scx.deadline` / `scx_deadline_idx`。
* 我们现状：**完全没有**。
* 补法：作为可选特性排在最后；先只补「cgroup 文件不存在即视为未配置」的读侧兜底。
* 风险：中；新增 cgroup 文件引入新的用户可见面（不是导出符号，不计入 15,489，但发布前需明确声明）。

### G5 接口层缺口：`hmbird_stat_fops` / `hmbird_stats_open` / `hmbird_stats_show` / `slim_gov_debug` / `slim_controls`
* 对照证据：`hmbird_stat_fops`、`hmbird_stats_open`、`hmbird_stats_show` **出厂与对照都有**；`slim_gov_debug` 出厂也有；`slim_controls` 对照有。
* 我们现状：本树用 `hmbird_stats_proc_ops`（`hmbird_sched_proc.c:158-181`，`single_open`）实现了同名 `/proc/hmbird_sched/hmbird_stats`，**但形态与出厂不同，且缺 `hmbird_stat_fops`（debugfs 形态）**。
* 补法：把 stats 拆成 `open/show` 一对 + `hmbird_stat_fops`，并补 `slim_gov_debug`、`slim_controls`。
* 风险：**极低**；且直接对应「接口层 21/27 → 27/27」这条已验收指标（缺的 6 条很可能就在这里）。

## 4. 「写 scx_enable=1 即硬挂死」根因候选（按可能性排序）

排序依据：① 对照/出厂是否**一致存在**；② 是否在 enable 必经路径上；③ 能否解释「adb 失联 + USB 不枚举 + 无 pstore」（硬挂而非 panic）。

| # | 可能性 | 候选 | 证据 | 与第10步的关系 |
|---|---|---|---|---|
| **C1** | **★★★** | **启用位与厂内状态机脱钩，且缺 tick/load-window 前置** | 对照与出厂都是 `ext_sched_class` + `ext_module_loaded`，都**没有** `hmbird_sched_class`；对照专门有门控串 `vendor module not loaded; cannot enable SCX` 与 `scheduler tick did not initialize the load window`，两条我们都没有；我们的 `hmbird_module_loaded` 被**开机** `hmbird_misc_init()` 置 1（`hmbird_misc.c:145`），门控等于被绕过 | 与第10步候选 1（启用位脱钩）一致，并新增「缺 `scx_scheduler_tick`」这一可补的实物级证据 |
| **C2** | ★★☆ | **调频联动缺失**：enable 期间无 governor 保存/恢复 | 对照有 `scx_restore_governors` / `scx_gov_mutex` + `governor restore failed` 串；我们 enable 路径全文无 `cpufreq` | 第10步 §1.3 第 8 条（本步升级为「对照有实物实现」） |
| **C3** | ★★☆ | **dsq 内部编号表缺失** → gdsq/partial/pcp 的 id 越界 | 对照与出厂都有 `update_dsq_idx` / `max_ext_dsq_internal_id` / `SCX_BPF_DSQS_DEADLINE`，我们只有改名的一半 | 第10步未单列；本步新增 |
| **C4** | ★★ | **CPU 拓扑/iso_masks 无兜底** | 对照有 `unexpected CPU topology, using all possible CPUs` 兜底；本树只有 `can't find cpu cluster` 一句打印，`set_cpu_cluster()` 读 DT `/soc/oplus,hmbird`，读空则 5 个 mask 全空 | 第10步未列；本步新增（我们已有 DT 版本兼容层，但**拓扑值本身**未兜底） |
| **C5** | ★☆ | **两套 sched_class 并存**（`__hmbird_sched_class` 与 `__ext_sched_class` 同处 `__sched_class` 段） | 本树 `vmlinux.lds.h:134-135`；对照只有一套 | 第10步候选（结构性，属「该不该走这条路」而非「补哪一环」） |

**判断**：C1 是主因，C2/C3/C4 是它的四个「缺环」，任一环都足以让 enable 走进未初始化状态；C5 是路线判断（§5 第 0 项）。
四者**不互斥**，且都指向同一个可操作结论：**先补齐对照侧那些安全门（尤其 G1），再谈 enable**。

## 6. 上机定位方案（供 Lead 执行；本步**不执行**）

### 6.1 breadcrumb（不刷内核也能定位「走到哪一步」）

在 `hmbird_ctrl()` → `bpf_hmbird_reg()` → `hmbird_ops_enable()` 之间插 8 个 `pr_emerg` 落点：
`B1 ctrl 入口` → `B2 门控通过` → `B3 ops_helper 创建` → `B4 cpus_read_lock + fork_rwsem` → `B5 遍历任务切类开始` → `B6 遍历任务切类结束` → `B7 static_branch_enable` → `B8 __hmbird_ops_enabled=1`。
同样在 `scx_scheduler_tick` / `restore_governors` 入口各打一点。要求 `pr_emerg` + console 已注册（`console_flush_on_panic`），并在 `hmbird_switch_log` 里同步 stage 号，便于只用 pstore 也能定位。

### 6.2 分阶段 enable（每档必须先抓到 breadcrumb 再进下一档）

| 档 | 做什么 | 期望 | 不放行的条件 |
|---|---|---|---|
| E0 | 只置状态位，不注册 sched_class、不切任务 | B1–B3 全出、系统存活 | 任一 breadcrumb 缺 → 停 |
| E1 | 注册 class、`switch_all=0`（不切任何任务） | B4–B7 全出、`/proc/hmbird_sched` 仍可读 | 出现 `SCX error` 或 adb 抖动 → 回滚 |
| E2 | 只切 CPU0/CPU1（`cpu_cluster_masks` 在 E2 前置先填好拓扑） | B5–B8、`sched_switch` 出现 hmbird 任务 | 单核即硬挂 → 问题在 enable 原语而非任务迁移 |
| E3 | 全量切换 | 全量稳定 ≥10 min | — |
