## 0. 结论摘要（TL;DR）

1. 权威源已锁定并取到全量路径清单（§1）。
2. 阶段0 清单完成：**新增 3 个内核文件、需整合 48 个既有文件、我们独有文件 0 个**（§2）。
3. **三个硬阻塞级事实**，直接决定阶段1/2 的做法：
   - **命名体系不同**：scx 分支用 `CONFIG_HMBIRD_SCHED`；我们树用 `CONFIG_SCHED_CLASS_EXT` + `CONFIG_SLIM_SCHED`。我们树里 `CONFIG_HMBIRD_SCHED` **根本没有定义**（只在 3 个文件里被引用 ⇒ 恒为假）。照搬 scx 分支会把整条 sched_ext 编译路径关掉。
   - **scx 分支的 hmbird_export.c 是子集**：只有 8 个导出，我们 opt55 有 **10 个**（多 iso_masks、scx_get_md_info）⇒ 覆盖即丢导出，直接违反硬约束。
   - **厂商模块实测只缺 2 个符号**：register_hmbird_sched_ops、test_task_is_hmbird；而这 2 个**不在 scx 分支里**（scx 分支压根没有 kernel/oplus_cpu/），它们在我们树的 sa_hmbird.c，被两道 config 闸门挡住。
4. ⇒ **ferstar scx 分支是必要条件，但不充分**。"全套可用风驰" = scx 分支（内核侧 sched_ext）**＋** 我们树的 kernel/oplus_cpu/sched/sched_assist/（OPPO sched_assist 侧）。

## 3. 命名体系差异（阶段1/2 的核心决策点）

| scx 分支 | 我们树（opt55/opt56） |
|---|---|
| CONFIG_HMBIRD_SCHED=y（"hmbird Scheduling Class(base on ext scheduler)"） | CONFIG_SCHED_CLASS_EXT=y（"Extensible Scheduling Class"） |
| —（无） | CONFIG_SLIM_SCHED=y（"slim sched"） |
| CONFIG_DYNAMIC_WALT_SUPPORT（depends HMBIRD_SCHED，default n） | —（无） |

工厂 stock 对照（refs/stock_config.gz）：

| config | stock（原厂） | 我们 out/.config |
|---|---|---|
| CONFIG_HMBIRD_SCHED | **y** | 未定义 |
| CONFIG_SCHED_CLASS_EXT | 未定义 | y |
| CONFIG_SLIM_SCHED | 未定义 | y |
| CONFIG_OPLUS_FEATURE_SCHED_ASSIST | n | n |
| CONFIG_DYNAMIC_WALT_SUPPORT | n | 未定义 |

编译路径对照：

    scx 分支 kernel/sched/build_policy.c       我们树 kernel/sched/build_policy.c
    --------------------------------------     ------------------------------------
    #include "hmbird_export.c"                  (Makefile: obj-y += hmbird_export.o)
    #ifdef CONFIG_HMBIRD_SCHED                 #ifdef CONFIG_SCHED_CLASS_EXT
    # include "ext.c"                          # include "ext.c"
    # include "hmbird_sched_proc_main.c"       #endif
    #endif

⇒ **不能字面搬运**：必须做 HMBIRD_SCHED ↔ SCHED_CLASS_EXT 的符号映射（或反向补齐 CONFIG_HMBIRD_SCHED）。

## 4. 「离全套可用风驰还差哪几块」

### 4.1 厂商模块 oplus_bsp_sched_ext.ko 的实测缺口 —— 只差 2 个符号

用 refs/mod-exports-622mods-4623.txt（622 模块所需符号并集）∩ 我们 out/Module.symvers 计算，
hmbird/scx 相关所需符号中**只有 2 个我们没导出**：

| 缺失符号 | 谁需要 | 我们树里定义在哪 | 为什么没导出 |
|---|---|---|---|
| register_hmbird_sched_ops | hmbird/hmbird_misc.c:94 | kernel/oplus_cpu/sched/sched_assist/sa_hmbird.c:15（已 EXPORT_SYMBOL_GPL） | 见 4.2 两道闸门 |
| test_task_is_hmbird | sa_balance.c / sa_common.c 等 | sa_hmbird.c:24（已 EXPORT_SYMBOL） | 同上 |

其余全部已具备，包括：android_vh_scx_sched_lpm_disallowed_time 的 3 个符号
（__SCK__tp_func_* / __traceiter_* / __tracepoint_*），以及我们自己的 10 个导出
（slim_for_app / scx_sched_rq_stats / scx_irq_work_lastq_ws / ext_module_loaded / hmbird_dir / non_ext_task /
__scx_ops_enabled / iso_masks / scx_get_md_info / task_is_scx）。

### 4.2 两道闸门（根因）

1. **CONFIG_OPLUS_FEATURE_SCHED_ASSIST 未开** ⇒ kernel/oplus_cpu/sched/Makefile 里
   obj-$(CONFIG_OPLUS_FEATURE_SCHED_ASSIST) += sched_assist/ 不成立 ⇒ **整个 sched_assist/ 目录不编译**，
   sa_hmbird.c 根本不参与构建（out/kernel/oplus_cpu/sched/sched_assist/ 不存在）。
2. **CONFIG_HMBIRD_SCHED 未定义** ⇒ 即便编了 sa_hmbird.c，其内部
   #ifdef CONFIG_HMBIRD_SCHED 也把这两个符号的定义整个包住 ⇒ 仍然不导出。

### 4.3 待办清单（按依赖排序）

| # | 事项 | 依赖 | 风险 |
|---|---|---|---|
| 1 | 决定命名映射策略（补齐 HMBIRD_SCHED vs SCHED_CLASS_EXT 等价改造） | — | 中：影响全部闸门 |
| 2 | 接入 3 个新增文件（android.h / hmbird_sched_proc_main.c / slim.h） | 1 | 低 |
| 3 | 整合 ext.c / sched.h / include/linux/sched/ext.h / build_policy.c | 1 | **高**：ext.c ±4000 行分歧；sched.h 破布局即破 CRC |

### 4.4 明确的「不可做」项
- 本树**没有 WALT**（无 kernel/sched/walt/）⇒ CONFIG_DYNAMIC_WALT_SUPPORT 相关代码走不到，登记为已知缺口。
- **不得**用 scx 分支的 hmbird_export.c 覆盖我们版（会丢 iso_masks / scx_get_md_info）。
- **不得**主动 register 任何 scx 调度器（Scene 的 game_scheduler 由机主决定；opt43 曾整机硬挂死 + PMIC 复位）。
