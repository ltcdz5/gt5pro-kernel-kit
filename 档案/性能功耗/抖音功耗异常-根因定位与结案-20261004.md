# 抖音功耗异常：根因定位与结案（2026-10-04）

> 现象：刷抖音功耗从近期常态 **2.3~2.4W** 涨到 **3.5~5.2W**，且"没有 LP 调度那种轻微卡顿感"
> 结论：**根因是 2026-10-03 18:24 的 Scene 版本更新**，与内核改动**无关**
> 修复：清除 Scene 数据重建 → 功耗回到 **2.17W**（比常态更好）

---

## 一、根因：Scene 更新（时间戳铁证）

```
Scene lastUpdateTime  = 2026-10-03 18:24:08      ← ★ 更新时刻
Scene versionName     = N1 2026.10 Alpha10   ← 测量当时的版本；**2026-10-04 02:08 已更新为 Alpha11**（该更新使 opt42 观察期作废重算，见 CHANGELOG §一）
功耗异常起点（实测）   = 10-03 15:00 ~ 21:46 之间  ← ★ 18:24 精确落在窗口内
```

**官方更新日志里的这一行正是我们实测到的症状：**

> `-修复 部分操作后(如首页触发主动内存回收) LP/HP/EP 频率控制失效`

| 实测症状 | "频率控制失效"的表现 |
|---|---|
| 限频器不工作 | `scaling_max_freq` = 硬件最高（2265600/3148800/2956800/3187200），完全无上限 |
| 频率下限不生效 | 小核最低频 **1248MHz**（应为 364）、中核 **1286**（应为 499）、大核 **1248**（应为 480） |
| 体感 | "没有 LP 那种轻微卡顿感"（因为没有上限，也就没有那个卡顿） |
| 动态功耗 | 相同负载下 CPU cycles **翻 1.94~2.87 倍**（活没多干，时钟翻倍） |
| 低功耗状态消失 | 基线 22% 样本 <2000mW、5% <1500mW；异常时段 **0% <2000mW** |

**⇒ 完整的因果链**：
```
Scene 更新(10-03 18:24)
   └─ LP 频率控制失效（限频器 + 频率下限都不下发）
        ├─ CPU 被顶在 1.25GHz 下限之上（不能降频）
        ├─ 没有上限约束（该压的不压）
        └─ 动态功耗 ∝ f·V²  ⇒ 功耗 +0.8~1.0W、温度升高
             └─ 热降频 ⇒ 帧率反而更差
```

## 三、LSE 外挂模块的实测结论（已放弃）

**LSE = LunarKernel Scheduling Extention**（作者 Cloud_Yun，GPL v2），外挂 `.ko`，注册 `lunar_ext_gov` 调速器。

### 实测数据（同一晚、同一内容口径）

| 指标 | 有 LSE（无限频） | **无 LSE（原始配置）** | 结论 |
|---|---|---|---|
| 平均功耗 | 5201 mW | **3468 mW** | LSE **+1.7W** |
| 中核平均频率 | **2932 MHz** | **1661 MHz** | LSE 让中核多跑 **76%** |
| FPS 均值 | 55.5 | **64.8** | **无 LSE 反而更流畅** |
| CPU 温度均值 | 80.6°C | 60.3°C | LSE 更热 |

**⇒ 判定：LSE 在这台机器上是"又费电又更卡"的净负面方案。**

**机制**：LSE 的 Slim-WALT 负载跟踪抬高了 util 估计值 → governor 看到"高需求" → 把中核顶在 ~2.9GHz；而它同时**替换/干扰了厂商自己的 WALT 跟踪**，导致任务放置变差 → 帧率反而下降。

### LSE 的已知硬约束（记录备查）

| # | 约束 | 后果 |
|---|---|---|
| 1 | **没有 `module_exit`** | `rmmod` 必然失败，`[permanent]`，只能重启卸载 |
| 2 | **开机早期加载 ⇒ 卡死循环** | 实测触发过一次（卡锁屏 + 看门狗重启循环），需 ADB 删模块救援 |
| 3 | **`sched_ravg_window_frame_per_sec` 写 0 ⇒ 除零** | handler 无边界保护 ⇒ 内核崩 |
| 4 | **`LSE_DEBUG_PANIC` 是编译期常量** | 内部一致性检查失败直接 panic |
| 5 | **无"governor 被选中才启用"的门** | 不选它也一直付钩子开销 |
| 6 | 与厂商 `oplus_bsp_sched_assist` 共用 `task_struct.android_vendor_data1[63]` | 争用风险 |

### 合规提示（若将来要二次分发）

## 六、健康检查（以后防这个坑）

这类 bug **静默失效，没有任何报错**。一条命令自检：

```sh
su -c 'echo "限频器 max: $(for p in 0 2 5 7; do cat /sys/devices/system/cpu/cpufreq/policy$p/scaling_max_freq; done | tr "\n" " ")"; \
       echo "下限   min: $(for p in 0 2 5 7; do cat /sys/devices/system/cpu/cpufreq/policy$p/scaling_min_freq; done | tr "\n" " ")"'
```

| 判据 | 正常 | 失效 |
|---|---|---|
| `max_freq` | 明显低于硬件最高（如 612000~2956800） | **全是硬件最高**（2265600/3148800/2956800/3187200） |
| `min_freq` | 可达 364800 / 499200 / 480000 | **顶在 1248000 / 1286400**（厂商默认，降不下去） |

**处置**：`pm clear com.omarea.vtools` → 重进 Scene → 重新启用 LP 调度。
**预防**：Scene 每次更新后跑一次；**不要**手工改 Scene 的 `profile.json`。

## 七、数据附录（本次分析用到的口径）

  `min 0.90 / p10 2.46 / p25 2.80 / 中位数 3.20 / p75 3.61 / p90 4.10 / max 6.48 W`
