## 更正 1：t152 重启 ≠ hung_task 触发（我先前的判断是错的）

- **我先前的主张**：t152 的重启由 t152.sh 写入 `hung_task_panic=1` + `hung_task_timeout_secs=20` 造成。
- **证伪方式**：逐行读 `t152.sh`（74 行），15 处命中 `hung_task|panic|softlockup|sysrq|printk`，**全部是读取原值（`:9-13`）/ 还原（`:19-23`）/ 打印（`:15`、`:24`）**；`:3` 自述「不打开 panic」。真正写开关的是 `t151.sh:6-10`、`t149.sh:11-15`、`t142.sh:10-11`。
- **内核语义也反驳**：`kernel/hung_task.c:111-115` 在 switch_count 变化时刷新 `last_switch_time`；`:116` 的阈值是「自上次切换以来」，不是「累计阻塞」。
- **归档复核**：`'hung_task: blocked tasks'` 在 608 个 _audit 文本文件中 **0 命中**。
- **结论**：**t152 重启原因回到「未确定」。**

## 更正 2：Route B ≠ 「4 行改动」

- **我先前的主张**：采纳参照补丁只需 4 行。
- **实测**：`diff -u` 参照重建产物 vs 我们 ext.c = **77 hunk / -1424 / +1574 = 2998 行**；整文件置换约 **2700–3800 行**。
- **补充**：真正语义缺口只有 **373 行**（901 行已在 hmbird.c，590 行可复用）—— 但「缺口小」不等于「改动小」。

## 更正 3：「关闭路径 double-add 崩溃是主嫌疑」已被推翻

- **我先前的主张**：关闭路径的 `list_add double add` 是 t157 的主因。
- **证伪**：
  1. `t158` 20 轮 enable/disable 循环 **20/20 全过**，`list_add double add` / `__list_add_valid` / `WALT-BUG` / `Oops` / `BUG:` 全 0。
  2. `t157` 的 256 MB 完整 DDR 转储里，上述签名**也全是 0**（连 `HMBIRD_EXIT*` / `SWITCH_ERR*` / `err_exit` 都是 0）。
  3. 末行之后**连无关的充电刷屏日志都同时停止** ⇒ 形态是全机瞬时冻结，不是 list 破坏性 panic。
- **修正后**：Stage BS-P0 / BS-P0b / Stage BQ 三件套确实修掉了 double-add（20 轮验证），但**它不是 t157 的原因**。t158 的「20 轮全过」也不构成「关闭路径已修好」——**样本是 10 s，没覆盖 t157 的 62 s 条件**（见更正 4）。

## 更正 4：t158/t159 全过 ≠ 关闭路径安全

- **我先前的主张**：t159 关闭后观察 15 分钟干净 ⇒ 延迟崩溃假说被证伪。
- **修正**：t159 每轮只启用 **30 s**，t158 每轮只启用 **10 s**，**都没有跨过 enable 后 60 秒的看门狗首触窗口**；t157 的 R1/R2 都是 **62 s**。
- ⇒ 这两个实验的「干净」是**条件必然**，不是安全性证据。

## 更正 5：tick 三件套不是「挂死」而是「延迟补记」

- **我先前的主张**：缺 `DECLARE_COMPLETION` / `wait_for_completion` 会导致永久挂死。
- **修正**：`hmbird_util_track.c:496` 的提前 return 不更新 `sts->mark_start`（`:514` 才写），基线建立后走 `:499 update_window_start` 对 `[mark_start, wallclock]` **整段 catch-up 补记**；`hmbird_scheduler_tick()` 的调用点 `hmbird.c:3469` 在 `:3471 if(!hmbird_enabled())` **之前** ⇒ 与 enable 无关、开机第一个 tick 就建好全部 window_start ⇒ 空窗 ≤ 1 tick（HZ=250 ⇒ **≤4 ms**）⇒ 风险由「中」降「低」。

## 更正 6：minidump 的 md_HMBIRD 段是空的

- **我先前期待的**：设备侧 DFR 为 hmbird 预留了 `md_HMBIRD.BIN`（4096 B），里面应有 `md_info_t` 快照（`sw_rec[]` / `excep_rec[]` / `snap`）。
- **实测**：**4096 字节全零**。`md_KCNTXT` / `md_KRUNQUEUE` / `md_MEMINFO` / `md_KFTRACE` 同样全零。
- ⇒ 冻结现场无法从转储重建；只能靠源码 + 设备侧实时取证。

## 附：本轮同时划掉的两个嫌疑
