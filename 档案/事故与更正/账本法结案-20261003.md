## 一、方法（三步，缺一不可）

```
第 1 步：判"已落地 / 真候选 / 冲突"
    git apply --check --reverse  通过 ⇒ 已在树里
    git apply --check            通过 ⇒ ★真候选
    两者都失败                   ⇒ 上下文冲突

第 2 步：判"这个 commit 是修复还是前置"
    正文里有 Fixes:          ⇒ ★真修复
    正文里有 Stable-dep-of:  ⇒ 只是某个修复的【前置】，不是修复本身（跳过是对的）

第 3 步：判它碰的头文件是"加声明/加宏"还是"加结构体字段"
    只加函数原型/宏 ⇒ CRC 安全 ✅
    改结构体成员   ⇒ 会沿类型链炸开（opt39 事故：109 个 CRC 变化 / 7 模块拒载）⇒ ⛔
```

## 四、其余 47 条真修复为什么走不到（按区域）

| 区域 | 代表条目 | 为什么本机不跑 |
|---|---|---|
| `arch/arm64` KVM | vgic-its / WFI / CPU_ON rollback / tlb walk cache | **手机上 KVM 未启用**（无虚拟化场景） |
| `drivers/hid` | HID buffer size / wacom OOB write | HID 编入（47 个成员）但 **`/sys/bus/hid/devices` = 0** ⇒ 需插 HID 设备才可达；wacom 更需**罗技 Wacom**专用设备 |
| `drivers/usb` | xhci hcpriv / **f_ncm net_device 生命周期** | xhci 是 **host** 控制器，而手机是 **device** 角色（SM8650 两角色都走 dwc3）；<br>f_ncm 虽然 `CONFIG_USB_CONFIGFS_NCM=y` 且 `f_ncm.o` 进了 `vmlinux.a`，但**设备 gadget 用的是 `f_fs`/`f_rndis`/`f_ccid`，从没用过 f_ncm** ⇒ 与 ipset 同类 |
| `drivers/net` | pppoe: drop PFC frames | 手机不跑 PPPoE |
| `include/linux` | padata pd UAF / randomize_kstack / dmi / tpm / cdrom / fbdev defio / hugetlb hwpoison | 要么未编入、要么改 `task_struct` 等**禁令头**、要么场景不存在 |
| `kernel/trace` | tracing/probes 3K 限制 | 需 ftrace 事件探针，本机未用 |
| `include/uapi` | KVM x86 UAPI | x86，无关 |
| `include/rdma` | RDMA DMA 迭代器 | 未编入 |

## 五、方法论价值

**账本法一次排除了整条路** —— 它省掉的是"逐条读代码才发现没用"的大量时间。
本次从"有 1824 条真候选"到"可用 0 条"，只花了约 20 分钟。

**但它的产出上限受【可达性】限制**：账本里攒的是 **stable/ACK 的全部改动**，
而一台具体设备只跑其中很小一部分。⇒ **账本法是"排除工具"，不是"发现工具"。**

⇒ 后续内容只能靠**读代码**（按三条判据选可达区域，再逐行看），即 USB / lib 两路正在做的事。

## 六、下次要不要再翻账本

**不必全量翻。** 只在两种情况值得重跑：
1. 账本目录**有新内容**（builder 又攒了新的 gap）
2. **设备能力变了**（例：插了 HID 设备、开始用 OTG host 模式、开了 KVM）
