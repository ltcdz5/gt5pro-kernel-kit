# 更正：闸门基准是 `strings` 转储 + `prep_new_page` 判砖是假阳性（2026-10-03）

> ⚠️ **本文更正我们自己的两处错误结论。** 发现来自 `厂商模块导出依赖表-20261003.md`
> 的静态解析，并经我方独立复核（真 ELF 解析 + 设备侧决定性检验）。

---

## 一、错在哪：**闸门1 的基准不是符号表，是 `strings` 转储**

### 事实（可复现）
`kernel-kit/档案/事故与更正/判砖实验-a4a5.md` §3 记的基准生成命令是
```
strings -a /vendor_dlkm/lib/modules/*.ko /vendor/lib/modules/*.ko
```
—— **是字符串转储**。

实测（我方独立复核，用 ELF64 `.symtab` 的 `SHN_UNDEF` 表项重解析 493 个 `.ko`）：

| 指标 | 数值 |
|---|---|
| `vko_syms.txt` 行数 | **199295** |
| 493 个 `.ko` 的真实 UND 引用名并集 | **4754** |
| 真实引用名 ⊂ 旧基准 | 4157（87.4%） |
| **真实引用名 ∉ 旧基准（闸门盲区）** | **595** |
| **其中来自 `system_dlkm`** | **586**（该分区 1187 个引用名里漏 49.4%） |
| 旧基准里根本不是 `.ko` 引用的（**噪声**） | **195138（98.0%）** |

**盲区成因**：dump 命令**没有包含 `/system_dlkm/lib/modules/`**。

### 两个方向的危害
- **假阳性（噪声）**：任何"恰好作为字符串出现在某个 `.ko` 里"的新增导出名都会被判砖。
- **假阴性（盲区）**：新增导出若被某个 `system_dlkm` 模块真引用，闸门看不见 ⇒ 会误判 PASS ⇒ **可能刷进砖**。
  实例：`system_dlkm/gzvm.ko` 强引用 `__arm_smccc_hvc`（我们确实导出它），但该名不在旧基准里。

## 二、直接后果：**P28 那次 `prep_new_page` 判砖是【假阳性】**

### 更正前我们写的
> "闸门1 判砖：`mm/page_alloc.c` 撤 `static` + `EXPORT_SYMBOL_GPL(prep_new_page)`。
> 厂商 `oplus_bsp_uxmem_opt.ko` **弱引用**它 ⇒ 导出后弱引用翻真调用 ⇒ 活锁 → PMIC 看门狗复位。
> **闸门第 5 次救场。**"

### 实测真相
```
prep_new_page 在旧基准(strings) 里?  ✅ 在
prep_new_page 在真基准(ELF) 里?    ✗ 不在
真 ELF 解析 493 个 .ko: ★ 没有任何 .ko 有 prep_new_page 的 UND 引用
```
`oplus_bsp_uxmem_opt.ko` 里出现的 `prep_new_page` **是一个字符串**（不是符号引用）。

⇒ **没有模块真的引用它** ⇒ 导出它**不会**翻任何"弱引用真调用"。
⇒ 那次 FAIL 是**旧基准的 98% 噪声造成的假阳性**。

### 那次回退有没有造成损失
**没有实际损失**，但要说清：
- 我们撤掉的是"`static` 去掉 + `EXPORT_SYMBOL_GPL`"这两处
- **保留了** `+ page->private = 0;`（来自另一个补丁 `e7790ab16571` 的真修复）
- 回退后的状态 = opt5 基线/P27 的状态（**健康**）⇒ **安全，但少了一个无害的上游导出**

⇒ 结论更正为：**"闸门第 5 次救场"这个说法作废**；应记为
**"闸门基准噪声导致的假阳性，回退无害但非必要"**。

### 闸门"救场"次数需要重算
已确认的真救场（CRC 面 / 真·导出面）：
| # | 版本 | 拦下什么 | 依据 |
|---|---|---|---|
| 1 | opt15 | 166 补丁里 net/bpf 改导出头 CRC ⇒ **9 个模块拒载、WiFi/蓝牙全挂** | 闸门2（CRC 真值） |
| 2 | P15 | `struct rq` 布局 ⇒ 47 个模块 | 闸门2 |
| 3 | P18 | 命名空间配置碰 `task_struct`/`cred` ⇒ 493 个模块 | 闸门2 |
| 4 | `act_api.h` | `struct tcf_exts` ⇒ 2 个模块 | 闸门2 |
| ~~5~~ | ~~P28~~ | ~~`prep_new_page`~~ | ⛔ **假阳性，作废** |

⇒ **真救场 = 4 次，全部由闸门2（CRC 真值）拦下。闸门1 至今没有拦下过一次真砖。**

## 四、还没结的一条（`test_task_ux` 与砖机理）

子代理报告 `§发现3` 质疑我们一直引用的"**弱引用拿 NULL 走跳过分支**"机制：
> 29408 个引用里**只有 5 个弱引用**；当年判砖的 `test_task_ux` 是
> **GLOBAL 强引用 + 2 条真 `R_AARCH64_CALL26` 重定位**，
> 按装载器语义那 6 个模块**根本装不上**，而不是"拿弱引用 NULL"。

**设备侧决定性检验（已做）**：
```
oplus_binder_strategy ✅ / oplus_bsp_dynamic_readahead ✅ / oplus_bsp_hybridswap_zram ✅
oplus_bsp_uxmem_opt ✅ / oplus_bsp_zram_opt ✅ / oplus_locking_strategy ✅
Unknown symbol 行数 = 0        lsmod = 621
```
⇒ 那 6 个模块**全部正常加载**。而 `test_task_ux` **我们确实不导出、基线也不导出**，
但它在真厂商引用名里。

**这条的意义**：
- 若"强引用拿不到就装不上"成立 ⇒ 那 6 个模块必须能拿到 `test_task_ux`（否则装不上），
  但我们不导出它 ⇒ **矛盾**，说明这些模块对它的引用**不是必须解析的**
  （可能是 `SHN_UNDEF` 但绑定为 `WEAK`，或装载器对该符号宽容）
- **无论哪种解释，闸门的规则都仍然成立**：
  "**不要新导出厂商模块引用的符号**" —— 因为新导出会让原本拿不到的东西变成拿到，
  路径从"跳过"变成"真调用"，而厂商模块的实现针对的可能是另一套内核状态。
- ⇒ **闸门规则不变，只是基准要换**（本次已换）。

**留给后续**：若要彻底确认砖机理，需要在**可控环境**里做一次"A/B 加一个 EXPORT"实验
（例如拿一个真基准里被引用的符号，加 `EXPORT_SYMBOL` 后构建、过闸门、刷机看是否循环重启）。
**但这有刷砖风险，需机主明确同意，且必须有回退镜像在手。**

## 五、教训（写进坑清单）

**"基准数据本身可能是错的"** —— 我们此前一直在验证"补丁对不对"、"产物对不对"，
却**从来没验证过闸门的基准是怎么来的**。这次是子代理去读了 `.ko` 的二进制才发现的。

⇒ **凡是用到"外部给的集合/名单"做判定，先花 5 分钟确认它是怎么生成的。**
一句 `strings -a` 与一次真 ELF 解析之间，差了 98% 的噪声和 12.6% 的盲区。
