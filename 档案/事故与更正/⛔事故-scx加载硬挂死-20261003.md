# ⛔ scx 加载实测：硬挂死（无 pstore）—— sched_ext 在本树上【运行期不可用】

> 机主要求"弄出 scx"（Scene 下一版将支持 scx 调度）。实测结论：
> **内核侧框架完整，但运行期一加载就硬挂死整机** —— 原厂自己也没启用它，原因找到了。

---

## 一、本轮做成了什么（编译侧全通）

| 步骤 | 结果 |
|---|---|
| `libbpf.a` 交叉编译（arm64 静态） | ✅ 2,845,802 字节（`make -C tools/lib/bpf ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu- CC=aarch64-linux-gnu-gcc LD=aarch64-linux-gnu-ld BUILD_STATIC_ONLY=1 O=…`；`.so` 会因 ld.lld 的 version-script 失败，**静态库不受影响**） |

| 样例适配 | ✅ 4 处：本树 `task_struct.scx` 是**指针**（`struct sched_ext_entity *scx`），样例按内嵌写的 ⇒ `p->scx.` → `p->scx->` |
| **BPF 调度器本体** | ✅ **724,312 字节，含 `.struct_ops` 段**（`-mcpu=v3` 必需：BPF 后端默认不支持 32 位原子，`user_exit_info.h` 的 cmpxchg 需要 ISA v3） |
| kfunc 需求清单 | ✅ 调度器只需 3 个：`scx_bpf_dispatch` / `scx_bpf_dispatch_vtime` / `scx_bpf_switch_all` —— **本树 19 个 kfunc 全覆盖** |

**⇒ 编译侧 100% 就绪：调度器能编出来，需要的 kfunc 本树全有。**

## 二、★ 实机加载：硬挂死

`bpftool struct_ops register simple.bpf.o`（v7.7.0，root）：

```
寄存器命令发出后：shell 立即无响应 → 整机离线（adb/fastboot 均无）
~10 秒后设备自己回来（uptime 归零 = 重启）
sys.boot.reason = reboot     ro.boot.bootreason = reboot
pstore = 0 条               ← ★ 没有任何 panic 现场
真 oops = 0
异常重启计数不变：total_9_dump_0_pmic_9（未被计为 pmic 异常）
```

**判定：`scx_ops_enable()` 路径硬挂死。** 它持有 `cpus_read_lock()`（`ext.c:2838`），
一旦在里面死锁 ⇒ 整机冻结 ⇒ 无 oops、无 pstore、PMIC 看门狗复位恢复（~60-90 秒）。
这与"早期 sched_ext 的 enable 路径死锁"这一已知问题类别吻合。

⇒ **即使做"部分接管"也救不了** —— 挂死发生在 enable 路径（`ops.init()` 返回之前），
与全接管/部分接管的语义无关。

## 三、为什么会这样：厂商 backport 是【残缺的运行期】

编译在、运行挂，旁证一堆：

```
❌ scx_bpf_switch_all(bool into_scx) 被削成无参只能 true（部分接管没了）
❌ //slim_walt_enable(true)  (ext.c:2817) 被注释，slim_walt.c 源码已删
❌ 无 /sys/kernel/sched_ext（sysfs 运维接口整个没有）
❌ 无 scx_bpf_cpuperf_*（无法接调频）
❌ 无 bpf_iter_num（6.13 的 BPF 迭代器）
❌ 本树 dmesg 从未出现过 scx 启用消息 ⇒ 原厂自己一次都没启用过
```

⇒ **原厂把框架编译进来但从未启用、也没给出启用路径 —— 最合理的解释就是：
他们知道这条路径跑不通（或没调通），所以没开。** 其他一加机型的 stock 内核启用了 scx，
说明完整可用的版本存在，但**没有进到这台真我的 drop 里**。

## 四、⚠️ 给 Scene 用户的结论

**Scene 下一版的 scx 调度在这台真我（本树内核）上【不可用】**：
- 框架能加载入口存在，但一加载就硬挂死整机（无现场、靠看门狗复位恢复）
- 要修好需要：ramdump/串口 环境 + 把上游 6.12 的 sched_ext 完整重做一遍 —— **超出常规刷机内核的范围**

**本机实际在跑的"风驰"内核组件（全部正常，我们从未动过）**：
```
mpam_game（按 PID 分优先级组：high/normal/low_prio_pids）—— 已加载
oplus_bsp_frame_boost (refcnt=5) / oplus_bsp_sched_assist (refcnt=14)
oplus_network_game_first / task_sched / qos_sched / schedinfo / sched_penalty
sched_walt + cpufreq_uag（当前 governor 就是 uag）
```

## 五、⚠️ 安全提醒（写给下一次）

**不要再在这台设备上 `struct_ops register` 任何 scx 调度器** —— 实测 = 硬挂死整机
（无 panic 现场，只能等看门狗复位）。除非先解决：
1. ramdump/串口 调试环境（挂死时能拿到现场）
2. 上游 6.12 sched_ext 完整 backport（enable 路径 + slim_walt 或替代利用率反馈 + cpuperf）

# ★ 后续实测：opt43 部分模式【同样硬挂死】⇒ 批量切换假设被证伪

opt43 注释掉了 `ext.c:2840` 的 `scx_switch_all_req = true`，并重建了**不含
`scx_bpf_switch_all()` 调用**的 BPF 调度器（723,952 字节；未定义 kfunc 只剩
`scx_bpf_dispatch` / `scx_bpf_dispatch_vtime`，本树全有；`scx_bpf_switch_all` 引用数 0）。

结果：**加载依然硬挂死**（adb 断连 → 8 秒后回来，uptime 归零，
`sys.boot.reason`=`ro.boot.bootreason`=reboot，pstore 0 条，异常计数仍 `total_9_dump_0_pmic_9`，
`lsmod` 621 / wlan0 UP / 真 oops 0，WARNING 仍为开机基线 10）。

⇒ **"挂死在批量切任务"的假设被证伪**。挂点在 `scx_ops_enable()` 核心：
对抗性审核指向 `ops.init` 的 BPF 调用（:2842）或静态位（`scx_has_op[]` / `__scx_switched_all`）
与 CPU 热插拔的交互——这两处都在 `cpus_read_lock()` 持有期间。

**要定位必须 ramdump/串口拿到挂死现场**（当前 pstore 留不下任何东西）。
**本机不具备 ⇒ scx 结案不做。** 详细已并入 `skills/../SKILL.md` 的"已结案方向"。
