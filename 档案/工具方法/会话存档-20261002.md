## 二、⭐ 今天最重要的产出：两道 CRC 闸门

### 2.1 事故：opt15 刷上去 WiFi/蓝牙全挂

9 个模块报 `disagrees about version of symbol`：

```
mac80211 / qca_cld3_kiwi_v2 / qca_cld3_peach / qca_cld3_qca6750 / rmnet_shs  → __skb_get_hash
oplus_connectivity_sla                                                        → nf_ct_delete
oplus_network_data_module                                          → tcf_action_exec / tcf_exts_*
```

**根因**：`CONFIG_MODVERSIONS=y` 的 `check_version()` 拿厂商 `.ko` 里 `__versions` 记的 CRC
跟内核 `__kcrctab` 比，不等就拒载。而 **genksyms 的 CRC 只由"声明"算出** ——
改函数体不动 CRC，**改头文件就动**。这批 ACK 全是 net/bpf/netfilter，正好改了
`include/net/act_api.h`、`include/net/xdp.h`、`include/net/netfilter/nf_conntrack_core.h` 等。

**原闸门为什么漏**：`gate_new_exports.py` 只比**导出集合**（谁在/谁不在）。
**符号还在、CRC 变了，它完全看不见。** opt5→opt14 没踩到，是因为那些改动集中在
`mm`/`f2fs`/`sched`/`block`，没碰网络栈的头。

### 2.2 新闸门（**以后每次刷机前必跑两道**）

| 工具 | 判据 | 备注 |
|---|---|---|
| `tools/gate_new_exports.py` | 导出集合：新增/消失 ∩ 厂商引用名 | 原有 |
| **`tools/gate_vko_crc.py`** | **真值**：解析 493 个厂商 `.ko` 的 `__versions`，逐符号比 CRC | **新增，推荐** |
| `tools/gate_crc_drift.py` | 本地预警：候选 CRC vs 能开机基准 ∩ `vko_syms.txt` | 新增，依赖的厂商名表不全，只当预警 |

`__versions` 格式：每 64 字节 = `u32 crc` + 4 字节填充 + `char name[56]`。

**厂商 `.ko` 怎么取**（`adb pull` 会被拒，要先 root 拷）：
```bash
su -c 'mkdir -p /data/local/tmp/vko && cp /vendor_dlkm/lib/modules/*.ko /data/local/tmp/vko/ && chmod 644 /data/local/tmp/vko/*.ko'
adb pull /data/local/tmp/vko ...\vendor-ko\vendor_dlkm
```

### 2.3 今天它救了我们**两次**

| 次数 | 候选 | 闸门结论 |
|---|---|---|
| 1 | opt15（166 条） | 刷之前**没跑真值闸门** ⇒ 翻车（闸门当时还不存在） |
| 2 | **perf3（关调试开关）** | **闸门2 报 493/493 模块全挂**，1995 个符号漂移 ⇒ **拦下，没刷** |

perf3 的漂移符号是 `__pskb_pull_tail`、`__dev_queue_xmit`、`alloc_netdev_mqs`、
`register_netdevice`… **连 `module_layout` 都漂了** —— 这是 `struct task_struct`
被改后沿指针类型图**级联**出去的（genksyms 会顺着指针追进结构体：
`sk_buff` → `sock` → … → `task_struct`）。凶手是 `CONFIG_SCHEDSTATS=n`；
另外 `CONFIG_SOFTLOCKUP_DETECTOR=n` 直接删掉了厂商引用的 `touch_softlockup_watchdog`
（闸门1 命中）。

> **教训：任何改动 `struct task_struct` / `struct sk_buff` / `struct net_device` 这类
> "中枢结构体"的 config，都会引发全表 CRC 漂移。** 判断方法只有一个：跑真值闸门。

| | opt15c | ThinLTO |
|---|---|---|
| 构建 | — | rc=0，**4.5 分钟** |

## 四、社区三份清单的结论

详见 `档案/基线与对照/社区验证配置-对照与取舍-20261002.md`。

| 项目 | 结论 |
|---|---|
| [`ferstar/kernel_manifest`](https://github.com/ferstar/kernel_manifest)（**同机型 RMX3888**） | **无货**。`patches/` 是孤儿文件（`build_v.sh` 没引用），而内容我们树里早在跑：`lib/lz4/lz4armv8/lz4armv8.S` + `lz4accel.o` 都进了 `vmlinux.a`，LZ4 已是 **1.10.0** |
| [`walunt236/oppo_oplus_realme_sm8750`](https://github.com/walunt236/oppo_oplus_realme_sm8750) | 质量最高，拿了 10 项 config（perf2） |
| [`cctv18/oppo_oplus_realme_sm8750`](https://github.com/cctv18/oppo_oplus_realme_sm8750) | **我们的上游就是它的 sm8650 版** |

### ⛔ P3b（zram lz4kd 双重压缩）**划掉**

- 设备 zram **不是我们编的**，是 `system_dlkm` 里的**官方 GKI zram.ko**（`/sys/module/zram` 不存在）
- `lz4k`/`zstdn` 是 **OPPO 自己的模块**（`oplus_bsp_lz4k` / `oplus_bsp_zstdn`）注册的
- 我们树里的 zram **没有 `ZRAM_MULTI_COMP`**，要做"双重压缩"得打补丁 —— 打了也到不了设备

### ⛔ P3a（ADIOS I/O 调度器）**做不了**

[`firelzrd/adios`](https://github.com/firelzrd/adios) 只有 **6.12.44 / 6.18.3 / 7.3-rc1** 三个补丁，
**没有 6.1**。从 6.12 往 6.1 移植 blk-mq 调度器（`elevator_mq_ops`、`blk_mq_sched_*` 都变过）
是大工程，硬塞只会做出开不了机的内核。

### ⚠️ P3c 净收益只剩 `CONFIG_SCHEDSTATS` —— 而它正是 perf3 翻车的凶手

**所以 P3c 也作废。**

## 五、两个结论

### 5.1 内核版本号保持 `6.1.141`，不要改成 `6.1.1xx`

- **`6.1.141` 是事实**（基线就是厂商的 6.1.141 GKI），**`6.1.188` 是主张**，我们没有资格主张它
- ACK 全量语料 **29,971 条**（单月 400~1500 条），我们两批真正进镜像的合计 **约 180 条**，
  且只覆盖 mm/f2fs/erofs/sched/block + net/bpf/ext4/scsi/crypto，**驱动层大面积空白**
- 报 6.1.188 之后，"这个 CVE 修了吗"这类问题**永远答不了**
- **要标"补了多少"，用横幅**：`init/Makefile:33` 的 `build-version = $(or $(KBUILD_BUILD_VERSION), $(build-version-auto))`，
  传 `KBUILD_BUILD_VERSION="<N>-ack138"` ⇒ `uname -v` 变成 `#45-ack138-p2`，**完全不动 `uname -r`**
  （⚠️ Makefile 自己会加 `$(pound)`，**不要**在值里再带 `#`）

### 5.2 ⭐⭐ 为什么内核改动全都"体感用不出来"

`lsmod` 里有一整套 **OPPO 私有的调度/内存优化栈**（全是 vendor 模块，在只读分区上）：

```
oplus_bsp_sched_assist      1048576  ← 1 MB，挂了 14 个模块，含 sched_walt
oplus_bsp_hybridswap_zram    237568  ← 混合交换
oplus_bsp_schedinfo          229376
oplus_bsp_eas_opt  oplus_bsp_qos_sched  oplus_bsp_frame_boost
oplus_bsp_task_overload  oplus_bsp_binder_strategy
oplus_bsp_uxmem_opt  oplus_bsp_mm_osvelte
oplus_bsp_dynamic_readahead  oplus_bsp_file_read_record
oplus_bsp_zram_opt / zsmalloc / zstdn / zstdn_o / lz4k
oplus_bsp_fg_protect / oplus_exit_mm_optimize
```

**这台机器的"快不快"实际由这一层决定，而我们刷 `boot_a` 碰不到它们。**
（机主装的 `IMS_VAROS`「官方调度屏蔽」和 SCENE 那套，本质就是在从用户态盖这一层。）

**⇒ 性能线的真正结论：在只刷 `boot_a` 的前提下，内核侧没有可证的性能空间。**

## 六、明天可以做的（按性价比排序）

0. ⭐ **【机主已定：跟上游一起加】命名空间组 config** —— `USER_NS` / `PID_NS` / `IPC_NS` /
   `SYSVIPC` / `POSIX_MQUEUE` / `NTSYNC` / `DEVTMPFS`，我们当前**一项都没有**。
   来源：cctv18 的包（见 `他人内核包分析（文档已移入非本项目归档）`）。**零 CRC 风险**（独立 config，
   不动任何头文件）。做法与 P5 同：写进 `gki_defconfig` → 构建 → 双闸门 → 刷。

1. **把尺子做准**（唯一能改变"测不出"局面的东西）：配对 A/B + 每侧 20~30 轮 +
   Wilcoxon 符号秩检验 ⇒ 能分辨 **~0.5%**。现有判据是"三个 app 中位数都要改善 ≥9%"，
   而任何内核改动能给的都 ≤2%。
2. **测 `boot_a` 之外的分区**：既然性能在 vendor 模块层，那要动的是 `vendor_dlkm`
   （厂商 `.ko`）。**但那要重刷 `vendor_dlkm`，风险等级完全不同，必须单独评估。**
3. **把闸门写进交接包**：`kernel-kit/skills/gt5pro-kernel-handover/` 已更新，
   但 `C:\Users\USERNAME\Desktop\GT5Pro内核交接包\` 那份还是旧的 —— **下一班接手的人
   如果不知道这两道闸门，一定会再翻一次车。**
4. ACK 第三批（如果需要）：先把**驱动层**纳入收割范围，但**先跑真值闸门再谈**。
