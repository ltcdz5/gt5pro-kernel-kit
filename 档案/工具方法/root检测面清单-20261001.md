# root 检测面清单（2026-10-01 00:5x 实测取证，只列不改）

取证方式：电脑端 adb 单条 root shell，**全程只读**，未改机主任何 KSU/Zygisk 设置。
每一项给三样：**证据（当场读数）** → **谁能看到** → **对应修法在哪** → **怎么验收**。
本清单不含"我已隐藏好"这类结论——没有指定检测 app 当靶子，隐藏只能自证到"暴露面清单"这一层。

## 0. 先说结论

- 我这台机器的 root 暴露面**主要来自 KSU 本体 + Zygisk/LSPosed + Tricky Store + 一个动了全局钩子的第三方模块**，
  不是来自我加的 `lru_gen_on`（见 §7 的自证）。
- 因此"把这个模块的隐藏 root 做好"这件事，模块侧的可做项已经做完（零挂载/零属性/零注入/私有目录）；
  再往下的每一条都要机主自己在 KSU 设置里取舍，且**必须拿检测 app 实测才算数**。

## 1. `/system/bin/su` 存在

- 证据：`ls` 输出 `/system/bin/su`（其余三个经典路径 `/system/xbin/su`、`/sbin/su`、`/system/bin/.usr` 均 No such file）。
- 谁能看到：这条读数是在 **root 挂载命名空间内**取的。未被授权的应用是否看得见它，取决于 KSU 的
  **卸载强度 / 挂载隔离（Unmount Level）** 设置——这正是承重开关，本机现值我没有读（要读得进 KSU 设置或 `ksud` 配置，属你的授权范围）。
- 修法：KSU 管理器 → 卸载强度设"非 root 进程不可见"档；并核对**应用授权列表**里银行类 app 一律不给 su。
- 验收：用**未授权**的目标 app 跑一次 RootBeer / `access("/system/bin/su", F_OK)`，返回"不存在"才算过；我这边无法替你判过。

## 2. Zygisk + LSPosed 在装载

- 证据：`/data/adb/` 下有 `zygisksu`、`lspd`；`/data/adb/modules/` 下有 `zygisk_lsposed`、`zygisksu`。
- 谁能看到：zygote 注入会留下**进程内证据**（maps 里的注入段、`app_process` 相关 hook），对做了检测的 app 是最强信号之一；
  `/data/adb/lspd` 本身在 0700 的 `/data/adb` 里，普通 app 读不到目录，但 LSPosed 的 socket/属性面另有暴露途径。
- 修法：要么把 LSPosed 从需要检测的 app 里"排除"（LSPosed 自身可按应用禁用注入），要么停用 LSPosed。
- 验收：同上，必须有靶子。**注意这条与"留存/性能优化"无关，纯取舍。**

## 3. Tricky Store + `pif.json`（Play Integrity 通道）

- 证据：`/data/adb/tricky_store`、`/data/adb/pif.json`。
- 谁能看到：目标不是 app 的 root 检测，而是 **Play Integrity（MEETS_DEVICE / STRONG）** 的硬件证书链。
- 修法/验收：跑 `Key Attestation` 类 app 看证书链是否 `TRUSTED`；这条已经在你掌控中，我不碰。
- ⚠️ 顺带：`/proc/cmdline` 里有 `oplusboot.verifiedbootstate=orange` 与 `oplusboot.serialno=DEVICE_SERIAL`、
  `oplus.avbkeysha256=7590…` —— **这些是设备唯一标识与解锁状态，整串 cmdline 不要外发/贴群**。

## 4. 某第三方 GPU 模块替换了 KSU 的全局钩子

- 证据：`/data/adb/` 下存在两枚 `*.ORIG` 备份文件
  ⇒ 它的安装脚本把**全局** `/data/adb/post-fs-data.sh`、`/data/adb/service.sh` 改名备份后写了自己的版本。
- 谁能看到：`/data/adb` 本身 0700 root-only，app 直接读不到；但这是一个**脆弱点**——全局钩子只有一个，
  任何模块覆盖它，就会让别的模块的 boot 行为失效；且检测类工具若拿到过一次 root shell，会把这个当"被改过"的指纹。
- 修法：把该模块的行为移进它自己的模块目录（KSU 支持 per-module `post-fs-data.sh`/`service.sh`），别占全局路径。
- 验收：`ls /data/adb/` 不再有 `*.ORIG`，且各模块的 boot 行为互不影响。

### 更正（01:1x 重启取证后，我上面这条判断说重了）

重启后实测：`ls -l /data/adb/post-fs-data.sh /data/adb/service.sh` ⇒ **两个都不存在**；
而该模块自己的目录里已经有 `post-fs-data.sh` 与 `service.sh`，**与本地留档的清理版逐字节相同**。
⇒ **该模块早就在用 KSU 自己的 per-module 钩子了**（09-29 那次就已改完，见提交 `d8859b8`），`/data/adb` 根下那两枚 `*.ORIG` 只是当时的删前副本，不是"全局钩子正被占用"。
我凭两个 `.ORIG` 文件名就下了"占用全局路径"的结论，是拿残留当现状——已纠正。
处置：两枚 `.ORIG`（与本地留档的删前副本 md5 相同）已**移入**该模块目录下的 `archive/`（`chmod 700`），
没有删除任何文件；要放回原处就是 `mv` 反方向一条命令。

## 5. SELinux 与授权面（这两条是好消息）

- 证据：`getenforce` = **Enforcing**（没有为了让模块跑而放宽）。
- 证据：`getprop | grep -iE 'ksu|magisk|apatch|root'` **没有任何 ksu/magisk 系统属性**（只匹配到 `dev.mnt.*root` 这类原厂挂载噪声）。
- 结论：这两条不需要修。

## 6. `/proc/cmdline` 干净度

- 证据：整串里**没有** `ksu`、`kp`、`apatch`、`superkey`、`androidboot.delta` 之类的第三方内核参数
  （本机是 LKM root，改的是 `init_boot`，不动 cmdline）⇒ 这条常见检测点本机是过的。
- 但 cmdline 含厂商私有参数与上面 §3 的唯一标识，仍然不要外发。

## 7. 本模块 `lru_gen_on` 的自证（v3）

| 项 | 现值 | 判定 |
|---|---|---|
| bind mount / 改分区 | 无（模块只含 `module.prop` + 3 个 hook + `uninstall.sh`） | 零挂载 ⇒ `cat /proc/mounts` 里不会出现本模块的任何条目 |
| `resetprop` 属性改动 | 无 | 见 §5，`getprop` 无新增键 |
| zygote 注入 | 无 | 不是 Zygisk 模块，目录里没有 `zygisk/` |
| SELinux 改动 | 无（`getenforce` 仍 Enforcing） | 不放宽 |
| 落盘文件 | `/data/adb/lru_gen_on/`（`chmod 700`）、`state.log`（`chmod 600`），全在 root-only 的 `/data/adb` 内 | app 不可读 |
| 唯一动作 | `echo Y > /sys/kernel/mm/lru_gen/enabled`、`echo 1000 > …/min_ttl_ms` | 不产生文件系统痕迹 |
| 文案 | `module.prop` 的 name/description 已中性化，不含 su/magisk/ksu/root 字样 | 仅在 app 已拿到 root 时才有意义（`/data/adb/modules` 本就是 root-only） |

⇒ 诚实表述：**这个模块本身不构成可被 app 观测的 root 泄露面**；上面 §1/§2/§4 才是。

## 9. 靶子自己送上门了：MemoryDetector 报 15 条挂载项，归属与结案（01:1x–01:2x）

机主跑了 `MemoryDetector v2.1.0`（未授 su），它报 `Found 15 item(s) modified or added by Magisk/KernelSU` ＋ 一条 `Abnormal size of dynamic partitions`。逐条对到模块目录：

| 报出的路径 | 出自哪个模块（模块目录里的实体文件） |
|---|---|
| `/system_ext/etc/oiface/oiface.config` | **IMS_VAROS** `MODS/B_ColorOS_OiFace/File/oiface.config` |
| `/vendor/etc/im/QAPE.xml`、`QGPE.xml`、`QGPEActionMap.xml` | **IMS_VAROS** `MODS/X_Qualcomm_Misc/CustomConf/` |
| `/vendor/etc/pwr/PowerFeatureConfig.xml` | **IMS_VAROS** 同上 |
| `/odm/etc/orms/orms_core_config.xml`、`/odm/etc/uah/uahconfig.pb` | **IMS_VAROS** `MODS/A_ColorOS_OrmsUrcc/File/` |
| `/my_product/etc/refresh_rate_config.xml`、`sys_resolution_switch_config.xml`（各重复一次） | **extreme_gt** `my_product/etc/` |
| `/my_product/etc/oplus_vrr_config.json` | **GT5PROLTPO3P0Enchance** `my_product/etc/` |
| `/my_stock/etc/ThermalServiceConfig/sys_thermal_config.xml` | **extreme_gt** `my_stock/etc/ThermalServiceConfig/` |
| `/vendor/etc/pwr/GamePowerOptFeature.xml`、`PSMPowerOptFeature.xml` | **归不到任何模块**：全模块目录 `find` 不到同名文件 ⇒ 要么检测器基线固件版本与本机不符（误报），要么改动不来自模块。**不给它编归属。** |

机制取证（**非 root** 的 shell，未授 su）：

- `grep -c dm-76 /proc/mounts` = **28 行** ⇒ 这 15 条全是 **hybrid_mount 建的 device-mapper 单文件 bind mount**（`/dev/block/dm-76`，f2fs），
  且**对普通进程全局可见**。所以"泄露"的不是某个模块的文案或目录名，而是**挂载本身**；`10=12`、`11=13` 重复＝同一路径挂了不止一层。
- ⚠️ 同一条 `find` 也证明：某第三方 GPU 模块（挂 GPU 用户态驱动）、`scene_swap_controller`（osense/内存策略 xml、`perfconfigstore.xml`）、`scene_systemless`、`PUIThemeCustomized` **同样是挂载型**——检测器没列它们只说明它那张路径表没覆盖，不等于它们没挂。
- `Abnormal size of dynamic partitions` 与模块无关（本机虚拟 A/B 的动态分区几何），删模块也不会消掉。

机主的处置与结果：他按 ZygiskNext 作者的建议**关掉了内核 unmount、改用 ZygiskNext 排除列表的「仅还原挂载」＋「使用匿名内存」**；
补一句"在 ksu 里面设置一下就好了" ⇒ **把目标 app 纳入逐 app 还原挂载后，该项报警消除**。
⇒ 结论形状（可复用）：**挂载可见性靠"逐 app 还原挂载"解决，不靠改模块文件**；代价是它依赖名单——不在名单里的 app 依旧全局可见。

## 10. 逐 app 还原挂载**覆盖不到**的一类：属性（实测）

同样以**非 root** shell 读：

| 键 | 读数 | 谁写的 |
|---|---|---|
| `debug.hwui.renderer` | `skiavk` | 某第三方模块的 resetprop |
| `ro.boot.vbmeta.device_state` | `locked` | 某第三方模块（伪装未解锁） |
| `ro.boot.flash.locked` | `1` | 某第三方模块 |

`getprop` 任何 app 都能读，**unmount / 还原挂载 / 匿名内存都不覆盖属性面**；要藏只能按 app 还原 prop（ZygiskNext 不做这件事），或者接受它。
