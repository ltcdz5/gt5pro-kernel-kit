# ColorOS 内置完整性看门狗（`oplus_kohashprocess`）—— 本机实测（2026-10-03）

> 起因：机主看到一条抖音说"ColorOS 已内置腾讯反作弊系统…内核时代估计要结束了"，问是不是真的。
> **本文是我方在本机（真我 GT5 Pro / 现役 version1-opt37）的第一手实测结论**，
> 不采信那条帖子的转述。

---

## 一、结论先说

**这条帖子在"东西存在"这一点上是真的，而且实物就在这台机器上。**
但它把名字说错了一点，机制描述**部分对、部分无从证实**，
而"内核时代要结束了"是**它的推论，不是事实** —— 按我们的实测，**它主要盯的不是"换过内核"**。

---

## 二、本机实测到的实物（可复现）

```
✅ /system_ext/bin/oplus_kohashprocess          44,296 B, root:shell 0755
   SELinux: u:object_r:oplus_kohashprocess_exec:s0
   （帖子写成 "oplus_kohashpro"，实际是 kohashprocess）

✅ init 服务：oplus_kohash_sys
   定义文件 /system_ext/etc/init/oplus_kohashprocess.rc：
     service oplus_kohash_sys /system/system_ext/bin/oplus_kohashprocess
         class late_start
         user system
         group root system
         disabled
         oneshot                       ← ★ 一次性，不是常驻循环
     on property:oplus.device.firstboot=* && property:sys.boot_completed=1 \
        && property:vendor.all.modules.ready=1
         mkdir /data/oplus/persist_hash 0770 system system
         start oplus_kohash_sys

✅ 它本次开机确实跑过：ro.boottime.oplus_kohash_sys = 29595951946 ns（29.6 秒）
   现在状态：init.svc.oplus_kohash_sys = [stopped]（oneshot 跑完就退）

✅ 二进制里的字符串证实帖子的关键路径：
     /proc/inte_status
     /proc/inte_ko
     EVP_sha256 / calculate_sha256 / "Error processing hash"
     /data/oplus/persist_hash/          ← 持久化哈希目录
     KOHASHPROCESS_SYS

✅ /data/oplus/persist_hash 目录存在（0770 system:system），但**当前为空**（0 文件）
```

**帖子说的 `kretprobe` / `load_module` 在用户态二进制里搜不到** —— 那两个是**内核侧**手段。
而内核侧我们查了：

```
✗ /proc/inte_ko / /proc/inte_status / /proc/inte_sysctl  —— 现在都不存在
✗ /proc/kallsyms 里 inte_ko / inte_sysctl —— 0 命中
✗ 493 个厂商 .ko 里 grep 'inte_ko|inte_sysctl|inte_status|kohash|load_module' —— 0 命中
✗ 我们内核源码树里 grep 'inte_ko|kohash' —— 0 命中
```

⇒ **提供那两个 `/proc` 节点的内核侧组件，既不在 `boot_a`、也不在这两个 dlkm 分区**。
（可能在别的只读分区、或按需挂载、或只在特定条件下加载。）

## 三、它到底在防什么（按我方证据推断，区分"实锤"与"存疑"）

| 帖子说法 | 我方判定 |
|---|---|
| 存在一个 OPPO 完整性看门狗（用户态 `oplus_kohashprocess` + init 服务） | ✅ **实锤**（见上） |
| 用 SHA256 做哈希比对 | ✅ **实锤**（`EVP_sha256`/`calculate_sha256`） |
| 持久化哈希存 `/data/oplus/persist_hash/` | ✅ **实锤**（目录存在） |
| 有 `/proc/inte_ko` 与 `/proc/inte_status` | ✅ **实锤**（二进制字符串里有；节点本身按需出现） |
| 有 `/proc/inte_sysctl` | ⚠️ **存疑**（二进制里没搜到这个字符串） |
| "**每小时**"跑一次 syscall 表 SHA256 快照 | ❓ **无从证实**（init 定义是 `oneshot`；若循环在二进制内部则看不到。且 dmesg 里**精确命中 0**，没有周期活动痕迹） |
| "kretprobe 挂 `load_module`，算哈希、比对厂商合法名单，未知/被改模块就记名单、`/proc` 上报" | ❓ **机制合理但未证实**（用户态无此串；内核侧组件未在本机找到） |
| "内核时代估计要结束了" | ❌ **这是推论，不是事实**。见下 |

## 四、关键问题：**它会不会盯上我们的自编内核？**

**按机制推导 + 本机证据，我们大概率不在它的靶心上：**

1. **它的靶子是"syscall 表被改"和"未知/被改的神码模块"**
   —— 这正是 **root 方案（改 syscall 表）与自编译 `.ko`** 的形状。
2. **我们的自编内核**是**用厂商自己的 GKI 源码树**构建的，
   **不改 syscall 表**、**不改任何厂商 `.ko`**、**内核导出面与 CRC 与厂商一致**
   （双闸门每次都验：闸门2 恒为 `= 1`，即只有基线就不符的 `bluetooth.ko`）。
   ⇒ **它按"改没改"来判的话，我们与厂商件无法区分。**
3. **反而更可能被注意到的是 KernelSU**（本机装在 `init_boot`，是"未知内核模块 + 钩子"的典型形状）——
   帖子的机制恰好对得上这一类。⚠️ 这条是**风险提示**，不是已证事实。

---

## 五、留档结论

- ✅ **东西是真的**：`/system_ext/bin/oplus_kohashprocess` + init 服务 `oplus_kohash_sys` 都在这台机器上
- ⚠️ **帖子把名字和部分细节说错了**（`kohashpro`→`kohashprocess`；`inte_sysctl` 未证实；"每小时"未证实）
- ❌ **"内核时代要结束了"是推论**；按我方证据，**"换过 boot_a"本身不是它判定的依据**
- 📌 **待办**：若要确证机制，需要在**它跑的时候**抓 `/proc/inte_ko` 的内容
  （`ro.boottime.oplus_kohash_sys` 给出的窗口是开机后约 29.6 秒；
  或把 `oplus_kohash_sys` 手动 start 一次并立刻 dump —— **但这会留下痕迹，需机主同意再动**）
