## 一、这是什么、我们做了什么、别人做了什么

### LSE 是什么
**LSE = LunarKernel Scheduling Extention**（作者 **Cloud_Yun**，声明许可 **GPL v2**）。
它是社区对 OPPO「风驰游戏内核」的**最小化复刻**：从厂商的 `hmbird_gki` 里拆出
**Slim-WALT 负载跟踪 + `update_task_ravg` 最小回调 + 调频器 + sched cluster 拓扑**，
做成一个**外挂 `.ko` 模块**（不改内核树、不用 sched_ext/BPF）。
注册的调速器名为 **`lunar_ext_gov`**。

### 我们（本项目）做了什么

| 成分 | 来源 | 性质 |
|---|---|---|
| `lunar_bsp_ext_sched.ko`（1,496,664 字节） | **LunarKernel 项目 / Cloud_Yun**，GPL v2 | **直接再分发他人编译产物** |
| 管理模块外壳（`service.sh` / `action.sh` / `uninstall.sh` / `delay.conf` / `README.md`） | **本项目原创** | 原创 |
| 部署配方（原子替换 + `chmod 555` + 杀 Scene daemon 使其重读配置） | **借鉴「Turbo 调度」模块**（作者 Turbo） | 借鉴思路 |
| Scene `profile.json` 的 `@governor` 改为 `lunar_ext_gov` 优先 | 本项目修改 | 原创改动 |

**⇒ 我们没有编写任何一行 LSE 代码，也没有它的源码。**
我们所做的是：**装载/调度/保持它生效**，以及**搞清楚它的边界条件**。

### ⚠️ 一个关键事实：这个 `.ko` 是「为你这台设备专门编的」

```
modinfo vermagic: 6.1.141-android14-11-o-ltcdz5-opt10 SMP preempt mod_unload modversions aarch64
                                    ^^^^^^^^^^^^^^^^^^^^ 本项目自编版本串
```
⇒ 它不是上游通用构建，而是**针对本机内核树编译的定制产物**。这意味着：
- 它只在你当前这棵树（以及 CRC 兼容的版本）上可用
- **上游源码与这个二进制之间是否存在差异，无法证实**

## 二、发布合规（发布前**必须**处理）

### GPL v2 的义务
再分发 GPL v2 的**二进制**，必须满足（摘要）：
1. **显著标注**版权人与许可
2. **提供对应源码**（或书面的源码获取方式）
3. 不得附加额外限制

### 本项目当前的合规状态

| 项 | 状态 |
|---|---|
| 标注作者/许可 | ✅ 已在模块 `README.md`、本文件标注（Cloud_Yun / GPL v2） |
| **提供源码** | ⚠️ **我们手上没有源码** ⇒ 只能给出上游仓库链接：`github.com/LunarKernel-Dev/lunarkernel_sched_extention` |
| 源码与二进制一致性 | ❌ **无法证实**（我们的二进制是为本机树编译的） |

### 🔴 一个必须知情的风险

社区调研显示：**LSE 本身是从 OPPO 的 `hmbird_gki` 拆改而来**。
如果其中部分实现源自厂商**闭源**代码，则**再分发的合规风险会转嫁到再分发者（本项目/发布者）身上**。
这一点我们无法核实，**必须如实告知**。

### ✅ 建议的合规做法（三选一，按干净程度排序）

1. **最干净：自己从上游源码重编 `.ko`**
   - 需要：LSE 上游源码 + 本机内核头文件 + 交叉编译环境
   - 收益：源码可提供、可验证、不依赖他人二进制
   - 成本：一次中等工作量
2. **可接受：只发布我们的管理外壳**（原创，正常开源），
   把 `.ko` 作为**可选、单独下载**，并在显著位置标注来源/许可/源码链接/风险
3. **不推荐：把整个包当作自己的作品发布** —— 会同时踩「冒充原创」与「GPL 不合规」

## 三、实现缺陷清单（均基于实测或源码级证据）

### 🔴 严重（会炸机 / 不可恢复）

| # | 缺陷 | 后果 | 证据 |
|---|---|---|---|
| 1 | **没有 `module_exit`** | `rmmod` **永远失败**（`-EBUSY`），**只能重启卸载** | `llvm-nm` 无 `cleanup_module`；实测 `lsmod` 显示 `[permanent]` |
| 2 | **开机早期加载 → 卡死循环** | 开机卡在锁屏界面 → 看门狗重启 → 循环；需 ADB 删模块救援 | **本项目实测**（`service.d` 立即加载一次即触发） |
| 3 | **`sched_ravg_window_frame_per_sec` 写 0 → 除零** | handler 无 min/max 保护 ⇒ 窗口变 0 ⇒ `div64_u64(delta, 0)` ⇒ **内核崩** | 源码级（handler 用不带边界的 `proc_dointvec`） |
| 4 | **`LSE_DEBUG_PANIC(8)` 是编译期常量** | 内部一致性检查失败 ⇒ **直接 panic** | 二进制 `.data` 常量 |

### 🟡 中等（行为不自洽 / 易冲突）

| # | 缺陷 | 说明 |
|---|---|---|
| 5 | **默认值 ≠ 生效值** | `frame_per_sec` 默认 `120`（应 ≈8.33ms），但实际窗口是编译期常量 **8ms**（≈125fps）；因为换算函数**只在 sysctl 写入时调用**，开机初始化不调用 |
| 6 | **写相同值是 no-op** | `if (val == frame_per_sec) goto unlock;` ⇒ 想把 120「重设」成 120 不生效，必须**先写别的值再写回** |
| 7 | **共享 `task_struct.android_vendor_data1[63]`** | 与厂商 `oplus_bsp_sched_assist` 同一槽位 ⇒ 存在争用/冲突风险 |
| 8 | **没有「governor 被选中才启用」的门** | 模块加载即注册**调度热路径钩子**（`android_rvh_schedule` 每次切换、`tick_entry` 每 tick） ⇒ 未选 `lunar_ext_gov` 时**开销照付、收益为零** |
| 9 | **没有自我保持机制** | 被 Scene 的 daemon 或厂商 HAL 改回 `uag` 后不会自己抢回（需外部守护/模块） |

### 🟢 轻微

- **与内核版本强绑定**：依赖厂商 vendor hook 与内部结构偏移，厂商一改即失效
- 无 ABI 保障；本机这个 `.ko` 是为 `-opt10` 编译的
- 上游**无官方调优档位、无机型支持列表**；6.1 + SM8650 上跑通**我们可能是首例**

## 四、性能与功耗：实测到的 vs 理论推断

### 已实测（本机，opt44 内核）

| 项 | 实测 |
|---|---|
| 最低频率被拉低 | p0 `1248000→556800`、p2 `1286400→614400`、p5 `1286400→499200`、p7 `1248000→672000` |
| 空载频率 | 可降至 **0.50 ~ 0.67 GHz**（原厂最低 1.25 GHz） |
| **满载升频** | p0 2.27GHz、p2 **3.07GHz**、p5 2.96GHz、p7 2.94GHz ⇒ **升频正常，未压满载性能** |
| 负载温度 | 65 ~ 78 °C（温和） |
| 链路稳定性 | 开机自动加载 → 自动生效 → **切应用不回退**；oops 0 |
| 切换开销（解析估算） | 空载 ≈ **单核 0.08%**；切换风暴 ≈ **单核 3%** |

### 理论推断

| 维度 | 推断 | 置信度 |
|---|---|---|
| **功耗** | 空载频率从 1.25GHz 降到 0.5GHz，动态功耗 ∝ f·V² ⇒ **倾向省电，幅度可观** | 中 |
| **功耗风险** | 若它在**中高负载**下比 `uag` 更积极升频，**可能反而更费电** | 未验证 |
| **性能（满载）** | 不受影响（实测升频到位） | 高 |
| **性能（轻载）** | ⚠️ 最低频率被拉低 **2.5 倍** ⇒ **滑动/点按/开 App 的响应可能变钝** | 中（需体感验证） |
| **游戏** | 窗口可与帧率对齐 ⇒ 理论上帧率更稳、卡顿更少 | 低（未实测） |

### ❌ 我们**没能**测出来的东西（诚实声明）

- **绝对功耗数字**：手机插 USB 在充电，且背景负载噪声大（loadavg 10+）
- **三次开销测量全部失败**：
  1. `ctxbench`（16 线程满载）→ 温度顶到 82°C，**热降频淹没信号**
  2. `pipebench`（低发热管道乒乓）→ 温度控制成功，但**噪声仍有 ±50%**
  3. 频率驻留 A/B → 发现方法学陷阱（切回 `uag` 时 `scaling_min_freq` 未恢复），修正后未能完成
- **结论**：**"LSE 到底省不省电、轻载会不会变钝"，目前只有理论推断，没有可信实测。**

## 五、⚠️ 风险告知（给使用者，务必阅读）

| 风险 | 说明 | 应对 |
|---|---|---|
| **开机卡死循环** | 若在**开机早期**加载该模块 ⇒ 卡锁屏 + 看门狗重启循环 | 本模块**强制延时 120 秒**（`boot_completed` 之后）；**绝不要**直接放进 `post-fs-data` / 早期脚本 |
| **无法卸载** | 模块 `[permanent]`，`rmmod` 必失败 | **卸载只能重启**；回退第一步永远是**先切回 `uag`**（`action.sh`） |
| **写 0 崩内核** | 往 `sched_ravg_window_frame_per_sec` 写 `0` 或负数 | **永远不要写 0**；要改窗口请写 60/90/120/240 之类正数 |
| **可能 panic** | 内部一致性检查失败会直接 panic（编译期常量） | 重启即恢复；开机默认 `uag`，**不会 bootloop** |
| **轻载可能变钝** | 最低频率被拉低到 0.5GHz | 观察体感；若不满意用 `action.sh` 切回 `uag` |
| **与厂商模块槽位冲突** | 共享 `android_vendor_data1[63]` | 若出现异常（卡顿/异常重启），先停用本模块 |
| **内核绑定** | 换内核/升级后 `.ko` 可能装不上或行为异常 | 换内核后**先别加载**，重新验证 CRC（113 个导入符号） |
| **合规风险** | 上游可能源自厂商代码，且我们无源码 | 见第二节；发布前务必处理 |

## 六、安全使用清单

**✅ Do**
- 让模块**自动延时加载**（默认 120 秒），不要手动提前
- 调参只写**正数**（fps 60/90/120/240、`target_loads` 85~95）
- 出问题**先切 `uag`**（`action.sh` 或管理器「操作」），再重启
- 换内核后重新验证 CRC 再启用

**❌ Don't**
- ❌ 不要放进 `post-fs-data.sh` 或任何早期启动脚本
- ❌ 不要写 `0` 到 `frame_per_sec`
- ❌ 不要试图 `rmmod`（无意义，只会报错）
- ❌ 不要把它当作"官方风驰"或"必备优化"来宣传
- ❌ 不要在未标注来源/许可的情况下二次分发 `.ko`

## 七、卸载与还原（都会自动做完）

```
管理器里卸载本模块 → uninstall.sh 会：
  ① 调速器还给厂商默认（写回 uag）
  ② 还原 Scene 的 profile.json（内容 9496 字节原始备份 + 权限 600 + 属主 u0_a373）
  ③ 重启 Scene 使其重读原配置
  ⇒ 重启后 LSE 内核模块随重启消失，系统回到接近原厂状态
```

备份位置：模块内 `scene_profile.orig.json`、设备上 `/data/local/tmp/scene_backup/`
