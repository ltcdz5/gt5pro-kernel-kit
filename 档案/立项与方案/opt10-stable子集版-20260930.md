# opt10 —— stable 6.1.142..145 能自洽落地的子集（2026-09-30）

## 一、这版是什么

- 基线：opt9（提交 `495c039ac`，父 `206914f9c`）
- 内容：Linux 6.1.142→6.1.145 四个正式版里，**不需要任何头文件/汇编/设备树配合就能编过并链接通过**的 10 个 `.c` 修复
- 横幅：`6.1.141-android14-11-o-ltcdz5-opt10`（`SUBLEVEL` 故意保持 141：只进了 10 个文件，写 145 是谎报）
- 镜像：`images/boot-opt10-repacked.img` md5 `85bb72dff6352dd60f804abe068c3c83`
- Image md5 `bdd5de8202c0f25fd6754b453d4e...`

## 二、"逐文件挑"这条路是怎么死的

142..145 四版共约 1.39 万个"版本×文件"条目，相关目录 3,480/版。整文件 `git apply --check` 能过的只有 147 条（133 个唯一文件，+890/−447），落地率约 1%；其余 13,539 条上下文冲突（Oplus 的 09-14 同步 `ebdd1643c` 早把这些位置改过一遍）。

拿这 133 个文件直接编，第一轮 `make -k` 出 **141 个 error**，性质全是一类：**`.c` 落地了、它依赖的头没落地**。

```
kernel/cred.c            atomic_long_t 传给 atomic_t *(refcount 语义变了)
kernel/locking/rtmutex.c struct rt_mutex_waiter 里没有 prio/tree_entry/deadline
kernel/posix-timers.c    signal_struct 里没有 posix_timer_id
net/core/dev_ioctl.c     struct sockaddr 里没有 sa_data_min
fs/iomap/iter.c          IOMAP_F_STALE 未定义
kernel/psi.c             psi_trigger_create 原型冲突
```

⇒ 分叉树上"文件能干净套上"绝不等于"语义完整"。kernel.org 的 `patch-6.1.x.xz` 是**压平的合并 diff，没有提交边界**（实测 `grep -c "^From [0-9a-f]{40}" = 0`），所以"按上游提交原子落地"在这个数据源上做不到。

收敛规则（这次用的）：第 0 轮退回全部 `.h/.tbl`、`include/**`、`scripts/**`、`.S`、`.dts/.dtsi`、`Kconfig` 改动 → 只剩纯 `.c` → 反复"编译→按报错 TU 退回"到 0 错。步数 88→33→23→11→10。

## 四、对旧记录的更正

`build_opt9.sh` 当时打印"opt9 与 opt5 全类型差异 0 行"是**错的**——它比到了一份陈旧的 `opt9.txt`。重跑后真实数是 **12 行**，且 `struct eventpoll` 从 192→216（`refcount` 之后插入 `struct callback_head rcu`），来自 epoll UAF 修复那一组改动，opt8/opt9 都带着，**而 opt9 正在真机上正常运行**。这条不改结论（静态闸照不住砖），但把"opt9 ABI 与原厂完全相同"这个说法否掉了。

## 六、结论

收益是 10 个上游修复，含 `net/ipv6/netfilter.c`、`security/selinux/xfrm.c`、`net/core/gen_estimator.c` 这几处安全相关的；性能/调度/功耗**没有任何变化**（不碰这些路径）。ABI 与 opt9 零差异，所以厂商 `.ko` 的相处方式和现在完全一样。

⛔ 但这仍然不等于"能开机"——本机已实测穷尽静态判定。退路已核对在位：opt9 `29ff625ac9fe...`、opt7-clean、opt5、原厂 `boot_a.img` `a33ff9988e5f...`。
