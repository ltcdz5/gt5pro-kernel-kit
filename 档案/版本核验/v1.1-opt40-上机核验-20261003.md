## 一、★★ 结构体改动的 CRC 判据（四次实测，规律已清楚）

| 版本 | 改了什么 | 导出 CRC 变化 | 闸门2 |
|---|---|---|---|
| opt38 | 4 处纯 `.c` | 0 | 1 ✅ |
| opt39 事故版 | `struct nf_conntrack_expect` **加字段** | **109**（39 个名字看不出来） | **7** ⛔ |
| opt39 | 纯 `.c` + 只加 `static inline` 的 `.h` | 0 | 1 ✅ |
| **opt40** | **`struct ext4_sb_info` 加 mutex** | **0** | **1 ✅** |

⇒ **判据不是"改不改结构体"，而是"该结构体在不在任何已导出符号的类型链上"。**
- `struct nf_conntrack_expect`：出现在 25 个已导出原型里，且**沿类型链**牵连到 `__skb_get_hash`
  （经 `struct sk_buff`）⇒ 109 个 CRC 变化 ⇒ 7 个厂商模块拒载（含 **WiFi 驱动 `qca_cld3_kiwi_v2`**）
- `struct ext4_sb_info`：**ext4 在 `vmlinux.symvers` 里导出 0 个符号**（`ext4_` 前缀 0 条）
  ⇒ 无人引用 ⇒ CRC 零变化 ⇒ 闸门2 仍 = 1

⚠️ **但仍必须实测** —— 名字看不出来的牵连（`__skb_get_hash`）就是反例，任何"穷举证明"只能当假设。

### ✅ 已确证的（`register_sysfs` 路径）
```
/sys/fs/ext4/ 有 14 个条目（features + 13 个设备）—— 每次 ext4 挂载都会 register
13 个 errors_count 属性可读，值全为 0
  例：/sys/fs/ext4/loop11/errors_count = 0，first_error_time = 0
ext4 挂载 25 / jbd2 线程 3 / [ext4-rsv-conver] 14 —— 与改前完全一致
EXT4 错误 0 ✓   无意外只读 ✓
锁错误（sleeping function called from invalid context / scheduling while atomic /
       bad unlock balance / held lock freed）全部 = 0 ✓
dmesg 里仅有的 2 条 "mutex" 是厂商 tri_state_key 驱动的 "init mutex variable" 日志，非报错可写 ext4（/mnt/vendor/persist）功能测试：touch / 写 / 读回 / sync / 删除 全部成功 ✓
```

### ⚠️ 未能确证的（诚实记录）
**`unregister_sysfs` 路径没能在本机功能性地跑通。**
试了三种办法挂载一个自造 ext4 镜像来制造"卸载"事件，全部失败：
1. `mount -t ext4 -o loop /data/local/tmp/img /mnt/...` ⇒ `unable to read superblock`
2. 显式 `losetup -f` + `mount` ⇒ 同样
3. 换到**不加密**的 `/mnt/vendor/persist` 上放镜像 ⇒ 仍然 `unable to read superblock`

**根因**：`dd if=/dev/block/loop50` 返回**空** —— 本机 loop 设备根本读不出来
（`/sys/block/loop0..49` 全被 APEX/opex 占用，且新建的 loop 设备读取失败）。
这不是本次改动的问题，是环境限制。

⇒ 所以 `unregister_sysfs` 里新加的 `mutex_lock/unlock` 只有**静态审查**背书
（与 `register_sysfs` 用同一把锁、同一函数里对称出现），**没有运行时验证**。
缓解：`register_sysfs` 跑通了 14 次 ⇒ 锁本身初始化正确、可正常获取；
且 `ext4_put_super` 里 `unregister` 之后紧接着 `flush_work`，锁的边界清楚。

### ★ 补充：事后做的严格静态自审（结论：改动安全）

既然运行时验不了，就把静态审查做扎实。逐条核过：

| 检查项 | 结果 |
|---|---|
| 新字段有没有落在 `#ifdef` 里 | ✅ 没有（最近的 `#ifdef` 是 `:1714 CONFIG_EXT4_DEBUG`，`:1716` 已闭合） |
| 三处加锁是否对称、边界是否正确 | ✅ `notify` 持锁+判 `state_in_sysfs`；`register` 持锁包 `kobject_init_and_add`；`unregister` 持锁包 `kobject_del` |
| 全树是否只有一处 `sysfs_notify` | ✅ **只有 `sysfs.c:525` 一处** ⇒ 锁覆盖完整，没有遗漏的调用点 |
| 所有 `kobject` 操作是否都在锁内 | ✅ `kobject_init_and_add`(:540)、`kobject_del`(:576) 都在锁内；`kobject_put`(:544) 在错误路径、锁外，但那时对象**不在 sysfs 里**（`state_in_sysfs=0`）⇒ 安全；`:594/:603/:606` 属 `ext4_init_sysfs`，操作的是**另一个对象**（`ext4_feat`/`ext4_root`），与本锁无关 |
| ★ **`mutex_init` 是否一定早于任何 `mutex_lock`** | ✅ **确认安全**。关键链条：<br>`sbi = kzalloc(...)` `:4314`（零初始化）<br>`mutex_init(&sbi->s_error_notify_mutex)` `:5296`<br>`ext4_register_sysfs(sb)` `:5537`<br>**`EXT4_SB(sb)->s_journal = journal` `:6010` ← 真正的 journal 在这里才装上**<br>而 `ext4_handle_error()` 里 `schedule_work(&sbi->s_error_work)` 的条件是 **`if (continue_fs && journal)`**（`:675`）⇒ **journal 为 NULL 时根本不会排 worker**<br>⇒ worker 最早只能在 `:6010` 之后跑，那时 `mutex_init` 早已执行 ⇒ **不存在"锁未初始化"窗口**<br>旁证：本树 `mutex_init(&sbi->s_orphan_lock)` 也在 `:5328`，同样靠后 ⇒ **我的放置位置符合本树既有惯例** |

⇒ **改动正确，无需调整。** `unregister_sysfs` 那条路径的运行时验证仍然缺失（环境限制），
但静态审查已把能查的都查了。

## 三、改动回顾（CVE-2026-31446）

**竞态**：`ext4_notify_error_sysfs()` → `sysfs_notify()` 先读 `kobj->sd`，而 umount 路径的
`ext4_unregister_sysfs()` → `kobject_del()` 并发把该 kernfs_node 释放，随后 `sysfs_notify()`
才 `kernfs_get(kn)` ⇒ **对已释放节点做 kref_get**。

★ **我改了子代理的一处说法**：单线程下 `sysfs_notify()` 是 **NULL 安全**的
（`kernfs_get()` 内部有 `if (kn)`，而 `kobject_del` 会把 `kobj->sd` 置 NULL，整段跳过）。
所以这**不是"NULL 解引用"，而是"读 `sd` 与 `kernfs_get` 之间被并发拆掉"的竞态**。

**代码位置**：`super.c:1259 ext4_unregister_sysfs` 在 `:1267 flush_work(&sbi->s_error_work)`
**之前**（`:1250-1257` 的注释自述了这个顺序及原因）。

**修法**（照上游 `d15e4b0a4185`）：
1. `ext4.h`：`struct ext4_sb_info` 加 `struct mutex s_error_notify_mutex`
2. `super.c`：fill_super 里 `mutex_init()`（紧跟 `INIT_WORK(&sbi->s_error_work)`，
   在 `:5536 ext4_register_sysfs` **之前** ⇒ 锁必定先于使用初始化）
3. `sysfs.c`：notify 持锁 + 判 `sbi->s_kobj.state_in_sysfs`；register/unregister 持锁包住 kobject 操作
