## 三、本版三项修复（回顾）

| 文件 | 改动 | 修的什么 |
|---|---|---|
| `fs/jbd2/transaction.c` | `journal = transaction->t_journal;` 从 abort 判断**之前**搬到**之后** | **CVE-2025-38337**：`h_transaction` 为 NULL 时先解引用 NULL ⇒ oops |
| `fs/ext4/extents.c` | 信用额估算 `ext_depth(inode)` → `EXT4_MAX_EXTENT_DEPTH` | jbd2 "not enough credits"（事务中途 extent 树变深） |
| `fs/ext4/inode.c` + `ext4.h` | `__ext4_iget` 加 `\|\| size > ext4_get_maxbytes(inode)` | 磁盘元数据无上界校验（损坏镜像可造超 maxbytes 的 `i_size`） |

## 四、留给 opt40 = v1.1

- **CVE-2026-31446**（`fs/ext4/sysfs.c` + `super.c`，ext4 sysfs UAF，CVSS 7.8）
  ⇒ 上游 `d15e4b0a4185` 要给 `struct ext4_sb_info` **加 mutex** ⇒ **改结构体，必须先过闸门2**
  ⇒ 因今天刚被结构体 CRC 炸过（109 个变化 / 7 模块拒载），**单独一版做，且要实测闸门**
  ⇒ 有利条件：**ext4 导出 0 个符号**（`ext4_` 前缀在 `vmlinux.symvers` 里 0 条），
     所以"结构体被谁引用"这一条理论上不成立 —— 但仍要实测
- **CVE-2025-38222**（`fs/ext4/inline.c:396`，形参 `unsigned int` 截断 ⇒ `BUG_ON` panic）
  ⇒ 需先确认本机有"可写 + inline_data"的 ext4 挂载点（25 个里多为只读 APEX loop）
