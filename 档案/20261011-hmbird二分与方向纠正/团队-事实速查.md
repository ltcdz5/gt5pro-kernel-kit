## B. 已证实的事实（不要重新论证，除非你要推翻它 —— 那就给证据）

1. **拓扑**（由 `scx_gov scx_cpufreq_init` 上机打印独立证实）：
   ```
   cluster id=0 cpumask=0-1 capacity=379     （A520）
   cluster id=1 cpumask=2-4 capacity=923     （A720 @3148MHz）
   cluster id=2 cpumask=5-6 capacity=867     （A720 @2956MHz）
   cluster id=3 cpumask=7   capacity=1024    （X4 prime）
   ```
   ⇒ 正确掩码：little{0,1} / big{2,3,4} / partial{5,6} / exclusive{7} / ex_free{7}

2. **缺陷 1（已修，opt139 起）**：`init_isolate_cpus()`（hmbird.c:669）曾把 CPU4 划入 exclusive，
   导致 big 只有 {2,3}。修法 `cpumask_set_cpu(4, iso_masks.big)`。

3. **缺陷 2（已修，opt139 起）**：`get_hmbird_cpu_util()` 读 `get_hmbird_rq(rq)->prev_runnable_sum_fixed`，
   该指针唯一写入者是厂商 `sched_walt.ko` 的 `init_hmbird_rq_wrq_variables()`（vendor-src/kernel-walt/walt.h:650），
   只在 `get_hmbird_version_type()==HMBIRD_OGKI_VERSION` 时调用；本机 DT 无 `/soc/oplus,hmbird`
   ⇒ version_type=UNKNOWN ⇒ 指针恒 NULL ⇒ **util 恒 0 ⇒ rescue 永不触发**。
   修法：`slim_walt_enable(1)` 里置 `slim_walt_ctrl = 1`，改用 hmbird 自带统计。

4. **修复效果（上机实测）**：util 0→99、`p_en=1 iso_free=1`、8 核占用由
   `91 91 32 51 0 0 0 0` 变成 `96 96 99 95 94 100 99 99`。

5. **★但开启 hmbird 后极不稳定★**：
   | 版本 | 结果 |
   |---|---|
   | opt139 | 8 线程满载时硬挂 |
   | opt140 | 45 秒通过（审核证明其改动是 **no-op**，疑似运气）|
   | opt141 | 开启后**立刻**硬挂（已去掉 irq_work 排队，仍挂）|
   **决定性证据 t141.log**：`scx=1` 后 `t=0s running=48`（空闲应为 1~3），随即挂死。

6. **审核已纠正的两点**（别再犯）：
   - `cpufreq_update_util()` 在本机是**空操作**（cpufreq_uag 走 waltgov 框架，不注册 update-util hook）
   - "持全部 rq 锁进调速器"是**厂商量产设计**，不是 AB-BA 死锁

7. **本机能力限制**：**没有 ftrace/kprobe**（`available_tracers=[nop]`）、**没有 lockdep**（CONFIG_PROVE_LOCKING 关）
   ⇒ 只能用 **pr_info 打点 + 二分禁用**。

## C. ★同类故障的历史（很重要，别重复踩）★

HANDOFF.md 记录过多轮"启用 hmbird 后硬挂"：opt104(~5s) / opt110(~7s) / opt111(~36s) / opt112(~3s) / opt133(30s)。
**opt120 的死亡现场**：
```
psi: inconsistent task state! task=5288:ndroid.systemui cpu=3 psi_flags=0 clear=4 set=0
CPU: 7 PID: 4606 Comm: kworker/7:6H
Call trace: android_rvh_dequeue_task [sched_walt] → dequeue_task → deactivate_task
            → walt_lb_pull_tasks [sched_walt] → walt_newidle_balance → newidle_balance
            → pick_next_task_fair → __schedule      （日志到此为止 ⇒ 硬挂）
```
当时定位出的**三条架构级根因**（后被 opt121 的 BK/BL/BN 修掉）：
1. arm64 把出厂的亲和性防线变成空检查（`task_cpu_possible_mask()` 对 64 位任务恒返回全掩码）；
   出厂靠 DT 的 `type=HMBIRD_OGKI` 让 WALT 越权断言有条件跳过，本机没有该节点。
2. `balance_hmbird()` 曾是死代码（零调用点）⇒ per-CPU DSQ 无消费者 ⇒ workqueue 池停摆。
3. **WALT 会拉 hmbird 类任务**：`walt_lb_pull_tasks` 遍历 `cfs_tasks` 不检查 class，
   hmbird 任务 prio 在 [100,139] 被当 fair ⇒ `deactivate_task` ⇒ **记账撕扯** ⇒ psi inconsistent。

**⇒ 我们的新变量 `slim_walt_ctrl=1` 激活的是 hmbird 自带的第三套记账
（`hmbird_sched_rq_stats` / `prev_runnable_sum` / `curr_runnable_sum`），与 WALT、PSI 并列。
极可能是第 3 条"记账撕扯"的变体。**
