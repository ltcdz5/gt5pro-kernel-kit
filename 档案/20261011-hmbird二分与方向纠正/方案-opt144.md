## 4. 【B】opt142 稳定时：让 partial 簇安全可用的修复方案（以及现在为什么挂）

### 4.1 结构性缺陷：partial 簇的 DSQ 消费者随 partial_enable 一起消失

`gen_cluster_ctx_separate()`（当前 1197-1230）与 `gen_cluster_ctx_common()`（1231-1249）里：

    case PARTIAL:
        if (!is_partial_enabled())      /* separate: 1201-1202, common: 1235-1236 */
            return -1;
        fallthrough;

所有消费者都这样起手：`consume_timeout_dsq()`、`consume_non_period_dsq()`、`consume_period_dsq()`、
`update_dsq_idx()` —— `gen_cluster_ctx()` 返回 -1 时**整段跳过该簇的 DSQ**。

而 `partial_enable` 的唯一写入者是 `set_partial_status()`（hmbird.c:619-624，`WRITE_ONCE(partial_enable, enable)`），
它只被 `set_partial_rescue()`（hmbird.c:882-889）调用，而后者只被 `partial_dynamic_ctrl()`（hmbird.c:984-1026）调用 ——
**该函数挂在唤醒路径上**：`hmbird_select_cpu_dfl()`（hmbird.c:3201）→ 限频 1 jiffy（250Hz，hmbird.c:992-995）。

### 4.2 为什么翻转会挂：三条同时成立的机理

**(i) 滞留 ⇒ nr_running 只增不减（与 running=48 直接对应）**
- 入队：hmbird.c:2390-2391 `get_hmbird_rq(rq)->nr_running++; add_nr_running(rq, 1);`
- 出队：hmbird.c:2467-2468 `hmbird_rq->nr_running--; sub_nr_running(rq, 1);`，**只在 `dequeue_task_hmbird()` 被调用时发生**；
  而 `dequeue_task_hmbird()` 只在任务被换出/迁移/睡眠/类切换时被 core 调用 —— **一个静静躺在 DSQ 里、从未被 pick 的任务不会触发 dequeue**。
- ⇒ partial_enable 一旦 1→0，此刻在 partial 簇 DSQ 里的任务**没有任何消费者**（`gen_cluster_ctx` 返回 -1），
  它的 +1 就永远配不平；每翻转一次就漏一批 ⇒ `procs_running` 单调爬升到 48。

**(ii) 选核掩码抖动 + 无锁改 idle_masks**
- `skip_update_idle()`（hmbird.c:656-667）随 `partial_enable`/`isolate_ctrl` 改变「哪些 CPU 维护 idle_masks」；
- `update_cpus_idle()`（hmbird.c:604-617）在 **set 分支直接读别的 CPU 的 `rq->curr`**，而它是**从唤醒路径（无 rq 锁）**被调用的；
- `hmbird_pick_idle_cpu()`（hmbird.c:3052-3063）据此选核 ⇒ 任务被放到「马上要退出掩码」的核上 ⇒ 迁移。

**(iii) 簇归属判定不对称**
- `task_only_blongs_to_cluster()`（hmbird.c:3165-3178）内部用 `gen_cluster_ctx()`；partial 关闭时它返回 -1 ⇒ 该函数返回 false
  ⇒ partial 簇的任务走「非簇限定」兜底（`select_cpu_from_cluster()` 用 big/little 掩码）⇒ 被放到错误簇。

### 4.3 修复方案（按风险从低到高）

**R2（推荐，根因级，最小）—— 把「partial 簇的消费」与 `partial_enable` 解耦**

    /* hmbird.c:1197 gen_cluster_ctx_separate() 与 1231 gen_cluster_ctx_common() */
    case PARTIAL:
    -    if (!is_partial_enabled())
    -        return -1;
    +    /* opt14x: partial 簇的 DSQ 必须【永远】有人消费。
    +     * 原来的 if (!is_partial_enabled()) return -1 让 partial_enable 的翻转
    +     * 直接把消费者抽走 ⇒ 已入队任务滞留 ⇒ add_nr_running 永不配平。
    +     * partial_enable 只应影响【选核】（select_cpu_dfl 的掩码），不影响【消费】。*/
         fallthrough;

判读：若 opt142 稳定（=partial 族有罪）而本版稳定，则元凶锁定为「消费者随开关消失」；
若本版仍挂 ⇒ 元凶是 partial 簇被**选核**使用这件事本身（R1/R3 方向）。
风险：partial 簇的 DSQ 在 partial 关闭期间也会被消费 ⇒ 任务可能被放到 partial CPU 上（因为消费只是把任务从 DSQ 搬到 rq）。
因此 **R2 必须与 R1 一起上**。

**R1 —— `partial_enable` 单向锁存 + 迟滞（消除抖动）**
- 在 `partial_dynamic_ctrl()` 里：只有在 `l_under && b_under` **连续 N 个 jiffy**（建议 N=8..32，即 32~128ms）成立时才 `set_partial_rescue(false,false,false)`；
- 并且**在关闭之前先清空该簇**：对 partial 簇的 DSQ 调用一次 `consume_dispatch_q()`（或直接把 l_need_rescue/b_need_rescue 置 0 而保留 partial_enable=1，让任务自然流出）；
- `set_partial_rescue(true,...)` 方向不变（立即开）。

**R3 —— 把 partial_dynamic_ctrl() 从唤醒路径移走**
- 移到 `hmbird_notify_sched_tick()`（hmbird.c:3462-3482，core.c:5831 每 CPU 每 tick、**rq 锁外**）或一个 delayed_work；
- 好处：去掉 250Hz 的无锁并发写与掩码抖动；代价：决策频率降到 HZ（对 rescue 足够）。

**R4 —— `update_cpus_idle()` 不要在唤醒路径读别的 CPU 的 rq->curr**
- 改为：`set_partial_rescue()`/`free_isocpu()` 只写状态位；`idle_masks` 全部由各 CPU 自己的 `__hmbird_update_idle()`（hmbird.c:3334-3363）维护，
  即把 `skip_update_idle()` 的判定反过来（partial 关闭时也允许 CPU 自己清 bit，只是不许别人替它 set）。

## 5. 【opt145】`sched_ravg_window_change()` 失效的修法（t2 原第 1 项）

### 5.1 现状（证据）
- 唯一写入 `new_hmbird_sched_ravg_window` 的是 `sched_ravg_window_change()`（util_track.c:658-665，`NSEC_PER_SEC / frame_per_sec`）；
- 唯一调用者是 proc 写路径 `sched_ravg_window_frame_per_sec_proc_write()`（hmbird_sched_proc.c:184-198，:192 调用）；
- 唯一**应用点**原本在 `slim_walt_irq_work()` 内（util_track.c:545-551），而该 irq_work 自 opt141 起不再被排队（util_track.c:438-466 只剩 cmpxchg）
  ⇒ **`new_hmbird_sched_ravg_window` 现在永远不会被应用**（全树只剩 4 处读：546/548/549 与定义 32）。

### 5.2 改法 A（推荐）：在 `hmbird_scheduler_tick()` 里显式应用

位置：**util_track.c:602-624 `hmbird_scheduler_tick()`**。选它的理由：
它由 `hmbird_notify_sched_tick()`（hmbird.c:3462-3482）从 `scheduler_tick()`（core.c:5831）调用，
**在 rq_unlock 之后、每 CPU 每 tick 都会跑**，且与 hmbird 的 enable 状态无关（不像 task_tick_hmbird 只对 hmbird 类 curr 触发）。

    /* util_track.c:602 hmbird_scheduler_tick() 末尾追加 */
    void hmbird_scheduler_tick(void)
    {
        int cpu = smp_processor_id();
        struct rq *rq = cpu_rq(cpu);
    
        if (unlikely(!tick_sched_clock)) {
            ... (原样保留 607-623) ...
        }
    
        /* opt145: 把 sched_ravg_window_change() 的结果在窗口边界应用。
         * 语义与厂商原实现（原 slim_walt_irq_work 内的那 5 行）逐字一致：
         * 只有当【本 CPU 的当前窗口还没越过新窗口】时才改全局尺寸，
         * 避免把已经用旧尺寸推进过的 window_start 与新的 prev_window_size 混用。*/
        if (unlikely(READ_ONCE(new_hmbird_sched_ravg_window) != hmbird_sched_ravg_window)) {
            struct hmbird_sched_rq_stats *srq = &per_cpu(hmbird_sched_rq_stats, cpu);
            u64 wc = rq_clock(rq);
    
            spin_lock(&new_sched_ravg_window_lock);
            if (unlikely(new_hmbird_sched_ravg_window != hmbird_sched_ravg_window) &&
                wc < srq->window_start + (u64)new_hmbird_sched_ravg_window) {
                hmbird_sched_ravg_window = new_hmbird_sched_ravg_window;
                /* 让本 CPU 立刻改用新尺寸，别的 CPU 在各自下一次 rollover 拾取 */
                srq->prev_window_size = hmbird_sched_ravg_window;
            }
            spin_unlock(&new_sched_ravg_window_lock);
        }
    }

注意：这里用 `rq_clock(rq)`（不持 rq 锁读 rq->clock）—— 与厂商原来在 irq_work 里用 `sched_clock()` 等价（同一时钟域）；
若担心 SCHED_DEBUG=y 的 `assert_clock_updated`（core.c 只有 update_rq_clock 内部用 RQCF_UPDATED，rq_clock() 本身不检查），
可改用 `sched_clock()`，避免任何时钟语义争议。**建议直接用 `sched_clock()`**。

### 5.3 改法 B（备选）：在 `task_tick_hmbird()` 里应用
- 位置 hmbird.c:3487-3506（captain 引的 3491 是其中的 slim_walt_ctrl 判断）。
- 优点：一定持有 rq 锁，窗口状态最稳；缺点：只对 hmbird 类 curr 触发，且形成 `rq->__lock → new_sched_ravg_window_lock` 嵌套。
- 全树只有 proc 写路径取 `new_sched_ravg_window_lock`（且不持 rq 锁）⇒ **无反向顺序，安全**，但比 A 脆。

### 5.4 必须同时做的两件事（否则修好一个坏掉两个）
1. **proc 写入侧钳位**（hmbird_sched_proc.c:184-198）：`frame_per_sec` 必须限制在 `[1, 1000]`。
   否则 `hmbird_sched_ravg_window = NSEC_PER_SEC / frame_per_sec` 可能 < 1024 ⇒ `>> SCX_SCHED_CAPACITY_SHIFT(10)` == 0 ⇒
   `scale_time_to_util()`（util_track.c:60-64）与 `slim_walt_cpu_util()`（util_track.c:318-327）**除以 0**
   （arm64 UDIV 除零返回 0，不陷入 ⇒ 只是 util 恒 0，症状与 opt138 相同）。
2. **应用时同步 `srq->prev_window_size`**（见 5.2 草案；或在应用后遍历所有 CPU 置位）。
   否则 `update_cpu_busy_time()`（util_track.c:353-435，第 361 行 `window_size = srq->prev_window_size`）
   与 `slim_walt_cpu_util()` 会在最长一个窗口内用旧尺寸。

### 5.5 风险与「何时放弃」
- 全局 `hmbird_sched_ravg_window` 被改时，各 CPU 的 `window_start` 步进（util_track.c:152-153）与已累积的 curr_runnable_sum 语义突变；
  厂商的「只在窗口边界应用」条件只检查**本 CPU**，别的 CPU 可能落后 1 个窗口 ⇒ 建议先把应用点做成「所有 CPU 的下一次 rollover 前不消费 util」或干脆只在一个窗口边界后生效。
- **若路线 D（换现成 util 源 + 关 slim_walt）被采纳，本项直接放弃**：proc 条目保留但变成 no-op，
  必须在文档/用户态侧标注「slim_walt 记账已关闭，按帧率设窗口不再生效」。

## 6. 【opt146】「无 hmbird 事件 CPU 窗口不滚动 ⇒ util 峰值保持」（t2 原第 2 项）

### 6.1 机理（证据链）
1. `slim_walt_cpu_util()`（util_track.c:318-327）返回 `srq->prev_runnable_sum / (srq->prev_window_size>>10)`；
2. `prev_runnable_sum` 只在 `rollover_cpu_window()`（util_track.c:119-129）里被更新（prev=curr; curr=0）；
3. `rollover_cpu_window()` 只被 `update_window_start()`（util_track.c:131-160）调用；
4. `update_window_start()` 只被 `hmbird_update_task_ravg()`（util_track.c:499）调用；
5. `hmbird_update_task_ravg()` 只有 5 个调用者：4 条 hmbird 类回调（2454/2910/2941/3491）+ 已死的 util_track.c:542；
6. ⇒ **没有 hmbird 任务事件的 CPU（NOHZ idle、只跑 RT/stop 的 CPU）窗口永不滚动** ⇒ `prev_runnable_sum` 保持上一次的值 ⇒ util「峰值保持」
   ⇒ `get_cpus_max_util()` 高估 ⇒ `l_over/b_over` 恒真 ⇒ `set_partial_rescue(true,...)` 常开（captain 的观察：rescue 一直开着）。

### 6.2 方案 (a)：逐 CPU 加锁的 irq_work（彻底，但有代价）

    /* util_track.c:518 slim_walt_irq_work() 重写（关键点：一次只持一把 rq 锁）*/
    static void slim_walt_irq_work(struct irq_work *irq_work)
    {
        struct rq *rq;
        int cpu;
        u64 wc = sched_clock();
        unsigned long flags;
    
        /* 绝不嵌套：每次只取一把 rq->__lock ⇒ 没有 AB-BA，也不会把 8 个核一起冻住。*/
        for_each_possible_cpu(cpu) {
            rq = cpu_rq(cpu);
            raw_spin_lock_irqsave(&rq->__lock, flags);
            /* NULL 实体防御（见 t1 报告 P1）：本路径会喂 rq->curr，可能是 init_task/idle */
            if (likely(get_hmbird_ts(rq->curr)))
                hmbird_update_task_ravg(rq->curr, rq, TASK_UPDATE, wc);
            raw_spin_unlock_irqrestore(&rq->__lock, flags);
        }
    
        /* 窗口尺寸的应用点放回这里也可以（与 §5 二选一，不要两处都做）*/
    }

并在 `slim_walt_window_rollover_run_once()`（util_track.c:438-466）里恢复排队：
    if (likely(cpu_online(raw_smp_processor_id())))
        irq_work_queue(&hmbird_slim_walt_irq_work);

取舍：
- ✅ 语义与厂商一致，所有 CPU（含 idle）的窗口都会滚动 ⇒ 从根上消除峰值保持；
- ❌ 每窗口一次 irq_work（125Hz）；若在 idle CPU 上排队，**IPI 会把该 CPU 从 idle 拉出来**（功耗）；
- ❌ 在 hardirq 上下文顺序取 8 把锁，最坏延迟 ≈ 8×（rq 锁争用时间）；需实测（建议先只对 `is_idle_task(rq->curr)` 的 CPU 做滚动，减少开销）。
- ⚠ 必须先做 §3 的 NULL 实体防御：该路径的 `rq->curr` 可能是 **swapper/0（init_task）**；
  不过 hmbird_init() 已经在启动时给 init_task 分配了实体（hmbird.c:5116-5131：`init_task.android_oem_data1[HMBIRD_TS_IDX] = kzalloc(...)`）
  ⇒ 实际非 NULL，但保留判空成本为 0。**这一条同时把 t1 报告里「init_task 是否有实体」的未决项正式关闭：有。**

### 6.3 方案 (b)：改用现成 util —— **结论：不能作为 drop-in 替代**

| 现成 util | 定义 | 能否看见 hmbird 类任务 | 结论 |
|---|---|---|---|
| `cpu_util_cfs(cpu)` | include/linux/sched/sched.h:3124（基于 `cfs_rq` 的 PELT util_avg） | **不能**（hmbird 类任务不在 cfs_rq 里；hmbird 的类注册在 fair 与 rt 之间，见 hmbird.c:3951 `.balance = balance_hmbird`） | ❌ |
| `sched_cpu_util(cpu)` | core.c:7731 = `effective_cpu_util(cpu, cpu_util_cfs(cpu), ENERGY_UTIL, NULL)` | **不能**：effective_cpu_util（core.c:7638-7729）只汇总 CFS + `cpu_util_rt(rq)` + `cpu_util_dl(rq)` + `cpu_util_irq(rq)` | ❌ |
| `rq->nr_running` | 被 hmbird 自己维护（hmbird.c:2391 add / 2468 sub） | **能**（hmbird 任务走 core 的 add/sub_nr_running） | ⚠ 只能当粗粒度/交叉校验用 |

**证据（关键）**：t140 实测 hmbird 启用 + 8 线程满载时 8 核 busy 94~100%，而此时 hmbird 类任务**全都不在 cfs_rq/rt_rq** ⇒
`cpu_util_cfs()` 必然接近 0 ⇒ 用它替换 `slim_walt_cpu_util()` 会得到「永远不 rescue」——与 opt138 的老症状一模一样。
厂商量产的 util 真源是 ROM `sched_walt.ko` 写的 `prev_runnable_sum_fixed`（vendor walt.c:5736-5740 → walt.h:648-664），
它的记账覆盖所有类 ⇒ 那才是唯一「现成且完整」的源，但本机 ROM 的 sched_walt.ko **没有 hmbird 集成**（captain 事实 3）⇒ 没人写 ⇒ 恒 NULL。

**(b1) 可用的正确用法：把现成 util 当「过期判据」**（推荐，零风险，直接修掉「rescue 常开」）：

    /* util_track.c:318 slim_walt_cpu_util() 加读侧衰减 */
    u16 slim_walt_cpu_util(int cpu)
    {
        u64 prev_runnable_sum;
        u32 wsz;
        struct hmbird_sched_rq_stats *srq = &per_cpu(hmbird_sched_rq_stats, cpu);
    
        wsz = READ_ONCE(srq->prev_window_size);
        if (unlikely(!wsz))                 /* 原实现无判零（arm64 除零=0，不崩但语义错）*/
            return 0;
        /* opt146(b1): 该 CPU 已经很久没有 hmbird 任务事件 ⇒ 窗口从未滚动，
         * prev_runnable_sum 是【过期峰值】。用 latest_clock（只在窗口滚动时更新）判过期。*/
        if (unlikely(sched_clock() - READ_ONCE(srq->latest_clock) > 2 * (u64)hmbird_sched_ravg_window))
            return 0;
        prev_runnable_sum = srq->prev_runnable_sum;
        do_div(prev_runnable_sum, wsz >> SCX_SCHED_CAPACITY_SHIFT);
        return (u16)prev_runnable_sum;
    }

取舍：
- ✅ 零锁、零 IPI、零上下文切换；直接消除「峰值保持 ⇒ rescue 常开」；
- ⚠ 语义损失：一个只跑 RT/stop 任务、完全没有 hmbird 事件的 CPU 会被报成 0。对 rescue 判据是「少报」方向，
  比现在「虚高 ⇒ 常开」更保守；若要补，可在 2 窗口超时后回退到 `cpu_util_rt(rq) + cpu_util_irq(rq)`（**能**看见 RT/IRQ）而不是 `cpu_util_cfs()`；
- 若同时采用 §6.2 的 (a)，则不需要 (b1)。**两者二选一。**

### 6.4 推荐
- 若 slim_walt 记账被保留：**先做 (b1)**（1 个函数、零风险、直接修掉 rescue 常开），把 (a) 留作「确实需要精确 per-CPU util」时的后续项；
- 若走路线 D：两者都不做，改为「换源」的更大改动（需要先把 hmbird 类任务的 util 用别的途径喂给 schedutil，超出本任务范围）。

## 8. 直接回答：dequeue 里的 wrapper 会不会造成 nr_running 只增不减 ⇒ 48？

**结论：单独这一条【不能】。但它能把整机锁死；而「只增不减」需要另一个条件。**

证据链：
1. `dequeue_task_hmbird()`（2444-2470）的顺序是：QUEUED 检查（2446-2450，**不满足就 return，不做减法**）→ `ops_dequeue()`（2452）
   → **`if (slim_walt_ctrl && task_current) wrapper(PUT_PREV)`（2454-2457）** → `clear_bit(QUEUED)` → `nr_running--; sub_nr_running()`（2467-2468）。
2. 所以「2454 永不返回」⇒ 该 rq 的 `sub_nr_running()` 永不执行。**但同一把 rq->__lock 也被 dequeue 持着**（dequeue 由 core 在持锁下调用）
   ⇒ 别的 CPU **无法**在这个 rq 上 `add_nr_running()`（enqueue 也要持同一把锁）⇒ 该 rq 的 nr_running 只是**停住**，不会涨。
   ⇒ 结果是**整机卡死**（所有等这把锁的 CPU 停摆），不是「只增不减」。
3. 「只增不减」的充分条件是：**有 CPU 在 enqueue（add_nr_running 成功），但没有任何 CPU 去 dequeue/消费**。
   而这与 `dequeue_task_hmbird()` 的耗时无关 —— 一个静静躺在 DSQ 里、从未被 pick 的任务**根本不会触发 dequeue**（dequeue 由 deactivate_task/迁移/类切换驱动）。
4. ⇒ 唯一能造成 `procs_running → 48` 的是 **§4.2(i)：DSQ 的消费者被抽走**（`gen_cluster_ctx(PARTIAL)` 在 `!is_partial_enabled()` 时返回 -1）。
   消费者是 `consume_dispatch_q()`，不是 `dequeue_task_hmbird()`；`sub_nr_running()` 全树唯一调用点是 2468。
5. 可验证的量化判据（不需 ftrace）：
   - `/proc/hmbird_sched/hmbird_stats` 的 `rq_nr` vs `scxrq_nr`（hmbird.c:4923 那两行已存在）—— 两者一起涨 = hmbird 记账膨胀；
   - 新计数器 `enq_cnt - deq_cnt` 与 `gdsqs` 非空个数 —— 前者涨、后者非 0 = 任务滞留在 DSQ。

**反过来说**：如果 opt142（partial 全关）仍挂，那就说明「消费者被抽走」不是元凶，
此时「整机锁死」类机理（含 C1：ROM WALT 在 tick 里对 hmbird 任务 deactivate/set_task_cpu）优先级最高 —— 与 §0 的判读一致。
