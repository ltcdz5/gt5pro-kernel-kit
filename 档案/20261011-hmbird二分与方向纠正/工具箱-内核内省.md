## 1. 调度器状态（回答"那 40 个任务在哪个 class / 哪个 CPU"）

### 1.1 `/sys/kernel/debug/sched/debug` —— 全 rq + 全任务快照
- **命令**：
  ```sh
  mountpoint -q /sys/kernel/debug || mount -t debugfs none /sys/kernel/debug
  cat /sys/kernel/debug/sched/debug > /data/local/tmp/sched_debug.txt
  ```
- **能回答**：每 CPU 的 `nr_running`（running 暴增时它长在哪几个 CPU）、**该 CPU 上挂着的所有任务**（comm/pid/state/vruntime/switches/prio）、CFS/RT/DL 队列积压。
- **输出形状**：`cpu#N` 段 + ` .nr_running : <n>` + `runnable tasks:` 表（表头 `S task PID tree-key switches prio wait-time sum-exec sum-sleep`）+ `cfs_rq[..]`/`rt_rq`/`dl_rq` 段。
- **root**：文件是 0444，但 `/sys/kernel/debug` 本身通常要 root 才能进 ⇒ **需要 root**。
- **阻塞风险**：★**高**。它逐 rq 加锁遍历、输出可达数百 KB。**绝不要放进 2 秒循环**（会重演 dmesg 拖死快照循环的坑）。只在"卡住那一刻"抓一次。
- **源码**：debug.c:301-345（创建）、:565-584（print_rq）、:586/668/698（三个 class 的 rq 打印）；CONFIG_SCHED_DEBUG=y(.config:7521)、CONFIG_DEBUG_FS=y(7426)。

### 1.2 `/proc/<pid>/sched` —— 判断某个任务属于哪个 class
- **命令**：`cat /proc/$(pidof system_server)/sched | grep -E "policy|ext.enabled"`
- **能回答**：该任务的 `policy` 数值与 `ext.enabled`。
- **★判据（含一个坑）**：`SCHED_HMBIRD = 7`（include/uapi/linux/sched.h:121）**与 `SCHED_EXT = 7` 同值**（:122），且 CONFIG_SCHED_CLASS_EXT=y(.config:116)。
  ⇒ 单看 `policy: 7` 不能区分；**`policy=7` 且 `ext.enabled : 0` ⇒ hmbird**（debug.c:1059 `__PS("ext.enabled", p->sched_class == &ext_sched_class)`）。
- **★未验证**：hmbird 是否真的把 `p->policy` 改成 7。我 grep `kernel/sched/hmbird/hmbird.c` **没有找到 `p->policy = SCHED_HMBIRD`**（只有 :3907 的判断）⇒ 若 hmbird 只改 `sched_class` 不改 policy，这条路**读不出来**。
  **上机 10 秒验证法**：启用 hmbird 前后各跑一次
  `for p in $(pgrep -f system_server); do grep -E "^policy" /proc/$p/sched; done`
  若启用后仍全是 0 ⇒ 判据作废，改用 §1.3 的 BPF/kprobe 或 §1.1 的列表人工比对。
- **阻塞**：低（单任务）。

### 1.3 `/proc/<pid>/stack` —— 饿死任务卡在哪
- **命令**：`cat /proc/<pid>/stack`（pid 从 `/proc/*/stat` 的 state=D 里挑，或直接对 `ux_page_pool_fi` 这类任务）
- **能回答**：该任务**当前内核栈**（符号 + 偏移）。opt142 现场里饿死 58s 的 `ux_page_pool_fi[1119]` 就属于这类目标。
- **输出形状**：每行 `[<ffff...>] func+0x.. /0x..`，末尾 `[<ffff...>] 0x0`。
- **root**：**需要**（源码 :493 检查 `CAP_SYS_ADMIN`，否则 -EACCES）。
- **阻塞**：低-中（对目标任务做 unwind，源码注释自称 "racily ... safe from races would require some work"，属标准调试接口）。
- **源码**：fs/proc/base.c:472 `#ifdef CONFIG_STACKTRACE`、:476 proc_pid_stack、:493 权限、:3364 注册；CONFIG_STACKTRACE=y(.config:7550)。

### 1.4 `/proc/schedstat`
- **命令**：`cat /proc/schedstat`
- **能回答**：每 CPU 的调度次数/运行时间/等待时间、调度域（domain）的负载均衡统计 ⇒ 迁移风暴/等待时间的旁证。
- **root**：否。**阻塞**：低。**源码**：kernel/sched/stats.c；CONFIG_SCHEDSTATS=y(.config:7523)。

### 1.5 `/proc/pressure/cpu`（PSI）—— ★把"饿死"量化
- **命令**：`cat /proc/pressure/cpu`
- **能回答**：`some avg10=.. avg60=.. avg300=.. total=..` / `full ...` ⇒ **任务饿死时 full 会飙升**，比 `running` 更直接、更可复核。
- **输出形状**：两行（some/full）+ 4 个字段。
- **root**：否。**阻塞**：极低。
- **源码**：kernel/sched/psi.c:1587-1595（`psi_proc_init` 建 `pressure/{io,memory,cpu,irq}`）；CONFIG_PSI=y(.config:131)。
- **★注意**：若内核命令行带 `psi=0` 或 CONFIG_PSI_DEFAULT_DISABLED，文件在但值恒 0 ⇒ 上机先读一次确认非零。

### 1.6 `/proc/softirqs`、`/proc/interrupts` —— IPI 风暴
- **命令**：`cat /proc/interrupts | grep -iE "resched|function call|IPI"`（间隔采样两次比差值）
- **能回答**：rescheduling IPI / function-call IPI 是否暴涨（对应"全 rq 锁 + 到处唤醒"）。
- **root**：否。**阻塞**：低。

### 1.7 `/proc/timer_list` —— ★直接确认 shadow tick 那个 1ms hrtimer
- **命令**：`cat /proc/timer_list | grep -A2 hmbird_scheduler_tick_no_balance`
- **能回答**：**hmbird 的 1ms shadow tick 是否真的在跑**、每个 CPU 的到期时间（周期应为 1ms）。
  这一点很重要：reviewer 已把 shadow tick 列为嫌疑（Stage K 起 `get_hmbird_version_type()` 恒 OGKI ⇒ `hmbird_shadow_tick_init()` 的 gate 是开的，见 `hmbird_shadow_tick.c:148-157`）。
- **输出形状**：` #N: <addr>, <function>`（:49 用 `%ps` 打回调符号）+ `# expires at ... [in ... nsecs]`。
- **root**：**需要**（:353 建的是 0400）。
- **阻塞**：中（逐 hrtimer base 加锁遍历；timer 多时可能偏慢）⇒ **不要进 2 秒循环**。
- **源码**：kernel/time/timer_list.c:46-57 print_timer、:353 `proc_create_seq_private("timer_list", 0400, ...)`、:359 `__initcall`；kernel/time/Makefile:6 `obj-y += ... timer_list.o`（**无条件编译**）；回调名来自 hmbird_shadow_tick.c:108 `->function = &hmbird_scheduler_tick_no_balance`。

## 2. 抓"卡住那一刻"（★零成本、最关键）

### 2.1 `/proc/sysrq-trigger` 的 `l` / `t` / `w`
- **命令**：
  ```sh
  echo 1 > /proc/sys/kernel/sysrq      # ★必须先做：写 trigger 会检查 mask
  echo l > /proc/sysrq-trigger         # 全部 CPU 当前栈（谁在持锁/自旋）
  echo w > /proc/sysrq-trigger         # 只打 D 状态任务的栈
  echo t > /proc/sysrq-trigger         # 全部任务状态（R/D/S）
  ```
- **能回答**：**"卡住那一刻全部 CPU 在干什么"**——这正是我们三次现场都没拿到的（opt142 只拿到了阻塞方的栈，没有持锁方的栈）。`l` 尤其关键：它会打印**正在自旋/持锁的那个 CPU**。
- **输出形状**：`sysrq: Show backtrace of all active CPUs` + `NMI backtrace for cpu N` + 每 CPU 一段栈；`w` 是 `sysrq: Show Blocked State` + 每任务 `task:<comm> state:D ... Call trace:`。
- **root**：需要（`/proc/sysrq-trigger` 通常 0200 root）。
- **★mask 陷阱**：`__handle_sysrq(key, check_mask=true)` 会检查 `sysrq_on_mask()`（drivers/tty/sysrq.c:578、:605）⇒ **`/proc/sys/kernel/sysrq` 必须是 1（或对应位）**，否则**静默无输出**。默认 `CONFIG_MAGIC_SYSRQ_DEFAULT_ENABLE=0x1`(.config:7423)，但 Android init 可能改过 ⇒ **上机先 `cat /proc/sys/kernel/sysrq`**。
- **阻塞**：`l` 用 smp_call/NMI 抓栈，通常安全；**但输出巨大**（8 核 × 数十行）⇒ 必须先放大 dmesg 缓冲/落盘，否则会被冲掉。
- **源码**：drivers/tty/sysrq.c:257 `sysrq_handle_showallcpus`、:308 `showstate`、:320 `showstate_blocked`、:348 `showmem`、:194 `show_timers`、:217 `showlocks`；CONFIG_MAGIC_SYSRQ=y(.config:7422)。
- **★未验证**：字母到 handler 的映射我**没有逐字核对**（sysrq_key_table 在 sysrq.c:461，是数组 + 注释）。`l/t/w/m` 是 upstream 标准语义，但我标"未逐字确认"；上机可先 `echo h > /proc/sysrq-trigger` 看帮助（若支持）。

## 3. tracepoint / kprobe（★本次最大的能力增量）

### 3.1 `/sys/kernel/tracing/events/` —— 逐次调度决策，不用重编
- **★关键认知**：`available_tracers=[nop]` **只说明没有 function tracer**（`.config:7598 # CONFIG_FUNCTION_TRACER is not set`），**与 tracepoint events 无关**。
  本机有：CONFIG_TRACEPOINTS=y(306)、CONFIG_TRACING=y(7594)、CONFIG_EVENT_TRACING=y(7592)、CONFIG_FTRACE=y(7596)、CONFIG_CONTEXT_SWITCH_TRACER=y(7593)。
- **可用事件**（include/trace/events/sched.h）：`sched_switch`(:246)、`sched_wakeup`(:178)、`sched_waking`(:170)、`sched_migrate_task`(:299)、`sched_stat_runtime`(:586)、`sched_process_exit`(:358)、`sched_blocked_reason`(:520)、`sched_pi_setprio`(:594)、`sched_wake_idle_without_ipi`(:737)。
- **命令**（root；tracefs 通常挂在 `/sys/kernel/tracing`，否则用 `/sys/kernel/debug/tracing`）：
  ```sh
  ls /sys/kernel/tracing/events/sched/            # ① 先确认可用（5 秒）
  echo 0 > /sys/kernel/tracing/tracing_on
  echo > /sys/kernel/tracing/trace
  echo 1 > /sys/kernel/tracing/events/sched/sched_switch/enable
  echo 1 > /sys/kernel/tracing/events/sched/sched_migrate_task/enable
  echo 1 > /sys/kernel/tracing/tracing_on         # ② 复现；卡住后：
  cat /sys/kernel/tracing/trace | tail -300
  ```
- **能回答**：**逐次切换**（prev/next/CPU/prio/state）⇒ 直接看出"某个任务为什么长时间不被选中"；`sched_migrate_task` 看迁移风暴；`sched_blocked_reason` 看 D 状态原因。
- **阻塞风险**：★**高**。开了就是每 CPU 每次切换写 ring buffer；8 核高负载下量极大。建议：只开 1-2 个事件、`echo <pid> > set_event_pid` 过滤、`echo 8192 > buffer_size_kb` 控制内存，**且不要在 2 秒循环里 cat trace**。
- **未验证**：设备上 tracefs 是否已挂载、SELinux 是否允许写（我们只从事实速查知道有人读过 `available_tracers`，说明 tracefs 挂载过）。

### 3.2 `/sys/kernel/tracing/kprobe_events` —— 不用刷机就能探函数
- **★这是把"只能 printk 重编"这条限制直接废掉的接口。**
- **命令**：
  ```sh
  echo 'p:hmb_ravg hmbird_update_task_ravg' >> /sys/kernel/tracing/kprobe_events
  echo 1 > /sys/kernel/tracing/events/kprobes/hmb_ravg/enable
  echo 1 > /sys/kernel/tracing/tracing_on
  # 复现后
  cat /sys/kernel/tracing/trace | tail -50
  echo '-:hmb_ravg' >> /sys/kernel/tracing/kprobe_events   # 清理
  ```
- **能回答**：任意**有符号的**函数的调用次数/时间点/参数/返回值 ⇒ 例如
  「`hmbird_update_task_ravg` 被调了多少次」「`set_partial_rescue` 到底有没有被调用」「`slim_walt_cpu_util` 的调用频率」「`hmbird_err_exit_work` 何时被排队」。
- **前提/限制**：目标函数必须有独立符号（**内联函数探不到**）。已知 `hmbird_update_task_ravg` 有符号（nm: `ffffffc008142884`）；`set_partial_rescue` 是 `static`，**需先在 out-core/vmlinux 里 nm 确认**（未验证）。
- **风险**：探热路径（每 tick × 8 CPU）会显著改变时序，**可能掩盖问题**；建议先探低频点（`hmbird_err_exit_work`、`slim_walt_enable`、`set_partial_rescue`），确认可行再上热路径。
- **源码**：kernel/trace/trace_kprobe.c:1959 `trace_create_file("kprobe_events", TRACE_MODE_WRITE, ...)`；CONFIG_KPROBES=y(689)、CONFIG_KPROBE_EVENTS=y(7612)、CONFIG_DYNAMIC_EVENTS=y(7615)。
  相关但更强：`dynamic_events`（kernel/trace/trace_dynevent.c:280）、`SYNTH_EVENTS=y`(7618)、`HIST_TRIGGERS=y`(7619) ⇒ 可做合成事件/直方图（进阶，未验证）。

## 7. 推荐的最小取证配方（给 captain，直接可用）

**启用前（各一次，全部 <1 秒，安全）**
```sh

cat /proc/sys/kernel/sysrq                       # 必须非 0，否则 echo 1 > ... 先打开

```

**启用后卡住那一刻（一次性，别循环）**
```sh
echo 1 > /proc/sys/kernel/sysrq
echo l > /proc/sysrq-trigger        # ★全部 CPU 栈 —— 持锁者在这里
echo w > /proc/sysrq-trigger        # D 状态任务栈
cat /proc/pressure/cpu
cat /sys/kernel/debug/sched/debug > /data/local/tmp/sched_debug.txt   # 哪个 CPU 上堆着谁
```

**如果只想回答一个问题**（优先级排序）
1. "谁在持锁" → `sysrq l`（§2.1）
2. "任务卡在哪个 class" → `/proc/<pid>/sched` 的 policy/ext.enabled（§1.2，**先验证判据**）+ `/sys/kernel/debug/sched/debug` 的任务列表（§1.1）
3. "饿死有多严重" → `/proc/pressure/cpu`（§1.5）
4. "某个函数到底有没有被调用" → `kprobe_events`（§3.2，**最大增量**）
5. "shadow tick 在不在跑" → `/proc/timer_list`（§1.7）

**⚠ 阻塞风险红名单（绝不放进 2 秒快照循环）**：`/sys/kernel/debug/sched/debug`、`/proc/timer_list`、`cat /sys/kernel/tracing/trace`、`dmesg`（已踩过）、`cat /proc/kmsg`（已踩过）。
**绿名单（可进循环）**：`/proc/stat`、`/proc/pressure/cpu`、`/proc/hmbird_sched/<int 节点>`、`/proc/<pid>/sched`（单个）。

## 9. 修订记录（2026-10-11 03:2x，captain 上机实测之后）

### 9.1 ★我的错误：把「不在我们的镜像里」当成了「设备上不存在」★

captain 实测：`/proc/hmbird_sched/slim_walt/` 与 `/proc/hmbird_sched/slim_freq_gov/` **都存在**（`cat` 返回 Is a directory），且 `/proc/hmbird_sched/slim_walt/slim_walt_ctrl` **能读出 0**。
⇒ 我在 §0-C4 与 §5 里写的"这些节点在本内核里根本不存在"**是错的**。

**正确表述（源码依据）**：
- 我们的内核镜像**只**创建 21 个**顶层**条目、**不创建任何子目录**（`hmbird_sched_proc_main.c:407` `proc_mkdir(HMBIRD_SCHED_PROC_DIR, NULL)`，:414-514）。
- `slim_walt/` 与 `slim_freq_gov/` 是**模块**建的：`kernel/oplus_cpu/sched_ext/main.c:328` `load_track_dir = proc_mkdir("slim_walt", hmbird_dir)`（`LOAD_TRACK_DIR` 定义在 :16）、`:357` `proc_mkdir("slim_freq_gov", hmbird_dir)`（:15）；其下 `slim_walt_ctrl`(:335)/`slim_walt_dump`(:340)/`slim_walt_policy`(:345)/`frame_per_sec`(:350) 与 `slim_gov_debug`(:364)/`scx_gov_ctrl`(:368)。
- **本树自己的文档就写明了这个分工**（我漏读了）：`kernel/Kconfig.preempt:150-167`
  > "hmbird_sched_proc_main.c is trimmed to the factory-kernel half (scx_enable, partial_ctrl, …) **while the module owns slim_walt/, slim_freq_gov/, scx_shadow_tick_enable, highres_tick_ctrl_dbg, cpu7_tl and frame_per_sec**."

**教训**：这正是我前几轮反复提醒 captain 的那类错误（"树里没有 ≠ 设备上没有"）。我这次自己犯了，而且**证据就在本树里**（Kconfig.preempt 的注释）。

### 9.2 连带结论（对后续实验有影响）

1. **读写 `/proc/hmbird_sched/slim_walt/slim_walt_ctrl` 作用于模块自己那份 BSS**（`main.c:30 int slim_walt_ctrl;`），与我们内核那份（`kernel/sched/hmbird/hmbird_misc.c:34`）**无关**（模块那份是局部副本，内核那份无 `EXPORT_SYMBOL`）⇒ 解释了"写它/读它对我们 hmbird 没影响"。**我 t16 §5 表格里给 `slim_walt_ctrl` 等节点标注的"不存在"作废**；它们**存在但属于模块**。
2. **ROM 模块确实被加载了**——而且这是**两条互相独立的证据**：
   - `/proc/hmbird_sched/slim_walt/`+`slim_freq_gov/`（本树不可能创建）；
   - `events/schedwalt/`（`sched_enq_deq_task`/`sched_cpu_util`/`sched_load_to_gov`/`sched_find_best_target`）——**本树 grep `schedwalt` = 空**，这些 tracepoint 只在 `vendor-src/kernel-walt/trace.h` 里 ⇒ 只能来自 ROM 的 `sched_walt.ko`。
3. **⇒ 我在 `审核-opt143.md` §R4 里的 vermagic 结论要重新定性**：那份结论（"`_audit/scx_vendor.ko` 的 vermagic 与内核不符 ⇒ 无法载入"）**对该文件本身仍然成立**（`check_modinfo` 在 `kernel/module/main.c:1995-2012` 是标准实现；`CONFIG_MODULE_FORCE_LOAD` 未设 ⇒ `try_to_force_load()` 返回 -ENOEXEC，连 `MODULE_INIT_IGNORE_VERMAGIC` 也救不了），
   **但我由它推出的"所以 ROM 模块没在跑"是错的**。
   ⇒ 结论应改为：**`_audit/scx_vendor.ko` 的 provenance 可疑**（大概率是 stock ROM dump，不是设备上真正加载的那份）；设备上真实模块的 vermagic **必然**等于我们内核（否则载不进）。
   ⇒ **定案命令**（captain）：`adb shell 'md5sum /vendor/lib/modules/oplus_bsp_sched_ext.ko /vendor/lib/modules/sched_walt.ko' ` 与 `_audit/` 里的副本比对；再看 `lsmod | grep -E 'sched_walt|oplus_bsp_sched_ext'`。

4. **新增可用的观测通道（captain 已发现，我补源码依据）**：

# 10. 观测纪律（★每次上机前先读这一节★）

> 来源：今晚的真实事故。**t150 的"卡死"不是 hmbird 单独造成的，是我们自己的观测开销造成的**——
> 同一轮里开了 **52 个 tracepoint** + 快照循环内跑 **dmesg** + 连打 **3 次 sysrq-l**。这三件事任何一件单独就足以把 8 核机器压垮。
> **观测开销必须记账**：每次测试都要记录"这一轮开了哪些 tracepoint、几次 sysrq、有没有在循环里跑 dmesg"，
> 否则事后**无法区分"hmbird 造成的"与"我们观测造成的"**——今晚就为此浪费了一整轮样本。

## 10.1 红名单：绝不放进循环（每一条都踩过）

| 接口 | 为什么不能循环 | 今晚的教训 |
|---|---|---|
| `dmesg` | 每次调用都要遍历/拷贝整个 ring buffer，缓冲大时是**重活**；输出量大 | t142：脚本 `snap()` 里跑 `dmesg tail -40`，日志停在 t3（up=68），循环再没往下走 |
| `cat /proc/kmsg` | 会**阻塞等待**新消息，等于把调用者挂住 | 事实速查 D 节已列为坑 |
| `cat /sys/kernel/debug/sched/debug` | 逐 rq 加锁遍历 + 输出数百 KB | 只在"卡住那一刻"抓一次 |
| `cat /proc/timer_list` | 逐 hrtimer base 加锁遍历 | 只在需要确认 shadow tick 时抓一次 |
| `cat /sys/kernel/tracing/trace` | 读整个 ring buffer，量随事件数爆炸 | t150：52 事件同时开，读 trace 本身就是负担 |
| `sync`（在写盘循环里） | 可能**卡在 FS 写回**上（写回 worker 被饿死时） | t142：最后一次写入停在 `dmesg tail` 之后、`sync` 之前 ⇒ **很可能卡在 sync** |

**绿名单（可进 2 秒循环）**：`/proc/stat`、`/proc/pressure/cpu`、`/proc/hmbird_sched/<int 节点>`（单个）、`/proc/<pid>/sched`（单个）、`/proc/loadavg`。

## 10.2 tracepoint 纪律

1. **一次最多开 2~3 个事件**（t150 开了 52 个 ⇒ 直接把自己压死）。优先顺序：
   `sched_switch`（谁切给谁）→ `sched_migrate_task`（迁移风暴）→ `hmbird/hmbird_update_history`（ravg 是否在跑）。
2. **必须先配置再开**：
   ```sh
   echo 0 > /sys/kernel/tracing/tracing_on          # 先关
   echo > /sys/kernel/tracing/trace                 # 清
   echo 8192 > /sys/kernel/tracing/buffer_size_kb
   echo <pid> > /sys/kernel/tracing/set_event_pid   # ★过滤，能砍掉大部分量
   echo 1 > /sys/kernel/tracing/events/sched/sched_switch/enable
   echo 1 > /sys/kernel/tracing/tracing_on          # 只在窗口内开
   ```
3. **测完立刻关**（`echo 0 > tracing_on`），不要让系统在 enabled 状态下继续跑。
4. 热路径事件（`hmbird_update_history`、`sched_stat_*`）**必须带 pid 过滤**，否则 ring buffer 几秒就被淹，反而丢掉关键窗口。
5. 判断"是否可用"用 `ls .../events/sched/`，**不要用 `available_tracers`**（它只反映 function tracer，本机是 `[nop]`，与 events 无关）。

## 10.3 sysrq 纪律

- **一次测试最多用 1 次 `sysrq-l`**（t150 用了 3 次）。每次 `l` 都会对**每个 CPU** 抓栈并打印巨量文本，在已经卡顿的系统上等于二次打击。
- **用之前先 `echo 1 > /proc/sys/kernel/sysrq`**（默认可能是 0 ⇒ **静默无输出**，白等一场）。
- 用之前先把落盘准备好（`t106.sh` 前台落盘），否则栈会被冲掉。
- 顺序建议：`w`（只打 D 状态，量小）→ 需要时再 `l`（全 CPU，量大）。

## 10.4 单变量与对照纪律

1. **一次只改一个变量**：观测开关也算变量。改观测就不要同时改内核配置。
2. **对照组必做**：不启用 hmbird、同脚本、同时长跑一次。t142 的 SMC/TZ hung-task 栈在**启用之前就已开始阻塞**（最早 dump 反推起点 ≤48.6s < enable 60.57s），说明**那批栈很可能是背景噪声**，只有对照能分辨。
3. **样本不许混用**：t142 / t147 / t150 是**不同条件**（不同 tracepoint 组合、不同 governor、不同观测开销）⇒ **不要把三者的"挂/不挂"并列当同一现象**。
4. **重复次数**：每配置 ≥5 次（既定审核结论），单次样本无法区分"通过"与"偶发"。

## 10.5 判据纪律（今晚两次栽跟头）

1. **不要用 stub 计数器**：`/proc/hmbird_sched/hmbird_stats` 的计数器是硬编码 0（`hmbird_sched_proc_main.c:326-356`）⇒ 基于 `gdsq_cnt=0`/`select_cpu=0` 的推断已作废。
2. **不要用"树里没有"推"设备上没有"**：今晚在这上面栽了**两次**——WALT（`sched_walt.ko` 是 ROM 模块）与 `slim_walt/` 子目录（ROM 模块创建）。**凡"我们树里搜不到"的结论，必须写"未验证（需设备侧确认）"。**
3. **不要用单条日志反推时间线**：`blocked for more than 20 seconds` 的"20 秒"是**超时阈值文本**，不是实际时长；对从未运行过的 kthread 还会立即触发。
4. **观察量本身要作为结论的一部分记录**（见本节开头）。

## 10.6 落盘纪律

- 硬挂无 panic 时**唯一**手段是 `t106.sh` 那类**前台**每 2 秒落盘 + sync（`nohup &` 不行）。
- **但要接受 sync 可能卡**（见 10.1）⇒ 落盘脚本应把关键状态写在 `sync` **之前**，或小文件分次写，避免最后一段全丢。
- 每次上机都要**保留原始日志**并写进 `_audit/`；今晚 `t139.log`/`t141.log` 丢失，直接导致最强的 `running=48` 证据**无法复核**。
