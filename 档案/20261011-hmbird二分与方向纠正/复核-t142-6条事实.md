## 逐条取证

### 事实 1：p_ctrl=0 全程 —— **成立**
- `t142.log:1`(header) `:2`(tpre1) `:83`(tpre2) `:165`(t1) `:246`(t2) `:327`(t3) **全部 `p_ctrl=0`**。
- 同一批里 `iso=0 iso_free=0` 也全程 0 —— 与源码预期一致：`partial_enable` 恒 0 ⇒ `is_partial_enabled()` 恒假 ⇒ `free_isocpu()` 不被调用（`hmbird.c:1010-1019`）。
- 读的正是 `/proc/hmbird_sched/partial_ctrl`（`t142.sh:19`）＝ `partial_enable`（`hmbird_sched_proc_main.c:419-422`）⇒ **opt142 生效的现场确认成立**。

### 事实 2：enable 成功 —— **成立**
- `dmesg_142.txt:17579` `[60.569516] schedtune: hmbird_sched: scx_enable=1 -> hmbird_ctrl() rc=0, enabled=1`
- 同刻 `dmesg_142.txt:17578` `<hmbird_sched>:hmbird enabled finished at jiffies = 4294907433, clock = 60569503726`（60.5695s）
- 脚本侧 `t142.log:164` `enable-write-returned rc=0 at up=60`

### 事实 3：running 增长 —— **基本成立，时间口径要改**
- `tpre1` up=54 running=**1**；`tpre2` up=60 running=**2**；`t1` up=62 running=**3**；`t2` up=65 running=**16**；`t3` up=68 running=**22**。
- ⇒ "1→3→16→22" 实际横跨 **14 秒**（up 54→68）；**6 秒只对应 3→16→22**（up 62→68）。建议改写：**"启用后 8 秒内 running 2→22（其中 3→22 用 6 秒）"**。
- `blocked=0 / waltbug=0 / psi=0` 在**全部 5 个快照**成立 ✓。
- ★**降级提醒**：`blocked` 是 `/proc/stat procs_blocked` 的**瞬时值**，而 dmesg 在 **68.597s** 就有 `smcinvoke_adci_ blocked for more than 20 seconds`。按 20s 超时反推，该任务应在 **≤48.6s** 已阻塞，与 54/60s 的 `blocked=0` 矛盾。两种解释：
  (a) hung_task 报的是"检测器上次看到该任务运行以来的时间"，对**从未运行过的 kthread** 会立即触发（假阳性）；
  (b) 检测器自身被延迟。
  ⇒ **不要把 `blocked=0` 当"启用前系统健康"的强证据**，也不要用 68.6s 那条反推"阻塞早于启用"。

### 事实 4：不是立即硬挂，61 秒后自禁 —— **成立**
- 时间线（全部来自 dmesg，行号可查）：
  - `17578/17579` enable 完成 @ **60.5695s**
  - `18718` `[121.844958] <hmbird_sched>type(4) ux_page_pool_fi[1119] failed to run for 58.016s, dsq=9223372036`
  - `18719` `[121.858432] hmbird-dbg: BB slim_walt_enable(0) from kthread_worker_fn+0x110/0x278`
  - `18720` `[121.858453] <hmbird_sched>:hmbird disabled finished ... clock = 121858453652`
- ⇒ 存活 **61.29s** ✓；`failed to run for 58.016s` ⇒ **受害任务从启用后约 2.3 秒（≈63.83s）就开始挨饿** —— 这条比"61 秒后挂"更有信息量，建议写进结论。
- "无 panic / pstore / WALT-BUG / psi inconsistent" ✓：全文 `WALT-BUG`/`psi: inconsistent`/`Kernel panic` 命中 **0**；唯一 pstore 命中是开机 10.48s 的 init 报错 `Could not read input file '/sys/fs/pstore/console-ramoops-0'`（= **没有转储文件**，反证无 panic）。
- ★机制确认：禁用入口是 `kthread_worker_fn` ⇒ 走 `HMBIRD_FATAL_INFO_FN`（`hmbird.c:327-336`：`queue_work(system_unbound_wq, &hmbird_err_exit_work)`）⇒ **是内核自检禁用，不是脚本**（脚本要到 ≈181s 才执行 `t142.sh:60`）。
- ★小订正：stall 行总长**恰好 100 字符**，`dsq=9223372036` 疑似被采集管道**截断**（`%llu` 正常应是 19-20 位）⇒ **不要用这个数做判断**。

### 事实 5：循环在 t3 后停止 —— **成立，但原因推断要改**
- `t142.log` 共 407 行；t3 状态行在 `:327`，其后是 t3 的 40 行 stats + 40 行 dmesg tail，**最后一行时间戳 68.972s**（`:407`）。脚本设计 60 次 × 2s ≈ 120s（`t142.sh:54-58`）⇒ 循环确实死在第 3~4 次之间 ✓。
- ★**更可能的原因**：`snap()` 第 36 行是 **`sync`**，而 dmesg 里有一条 hung-task 栈正是 `kworker/u16:2` 卡在 `f2fs_write_inode` → `__writeback_single_inode` → `wb_workfn`（`dmesg:18496-18510`，109.5s）——**同一个文件系统**。日志的最后一次写入正好停在 `dmesg tail`（第 34 行）之后、`sync`（第 36 行）之前 ⇒ **脚本很可能卡在 `sync`**。
- 意义不同：若是 sync/FS 写回被饿死，"循环停止"是**存储侧的后果**，不是"读 /proc 卡住"；这也解释了为什么我们手上只有启用后前 8 秒的现场。

### 事实 6：hung task 全在 SMC/锁 —— **成立，范围要扩大**
- 完整命中（`blocked for more than 20 seconds`）：`18001`(68.597s smcinvoke_adci_:992)、`18255`(89.077s 同任务)、`18461-18648`(109.55-109.56s 一批 8 条：init:343 / kworker/u16:1:76 / kworker/u16:2:94 / smcinvoke_adci_:992 / Binder:vold:1206 / kgsl_devfreq_no:1278 / TP:2151_2:9242 / binder:2621_1:2711)。**captain 的 18505-18648 只覆盖最后一批的一部分。**
- 逐条看栈：`__scm_smc_call`（`mutex_lock` / `wait_for_completion` / `down`）、`max_freq_show+0x28 → mutex_lock`（`:18612` ✓ 与 captain 一致）、`blk_crypto_get_keyslot → down_read`、`f2fs_write_inode`。**确实没有一条落在 sched 代码里**（只有 `__switch_to/__schedule/schedule` 这些阻塞方共有的框架帧）✓。
- ★但这只证明"**阻塞方卡在锁上**"，**不证明"持锁者是谁"**。"持锁者是 cpufreq/scx_gov"目前仍是假设。

## 对 captain 新结论的三条修正建议

### ★修正 A（重要）：governor 假设**没有现场证据**，测试脚本根本没记录 governor
- `t142.sh:17-24` 的 `knobs()` 只读 `partial_ctrl / isolate_ctrl / iso_free_rescue / watchdog_enable / slim_walt_ctrl`；`:39` 的 header 同样只加 `$(knobs)`。**全程没有 governor 字段**。
- dmesg 里 `scx_gov` 只有 **30.5s 的 init/注册**（`:16341-16348` `assign_cluster_ids` + `scx_cpufreq_init`），**在 enable（60.57s）之前**；全文 governor 相关只有 `__cpufreq_limits_init`（`:16320`，30.37s）。
- ⇒ "**scx_enable=1 会把 4 个 cluster 的 governor 切成 scx_gov**" 这条**目前没有证据**；引用 30.5s 那条不能支持它（时间在启用之前）。
- 建议：零刷机二分时把 `cat /sys/devices/system/cpu/cpufreq/policy*/scaling_governor` 加进每次快照（1 行），否则二分结论又只剩"稳/不稳"两个比特。

### ★修正 B：结论措辞 —— "三族无罪"成立，但是"**不需要**这三族"而非"三族被证明无害"
- opt142 现场已证 `p_ctrl=0`（partial 恒关）且源码已证该函数 util 采样关闭 ⇒ 失败仍发生 ⇒ **这三族不是失败的充分原因** ✓。
- 但 opt142 的失败形态（61s 后自检自禁、系统恢复）与 opt141（立即硬挂）**不同** ⇒ 严格说是"**同一症状族仍在**"，不是"同一个 bug 被复现"。建议结论里保留这个限定。

### ★修正 C（方法论）：建议加一次**对照运行**（不启用 hmbird，同样时长同样脚本）
- 最早的 hung-task dump 在 68.597s，按 20s 超时反推其阻塞起点 ≤48.6s（**早于 enable**）；同时这批栈全是 **SMC/TZ/充电/显示** 相关，而该机在充电+高负载下这些栈本就常见。
- ⇒ 若**不启用 hmbird** 也会出现同样这批 dump，则"持锁者被饿死"的因果链要重新审。一次对照运行的成本 ≈ 一次测试，收益是**排除背景噪声**，强烈建议在 governor 二分前先做。

## 一句话
**6 条事实取数基本正确（2 处口径/范围需修）**；但由它们推出的"**scx_gov 是元凶**"目前**证据不足**（脚本没记 governor、dmesg 无切换记录、30.5s 那条在启用之前），且"三族无罪"应限定为"**这三族不是充分原因**"。建议：governor 二分时**同时记录 governor + 加一次不启用的对照运行**。
