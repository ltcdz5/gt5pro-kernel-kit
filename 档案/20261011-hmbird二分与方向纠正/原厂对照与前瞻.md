## 0. 三句话结论（先看这个）

1. **厂商的正常路径是"WALT 桥接"路径，不是 slim_walt 路径。**
   厂商 slim_walt_ctrl **在正常运行时是 0**（唯一写入者是人手写 proc，见 §2），
   厂商的 CPU/task util 全部来自 walt_rq 的统计字段（init_hmbird_rq_wrq_variables() 接的线）。
   ⇒ 我们开的 slim_walt_ctrl=1 在**厂商机器上属于没人跑过的路径**。

2. **我们走不了那条桥接路径，而且原因比"DT 没有节点"更根本：**
   GT5 Pro（SM8650）这一代的 ROM sched_walt.ko **根本没有 hmbird 集成**
   （原厂 boot Image grep "oplus,hmbird" = 0、HMBIRD_OGKI = 0；原厂 oplus_bsp_sched_ext.ko
   126 个未定义符号里 of_* = 0 ⇒ 完全不读 DT；sched_walt.ko 是 GT5 Pro 代次）。
   ⇒ **补 DT 不会让 init_hmbird_rq_wrq_variables() 出现**，因为那个函数在 ROM 模块的二进制里不存在。

3. **因此 struct hmbird_ops 对齐（CE2-H5）是一条"必做但救不了命"的事：**
   厂商 6 字段 / 我们 5 字段确实不一致（§3），但只要 ROM WALT 不调 hmbird_ops，
   越界调用**当前不会发生**；它是"未来一旦真的接上 WALT 门控就会立刻炸"的定时炸弹，不是今晚硬挂的元凶。

**⇒ 推荐路线：D（务实路线，§7）——放弃 slim_walt 热路径，把 rescue 判据改接现成内核统计，
   同时把 struct hmbird_ops 补齐作为"未来可走厂商路径"的前置条件。**

### 1.3 结论：厂商正常路径 = 桥接路径


## 2. slim_walt_ctrl 在厂商那边到底由谁打开？——★明确回答：正常运行时不打开★

### 2.1 全部写入者（穷举）

grep -rn "slim_walt_ctrl" vendor-src/（排除 hmbird.c.txt 副本）的全部命中：

|---|---|
| kernel-hdr/hmbird_proc_val.h:15 | extern int slim_walt_ctrl; 声明 |
| kernel-hmbird/hmbird_sched.h:51 | extern int slim_walt_ctrl; 声明 |
| **kernel-hmbird/hmbird_sched_proc.c:33** | **int slim_walt_ctrl; 定义，BSS 默认值 0** |
| kernel-hmbird/hmbird_sched_proc.c:232-247 | slim_walt_ctrl_write() → slim_walt_enable(tmp_val); *pval = tmp_val;（**proc 写路径，唯一"打开"入口**）|
| kernel-hmbird/hmbird_sched_proc.c:593-596 | HMBIRD_CREATE_PROC_ENTRY_DATA("slim_walt_ctrl", …) 建 /proc/hmbird_sched/<load_track_dir>/slim_walt_ctrl |
| kernel-hmbird/hmbird_util_track.c:469 | if (!slim_walt_ctrl) return;（读）|

**slim_walt_enable(int) 的全部调用者（vendor）：**
- hmbird_sched_proc.c:241（proc 写路径，slim_walt_enable(tmp_val)）— **唯一可能传 1 的地方**
- hmbird.c:3705（disable 路径，slim_walt_enable(false)）— 只会关

### 2.2 明确回答

> **在厂商正常运行时 slim_walt_ctrl 是 0。**
> 它**只能**由用户态 echo 1 > /proc/hmbird_sched/slim_walt/slim_walt_ctrl 打开
> （hmbird_sched_proc.c:232-247 → hmbird_util_track.c:594-601），内核侧没有任何"启用 hmbird 时顺手打开它"的代码。
> hmbird 关闭时反而会把它清 0（hmbird.c:3704-3705）。

> **⇒ slim_walt_irq_work（hmbird_util_track.c:494-533，一次性锁住全部 CPU 的 rq->__lock）
> 在厂商机器上正常不跑。** 它的唯一排队者是 slim_walt_window_rollover_run_once()
> （hmbird_util_track.c:424-442），而后者只被 hmbird_update_task_ravg()（同文件 491 行）调用，
> 而 hmbird_update_task_ravg() 第一件事就是 if (!slim_walt_ctrl) return;（同文件 469-470）。
> **⇒ 厂商主线里，整套 slim_walt 记账 = 死代码，只在人手打开那个 proc 节点后才活。**

### 2.3 我们与厂商在这条路上的唯一差别

我们把 slim_walt_enable(1) 接进了 enable 路径（kernel/sched/hmbird/hmbird_util_track.c:626-640，
Stage BB 加的 slim_walt_ctrl = 1;）。
⇒ **我们等于把厂商的"调试开关"当成主路径打开了。**
这解释了"厂商不崩、我们崩"：**我们跑的是厂商从未在量产上跑过的那条分支。**

补充：LSE 说 slim_walt_ctrl "别随便关不然没法调频"，那说的是 **SM8750 移植（LSE）** 的场景；
但我们这台机器的 ROM WALT 连 hmbird 符号都没有（§1.1 注），
桥接和 slim_walt 两条路都不完整 —— 这是移植层面的先天缺口，不是配置问题。

## 3. ★核实 CE2-H5：struct hmbird_ops 布局不一致★

### 3.1 厂商定义（找到确切位置了）

**不在** kernel-hdr/hmbird.h（那个文件里没有 struct hmbird_ops 定义，只有 struct hmbird_rq @198
与 struct hmbird_sched_change_guard @221）。
**真实字段表由 vendor-src/kernel-hmbird/hmbird_misc.c:126-134 的赋值确定**（权威），
宏在 vendor-src/kernel-walt/walt.h:1573-1588：

```c
/* vendor walt.h:1573-1588 */
extern struct hmbird_ops *hmbird_ops;
#define HMBIRD_CALL_OGKI_OP(op, args...)      do { if (hmbird_ops && hmbird_ops->op) { hmbird_ops->op(args); } } while(0)
#define HMBIRD_CALL_OGKI_OP_RET(op, args...)  ({ __typeof__(hmbird_ops->op(args)) __ret = 0; if (hmbird_ops && hmbird_ops->op) __ret = hmbird_ops->op(args); __ret; })
```
```c
/* vendor hmbird_misc.c:126-134 —— 厂商写的 6 个字段，这就是权威字段表 */
void hmbird_ops_init(struct hmbird_ops *hmbird_ops)
{
        hmbird_ops->scx_enable                   = get_hmbird_ops_enabled;       /* +0  */
        hmbird_ops->check_non_task               = get_non_hmbird_task;          /* +8  */
        hmbird_ops->hmbird_get_md_info           = hmbird_get_md_info;           /* +16 */
        hmbird_ops->hmbird_get_boost_enable      = hmbird_get_boost_enable;      /* +24 */
        hmbird_ops->hmbird_get_boost_bottom_freq = hmbird_get_boost_bottom_freq; /* +32 */
        hmbird_ops->hmbird_get_boost_weight      = hmbird_get_boost_weight;      /* +40 */
}
```

> ⚠ 快照缺口：vendor-src/kernel-hdr/hmbird.h 里**没有** struct hmbird_ops { … }; 的定义体
> （grep "struct hmbird_ops" 在该目录 0 命中；hmbird_sched.h:84 只有前向声明）。
> 所以字段**顺序**由 hmbird_misc.c:128-133 的赋值顺序推定。
> 独立佐证：walt.c:2149 / 4806 / 5091 只访问 ->scx_enable（字段 0）与 ->check_non_task（字段 1），
> 这两点与我们的前两字段一致 ⇒ **前两字段对齐**，错位从第 3 个字段开始。
> 完整的 struct 定义体必须由 patcher 从 OnePlusOSS SM8750 源码树取，见附录 B-4。

### 3.2 我们的定义

include/linux/sched/hmbird.h:367-373（[读到的]）：
```c
struct hmbird_ops {
        bool (*scx_enable)(void);                                            /* +0  */
        bool (*check_non_task)(void);                                        /* +8  */
        void (*do_sched_yield_before)(long *skip);                           /* +16 */
        void (*window_rollover_run_once)(struct rq *rq);                     /* +24 */
        void (*hmbird_get_md_info)(unsigned long *vaddr, unsigned long *size);/* +32 */

```
sizeof = 40 字节。

### 3.3 逐字段对比表

| # | 偏移（厂商/我们）| 厂商字段 | 我们字段 | 判定 |
|---|---|---|---|---|
| 0 | +0 / +0 | scx_enable | scx_enable | ✅ 一致（walt.c:2149/4543/5091 用）|
| 1 | +8 / +8 | check_non_task | check_non_task | ✅ 一致（walt.c:4806 用）|
| 2 | +16 / +16 | hmbird_get_md_info（厂商顺序第 3）| do_sched_yield_before | ❌ **错位**（walt 侧没人调 do_sched_yield_before，所以暂不炸）|
| 3 | +24 / +24 | hmbird_get_boost_enable | window_rollover_run_once | ❌ **错位**（walt.c:2583 的 HMBIRD_CALL_OGKI_OP(window_rollover_run_once, rq) 会取到厂商的 hmbird_get_boost_enable 地址并当 void(*)(struct rq*) 调用）|
| 4 | +32 / +32 | hmbird_get_boost_bottom_freq | hmbird_get_md_info | ❌ 错位 |

且**第 2 字段起顺序就不同**，不只是"少一个"。

### 3.4 对齐所需的确切改动（给 patcher 的处方，我不改）

**方案 A1（推荐，严格对齐厂商 6 字段）** —— 改 include/linux/sched/hmbird.h:367-373：
```c
struct hmbird_ops {
        bool (*scx_enable)(void);
        bool (*check_non_task)(void);
        void (*hmbird_get_md_info)(unsigned long *vaddr, unsigned long *size);

```
配套（kernel/sched/hmbird/hmbird_misc.c:128-133）：
- 补 hmbird_get_boost_enable / bottom_freq / weight 三个 getter 并赋值（厂商 hmbird_misc.c:111-124 逐字）；
- 我们现有的 do_sched_yield_before / window_rollover_run_once 需要处理 ——
  **先确认有没有人在用**：grep -rn "do_sched_yield_before|window_rollover_run_once" kernel/
  ⇒ [读到的] **我们树里 0 命中**（只有 hmbird_util_track.c 里的 slim_walt_window_rollover_run_once，那是另一个函数）。
  ⇒ 可以安全删掉这两个成员。

**方案 A2（最小改动，只保证不越界）** —— 只在 5 字段末尾补 3 个 void * 占位，保证 sizeof == 48。
⇒ 但**不保证语义正确**（walt 调 window_rollover_run_once 仍会错位）。
**只在"短期不接 WALT 门控"时才可接受。**

**验证命令（零风险）**：
```c
BUILD_BUG_ON(sizeof(struct hmbird_ops) != 48);
BUILD_BUG_ON(offsetof(struct hmbird_ops, scx_enable) != 0);
BUILD_BUG_ON(offsetof(struct hmbird_ops, check_non_task) != 8);
```

### 3.5 但请注意：这条警告"现在不致命"

hmbird_ops->* 的**唯一** ROM 侧读者是 sched_walt.ko。
而 [已证实] 本机 sched_walt.ko 是 GT5 Pro 代次、二进制里没有 HMBIRD_*（HANDOFF.md:1276）。
⇒ **当前没有任何 ROM 代码会解引用我们的 hmbird_ops**，
所以 §3.3 的越界/错位**在今晚的硬挂里不构成元凶**。
它的真实风险是：**一旦我们哪天真的让 ROM WALT 走 OGKI 门控（例如换了 SM8750 代次的 WALT 模块、
或 ROM 升级），就会立刻变成"调错函数指针 ⇒ 必挂"。** 属于"必须先修、但修了也不解决当前问题"。

## 4. 厂商 walt.c 里三处"hmbird 开着就让路"的版本门

| # | 文件:行号 | 函数 | 逻辑 | hmbird 开着时的行为 | 我们补 DT 后会怎样 |
|---|---|---|---|---|---|
| 1 | walt.c:2144-2164 | account_busy_for_task_demand() | if (HMBIRD_OGKI_VERSION == type) { if (hmbird_ops && hmbird_ops->scx_enable && hmbird_ops->scx_enable() && (event==PICK_NEXT_TASK || event==TASK_MIGRATE)) return 0; } | **PICK_NEXT_TASK / TASK_MIGRATE 两种事件的 WALT task-demand 记账被跳过**（记 0）| 无变化 —— 我们 get_hmbird_version_type() 由 **Stage K** 已恒为 OGKI，**这个门现在就是开的** |
| 2 | walt.c:4543-4548 | walt_window_rollover 尾部 | if (OGKI != type || !(hmbird_ops && hmbird_ops->scx_enable && hmbird_ops->scx_enable())) { core_ctl_check(...); } | **hmbird 开着 ⇒ 不调 core_ctl_check()**（core_ctl 不参与 CPU 热插拔/隔离决策）| 无变化（门已开）|
| 3 | walt.c:4800-4811 | android_rvh_set_task_cpu() | if (!cpumask_test_cpu(new_cpu, p->cpus_ptr) && (OGKI != type || !(hmbird_ops && hmbird_ops->check_non_task && !hmbird_ops->check_non_task()))) WALT_BUG(...) | **hmbird 开着 + check_non_task() 为真 ⇒ 跳过"选了未亲和 CPU"的 WALT_BUG 断言** | 无变化（门已开）|

**补 DT 之后它们会变成什么行为？** —— **什么都不会变。** 原因有三层：

1. **内核侧已经变了**：include/linux/sched/hmbird_version.h:23-58 是 **Stage K** 的版本
   （git log -1 8965269ef89d「Stage K: treat a missing DT hmbird node as OGKI」，2026-10-09 18:38）。
   它在"没有 DT 节点"时**直接 hmbird_version_type = HMBIRD_OGKI_VERSION;**
   ⇒ 我们内核里 get_hmbird_version_type() **恒为 OGKI**。上面三个门的 OGKI != type 分支**早已是"假"**。
2. **厂商模块改不到**：hmbird_version_type 是 static（hmbird_version.h:19），
   get_hmbird_version_type() 是 static inline ⇒ **每个 TU 一份拷贝**（HANDOFF.md:287 已指出）。
   ROM sched_walt.ko 有自己的那份，而且它的二进制里**根本没有这些门**（§1.1 注）。
3. **DT 只是给"会读 DT 的代码"看的**：原厂 oplus_bsp_sched_ext.ko 的 of_* 未定义符号 = 0
   ⇒ 原厂模块完全不读 DT（HANDOFF.md:1275）。

> ★附带修正一条团队事实★：速查表 B-3 说"本机 DT 无节点 ⇒ version_type=UNKNOWN ⇒ 指针恒 NULL"。
> 这个因果链**第一环已经过期**：Stage K（10-09）之后内核侧恒 OGKI。
> 真正让 get_hmbird_cpu_util() 恒 0 的是**另一件事**：
> (a) 本机 ROM WALT 无 hmbird 集成 ⇒ 没人写 prev_runnable_sum_fixed（主因）；
> (b) 即便指针被写上，prev_window_size 指向 srq->prev_window_size，
>     而它由 hmbird_sched_init_rq()（hmbird_util_track.c:534-541）初始化，
>     那个函数只经 slim_walt_enable(1) → hmbird_sched_stats_init() 到达
>     ⇒ slim_walt_ctrl=0 时它恒 0 ⇒ hmbird.c:891-892 的 if (!prev_window_size) return 0; 兜住。
> ⇒ **结论不变（util 恒 0），但修法方向要改**：不是"补 DT"，而是"补一个能在本机真正供数的 util 源"。

### 5.2 ★对"研究子代理根因 1"的核实结果：**不成立（至少不是本移植引入的偏离）**

研究文档（研究-启用即硬挂-根因假说.md）主张：hmbird_update_task_ravg.c:466 先解引用 get_hmbird_ts(p)，
之后才判断 slim_walt_ctrl；厂商在 kernel-hdr/hmbird.h:335 是按 class 保护的 ⇒ 非 hmbird 任务没有有效实体 ⇒ 往野指针写。

核实结论（三条证据）：

1. **厂商代码逐字相同** —— vendor-src/kernel-hmbird/hmbird_util_track.c:462-470
   与我们的 hmbird_util_track.c:486-494 在这一点上**一字不差**（D-10）。
   所以"顺序错"不是我们的偏离；厂商同样"先解引用、后判断"。
2. **厂商的 4 个调用点全部在 hmbird class 自己的函数体内**（D-11）：
   dequeue_task_hmbird / set_next_task_hmbird / put_prev_task_hmbird / task_tick_hmbird。
   传给它的 p/curr 必然是 hmbird 任务 ⇒ get_hmbird_ts(p) 必然有效。
   我们的调用点位置**一一对应**，没有新增"对任意任务调用"的点。
3. 研究文档引用的 kernel-hdr/hmbird.h:335 那处 class 保护属于 **hmbird_task_util()**
   （另一个函数，static inline u16 hmbird_task_util(...)），与 hmbird_update_task_ravg() 无关，
   **不能当作后者的契约**。

**唯一残留的真问题**（值得单独确认，但风险等级下调）：
slim_walt_irq_work()（hmbird_util_track.c:494-533）第 518 行传的是 **rq->curr**，
而 rq->curr 可以是**任何**任务（fair/RT/idle）。厂商主线里它不跑（§2.2），
我们 opt141 已把 irq_work 排队去掉（git log -1 a5d5835a23d5）⇒ 这条路径当前**不可达**。
**⇒ 修它的收益是 0；不要再在这条线上花时间。**
（get_hmbird_ts(p) 对非 hmbird 任务是否恒 NULL：hmbird_ops_prepare_task 会给所有任务建实体，
所以更可能是"有实体但内容陈旧"，而不是野指针 —— **[推测的]**，与硬挂无关。）

### 5.3 一条正面结论

hmbird_util_track.c 与厂商的差异集中在**我们新增的打点与防御**（opt139-142 的注释块、
get_cpus_max_util() 常量返回、irq_work 去排队）。**核心记账算法没有偏离。**
⇒ 如果 slim_walt 路径本身有 bug，那 bug **厂商源码里也有**，
只是厂商从不在量产上打开它（§2.2）。这进一步支持"关掉它、换路"的结论。

## 6. 前瞻：接下来最可能撞上的 3~5 个新难题

### N-1（最高）running 暴增 48 与"PSI 记账撕扯"同源，但这次是 hmbird 侧的 nr_running
- **现象预期**：slim_walt_ctrl=1 一开，procs_running 从 1~3 跳到 48，几十秒内硬挂无 panic
  （t141.log：[02:06:03] t=0s running=48 load1=8.76，随即无 done 标记）。
- **根因猜测**：hmbird_update_task_ravg() 打开的 4 条热路径里，
  dequeue_task_hmbird（我们 hmbird.c:2436）与 enqueue_task_hmbird 的
  hmbird_rq->nr_running / sub_nr_running() 配对在"任务被 WALT 拉走又回来"时失配；
  叠加厂商 WALT 的 walt_lb_pull_tasks 不检查 class（速查表 C-3）。
- **预防措施**：**不要**在 slim_walt_ctrl=1 的前提下继续二分——那条路已验证三次皆挂。
  改为走 §7 的路线 D（换 util 源），把这条路径整体关回 0。
- **若撞上怎么快速定位**：
  1. echo 8 > /proc/sys/kernel/printk 扩缓冲（速查表 D）；
  2. t106.sh 前台落盘快照（硬挂唯一手段，**不能用 nohup &**）；
  3. 在 enqueue_task_hmbird/dequeue_task_hmbird 的 sub_nr_running/add_nr_running 前后各打一条
     pr_info("hmbird-dbg: nr_running cpu=%d h=%u rq=%u")，两次快照对比即可看出是"加多减少"还是"减多加少"。

### N-2（高）get_hmbird_cpu_util() 的"假修好"
- **现象预期**：某次改动后 util 突然非 0 且看似正常，但数值是**陈旧值/常量**
  （例如一直贴着 capacity），rescue 常开，负载被永久塞进 partial{5,6}。
- **根因猜测**：prev_window_size 指向 srq->prev_window_size（我们 hmbird.c:5167-5168 加的），
  而它只在 hmbird_sched_init_rq() 里被赋值（hmbird_util_track.c:538），
  该函数只经 slim_walt_enable(1) 到达 ⇒ 不打开 slim_walt 时恒 0 ⇒ 我们永远拿到 0。
  若有人"顺手"把 prev_window_size 改成常量，util 就变成"分子 / 固定窗口"——**分子也是 0**（没人写），
  于是仍 0；但若同时把分子接到别的计数器，就会得到**语义错误的非 0 值**。
- **预防措施**：任何 util 源的改动都必须同时打印 分子 / 分母 / 结果 三元组，
  并**在两种负载下各取 3 个样本**验证单调性。
- **若撞上怎么快速定位**：在 get_hmbird_cpu_util() 出口加
  pr_info_ratelimited("hmbird-dbg: util cpu=%d num=%llu den=%u res=%llu")；再在空载/单线程/8 线程三种场景各抓 5 秒。

### N-3（中高）opt142 的 get_cpus_max_util() { return 0; } 被遗忘
- **现象预期**：实验结束后忘了回滚，rescue 永不触发，8 核又退回 91 91 32 51 0 0 0 0 的形态，
  但**没人知道为什么**（因为代码里写着 return 0 还带一大段注释）。
- **根因猜测**：hmbird.c:913-928 是 captain 02:20 临时插的实验代码。
- **预防措施**：把实验开关做成**显式模块参数**（例如 static int exp_no_rescue;），并在 hmbird_proc_init 里暴露。
- **若撞上怎么快速定位**：grep -n "opt14[0-9]|二分实验" kernel/sched/hmbird/*.c 一把扫出所有实验残留。

### N-4（中）struct hmbird_ops 错位在"某天真的接上 WALT"时爆发
- **现象预期**：某次改动让 ROM WALT 开始调 hmbird_ops->*，
  立刻在 account_busy_for_task_demand / walt_window_rollover / android_rvh_set_task_cpu 里崩
  （无 panic 的硬挂，或 WALT_BUG 断言风暴）。
- **根因猜测**：§3.3 的字段错位（第 2 字段起顺序不同 + 少 8 字节）。
- **预防措施**：**现在就补** §3.4 的 A1 方案 + BUILD_BUG_ON(sizeof==48)。
  改动量极小（一个结构体 + 三个 getter），风险几乎为零（当前无读者）。
- **若撞上怎么快速定位**：崩栈里出现 [sched_walt] 且 PC 落在
  account_busy_for_task_demand / walt_window_rollover / android_rvh_set_task_cpu 附近 ⇒ 直接查 hmbird_ops 字段偏移。

### N-5（中）"关掉 slim_walt 后 util 归 0 ⇒ 回到原点"的挫败感导致反复横跳
- **现象预期**：按 §7 路线 D 关掉 slim_walt 后，8 核占用又变成 91 91 32 51 0 0 0 0，
  团队误以为"修复白做了"，于是又去开 slim_walt，回到硬挂循环。
- **根因猜测**：路线 D 必须**同时**提供新的 util 源，只关不换 = 什么都没做。
- **预防措施**：**把"关 slim_walt"和"接新 util 源"作为同一个提交**，不允许拆开。
- **若撞上怎么快速定位**：看 p_en/iso_free 两个计数器；若恒 0 而 slim_walt_ctrl 也是 0 ⇒ 就是"只关没换"。

## 7. 我们该怎么做：2~3 条路线 + 明确推荐

### 路线 A：补 DT + 对齐 struct hmbird_ops ⇒ 走厂商桥接路径
| 项 | 内容 |
|---|---|
| 改动量 | DTBO 加 /soc/oplus,hmbird/version_type { type="HMBIRD_OGKI"; } + §3.4 的结构体对齐 + 把 slim_walt_ctrl 改回 0 |
| 风险 | **极高**（方向性错误）。**补 DT 对本机无效**：ROM WALT 是 GT5 Pro 代次、不读 DT、没有 HMBIRD_* 符号（§1.1/§4），补了也不会让 init_hmbird_rq_wrq_variables() 出现。DT 只影响**我们内核侧**，而内核侧 Stage K 已经恒 OGKI。⇒ **A 拿不到任何东西。** |
| 能拿到什么 | 结构体对齐本身（N-4 的预防）是**有价值的副产品**，但它应该独立做，不应捆绑 DT |
| 结论 | **不推荐作为主路线。** 只把"对齐结构体"拆出来做（见 D 的附带项）|

### 路线 B：继续修 slim_walt 路径
| 项 | 内容 |
|---|---|
| 改动量 | 中~大：要逐条审计 if (slim_walt_ctrl) 的 **9 个分支**（hmbird.c:2448/2593/2875/2904/2935/3077/3485/4424 + hmbird_util_track.c:493），外加 irq_work 已去排队后的窗口语义修复（夜间纪要 §四 待办 2：无事件 CPU 窗口不滚动 ⇒ "峰值保持"）|
| 风险 | **高**：这是厂商**从未在量产上跑过**的路径（§2.2），等于我们自己写一套调度记账；本机**无 ftrace/kprobe/lockdep**，只能 pr_info 二分，定位成本极高 |
| 能拿到什么 | 若成功，util 质量最好（自洽、不依赖 ROM WALT）|
| 结论 | **不推荐作为第一选择。** 保留为"若 D 的 util 质量不够"的备选。**注意：D-3 的 slim_walt_ctrl=1 在 enable 路径里，B 路线意味着先把它改回 0，只在需要时按需打开** |

### 路线 C：绕开两者，rescue 判据改用现成 util
| 项 | 内容 |
|---|---|
| 改动量 | **小**：只改 get_cpus_max_util()（hmbird.c:913-960）与 is_misfit_task_on_fake_big()（hmbird.c:~2317 对应处）的 util 来源，不碰任何 if (slim_walt_ctrl) 分支 |
| 风险 | **低**：slim_walt_ctrl 保持 0，整条 slim_walt 热路径不激活（= 厂商量产状态）；改动局限在"读一个数" |
| 能拿到什么 | rescue 能触发 ⇒ partial{5,6}/exclusive{7} 被真正利用 ⇒ 达成"8 核铺开"的目标；且**不与硬挂路径相交** |
| 具体候选 util 源（按推荐度）| ① arch_scale_cpu_capacity(cpu) + cpu_rq(cpu)->cfs.h_nr_running 之类纯 rq 计数（零依赖，但粗糙）<br>② cpu_util_cfs(cpu) / cpu_util_rt(cpu)（kernel/sched/pelt.c 已有，本机 PELT 未关）<br>③ PSI：psi_system / per-cpu PSI 的 some 平均值（本机 PSI 开着，速查表里 PSI 报过错，说明它在工作）<br>④ 直接读 /proc/stat 派生的 busy 比例（最慢，不建议在热路径用）|
| 结论 | **★推荐（与 D 合并执行）★** |

### 路线 D（= C + 结构体对齐）★最终推荐★
**分两个独立提交：**

**D1（主，解决当前目标）**：把 rescue 判据从"hmbird 自记账"换成"现成内核统计"，并把 slim_walt_ctrl 关回 0。
- 改：kernel/sched/hmbird/hmbird_util_track.c:626-640（去掉 Stage BB 的 slim_walt_ctrl = 1;，恢复厂商形态：enable 侧不做任何事）；
- 改：kernel/sched/hmbird/hmbird.c:913-960（get_cpus_max_util() 的 util 源换成候选 ②或③），**同时回滚 opt142 的 return 0;**（N-3）；
- 改：hmbird.c 里 is_misfit_task_on_fake_big() / heavy_rt_placement() 的 task util 源
  （厂商在 slim_walt_ctrl=0 时用 get_hmbird_ts(p)->demand_scaled，而该字段本机由 ROM WALT 的 OGKI 门写入
  —— **但它同样是 ROM 侧**，需先用 pr_info 验证是否非 0；若非 0，则 task util 可以原样保留）。
- **验收判据**：slim_walt_ctrl == 0 的前提下，空载 8 核占用回到 9x 9x 9x 9x 9x 10x 9x 9x 形态
  （= partial/exclusive 被用上），且 ≥5 次重复实验（每次 ≥10 分钟 + 一次 8 线程满载）零异常。

**D2（独立，清掉定时炸弹）**：§3.4 的 struct hmbird_ops 对齐 + BUILD_BUG_ON 断言。与 D1 无耦合，可先合入。

**为什么推荐 D：**
1. 它**不碰**唯一被证明会挂的那条路径（slim_walt_ctrl=1）；
2. 它**不依赖**本机根本不存在的 ROM WALT hmbird 集成（§1.1 注）；
3. 它的改动面最小、可验证性最强（只看一个 util 数字 + 8 核占用）；
4. D2 顺带把 CE2-H5 这颗定时炸弹拆掉，且**风险近零**（当前无读者）。

**明确不推荐 A 作为主路线**：A 的核心假设（"补 DT 就能让 ROM WALT 接上 hmbird"）
已被 [已证实] 的二进制证据否掉（oplus,hmbird=0 / HMBIRD_OGKI=0 / of_*=0 / sched_walt.ko 无 HMBIRD_*）。
补 DT 只会改变**我们内核侧**，而 Stage K 早已把它恒置 OGKI ⇒ **净收益 = 0，净风险 = 全局配置变更**。

## E-4) ★给 patcher 的处方（路线 D1 的升级版，我不改源码）★

把 kernel/sched/hmbird/hmbird.c:880-897 get_hmbird_cpu_util() 改成：

```c
inline u64 get_hmbird_cpu_util(int cpu)
{
	u64 util = 0;

	/*
	 * 设备模块 oplus_bsp_sched_ext.ko 的 android_vh_get_util_handler
```

**为什么这是路线 D 的最优形态：**
1. **零新增记账**：不打开 slim_walt_ctrl（保持厂商量产状态），不碰任何 if (slim_walt_ctrl) 分支；

3. **失败安全**：若模块没注册该钩子（或模块没加载），util 保持 0 ⇒ 行为与今天完全一致，不会更糟；
4. 改动只有**一个函数体 + 一行调用**。

### E-9.4 ★解法：同一个钩子也能给 task util（TASK 分支）★

`android_vh_get_util_handler` 的 **TASK 分支**（`cpu=-1` + `p != NULL`）就是 task util：

```
28d0: tbz  w1,#0x1f, 28dc   ; cpu >= 0 ?
28d4: cbnz x2, 28dc         ; p != NULL ?
28dc: cbz  x2, 28ec         ; p == NULL -> CPU 分支
28e0: ldrh w8, [x2, #0xc76] ; TASK 分支: *util = *(u16*)(p + 0xc76)
28e4: str  x8, [x3] ; ret
```

⇒ **调用 `trace_android_vh_get_util(-1, p, &util)`（cpu=-1 + p!=NULL）就能拿到 task util**，
而且**这正是 ext.c:1762 已经在用的调用形式**（只是它在不可达的代码里）。
返回值是 `u16`（`ldrh` 零扩展），与 hmbird 自己的 `u16 demand_scaled`（`hmbird_util_track.c:203`）类型一致。

| `waltgov_run_callback` | `cpufreq_uag` 模块（captain 的 kallsyms：`waltgov_run_callback [cpufreq_uag]`）| 我们树 `cpufreq_uag_main.c:2593 fbg_add_update_freq_hook(waltgov_run_callback)` | **框架统一「跑回调」的入口**，被挂进 frame_boost 的 update-freq 钩子 |
| 对应我们树的同族代码 | `cpufreq_uag_main.c:85 struct waltgov_callback cb;`、`:1113 uag_gov_update_single(struct waltgov_callback *cb, …)`、`:1363 uag_gov_update_shared(struct waltgov_callback *cb, …)`、`:2582 waltgov_add_callback(cpu, &sg_cpu->cb, …)`、`:2609 waltgov_remove_callback(cpu)` | [读到的] | `uag` 与 `scx_gov` 是**同一框架下的两个 governor**，各自往 `waltgov_cb_data` 挂自己的 `*_update_freq` 回调 |

**`scx_gov_start`（模块 @0xb34）的反汇编证据**（它往那张表挂回调）：

```
b58: adrp x21 = __per_cpu_offset
b68: adrp x23 = .data..percpu+0x8        ; per-cpu 回调槽基址
b70: adrp x24 = waltgov_cb_data          ; ← 框架的回调表
b78: adrp x25 = .text+0x1ae0             ; = scxgov_update_freq（本模块 @0x1ae0）
bac: ldr  x9, [x21, cpu, lsl #3]         ; __per_cpu_offset[cpu]
bb0: adds x9, x9, x23                    ; x9 = per-cpu 槽
bb4: stp  xzr, xzr, [x9, #0x20]
bb8: stp  xzr, xzr, [x9]                 ; [0]/[8] = 0
bbc: stp  x20, xzr, [x9, #0x10]          ; [0x10] = policy (x20 = [policy+0x58])
bc0: str  w0, [x9, #0x18]                ; [0x18] = cpu
```

⇒ 即初始化一个 `struct waltgov_callback`：`{ 0, 0, policy, cpu, 0 }`，回调 = `scxgov_update_freq`。
**⇒ 结论：`uag` 与 `scx_gov` 共用 `waltgov_cb_data` + `waltgov_run_callback` 这一套锁/框架。**
**若框架层某处长期持锁，两个 governor 会一起被拖住** —— 这与现场「持锁者被饿死 ⇒ 后续全部阻塞」的形态一致，
**但要把责任归给 `scx_gov` 还需要先证明它在 t142 时是 active 的（见 E-10.3）。**

### E-10.5 `scxgov_update_freq`（模块 @0x1ae0）逐字

```
1af8: and  w8, w2, #0x3
1afc: cmp  w8, #0x1
1b00: b.ne 0x1b74            ; if ((flags & 3) != 1) return
1b04: ldr  x9, [x0, #0x10]   ; x9 = cb->policy
1b1c: ldr  x20, [x9]         ; x20 = policy->cpus（cpumask）
1b20: adrp x23 = &walt_rq
1b34: _find_next_bit 循环（遍历 policy->cpus）
1b4c: ldr  x8, [__per_cpu_offset[cpu]]
1b50: add  x8, x8, &walt_rq
1b54: ldr  x8, [x8, #0xa0]   ; walt_rq.prev_runnable_sum_fixed  (offset 160)
1b58: cmp  x19, x8 ; csel   ; x19 = max(...)
1b70: bl   scx_gov_update_cpufreq(policy, max)   ; T @0x80
```

⇒ **`scx_gov` 的频率决策输入就是 `walt_rq[cpu]+0xa0` 的最大值**（与 E-2 同一个字段）。
它本身是**无锁纯读**，不会卡；要卡只能卡在 `scx_gov_update_cpufreq`（@0x80）或框架层。
⇒ 建议 analyst 重点看 `scx_gov_update_cpufreq` @0x80-0xe0 的 `raw_spin_lock` 与
CE2-H2 提的「`policy->governor_data` 不判空」那一点。
