## 4. 断言 4：`slim_walt_cpu_util()` 的 `do_div` 除零风险

### 判定：**当前构建下"无实际除零风险"（即"有风险"不成立）**；但**代码本身没有防护**，属"潜在缺陷 + 与姊妹函数不一致"

- 代码：`hmbird_util_track.c:318-327`
  ```
  320  u64 prev_runnable_sum;
  323  prev_runnable_sum = srq->prev_runnable_sum;
  324  do_div(prev_runnable_sum, srq->prev_window_size >> SCX_SCHED_CAPACITY_SHIFT);
  ```
  `SCX_SCHED_CAPACITY_SHIFT = 10`（`util_track.c:47`）。**除数是 0 的条件是 `prev_window_size < 1024`**（不只是 ==0）。
- `prev_window_size` 的**全部赋值点**（`u32 prev_window_size` 在 `include/linux/sched/hmbird.h:156`，per-rq `srq` 内）：
  - `hmbird_util_track.c:570`（`hmbird_sched_init_rq()`）：`srq->prev_window_size = hmbird_sched_ravg_window;`
  - `hmbird_util_track.c:155`（`update_window_start()`）：同上
  **两处赋的都是 `hmbird_sched_ravg_window`**，没有别的来源。
- `hmbird_sched_ravg_window` 的取值：`util_track.c:31` `int hmbird_sched_ravg_window = 8000000;`（**静态初始化，非 0**）；
  唯一改写点 `util_track.c:549`（在 `slim_walt_irq_work` 内）= `new_hmbird_sched_ravg_window`（`:32` = 8000000）；
  而 `new_hmbird_sched_ravg_window` 只由 `sched_ravg_window_change()`（`:658-665`）写，
  **它在本树里唯一调用点是 `hmbird_sched_proc.c:192`——该文件未编译**。
- ⇒ `8000000 >> 10 = 7812 ≠ 0`，且**运行期无法被改成 <1024 的值**。
- **调用顺序**：`srq->prev_window_size` 在 `hmbird_sched_init_rq()` 前是 0（per-cpu BSS 清零），
  而 `slim_walt_cpu_util()` 只在 `slim_walt_ctrl != 0` 时可达；
  `slim_walt_ctrl = 1` 在 `slim_walt_enable()` 内**位于 `hmbird_sched_stats_init()` 之后**（`util_track.c:634-637`）⇒ 同一 CPU 上顺序正确。

### 但有两个必须记下的保留意见

1. **无防护 + 与姊妹函数不一致**：老路径 `get_hmbird_cpu_util()` 明确做了 `if (unlikely(!prev_window_size)) return 0;`（`hmbird.c:891-892`），
   新路径 `slim_walt_cpu_util()` **没有任何判断**。同一文件 `util_track.c:62`（`scale_time_to_util`）也是**无保护的同款 do_div**，而它在活路径上（`add_to_task_demand`→`update_task_demand`）。
   ⇒ 建议（低风险、零成本）在 `:320` 后加 `if (unlikely(!srq->prev_window_size)) return 0;`，`:60-64` 同理。
2. **可见性/顺序是"约定"而非"保证"**：`slim_walt_ctrl` 是**普通 int**，写入（`util_track.c:637`）与读取（`hmbird.c:945` 等）都**无 `WRITE_ONCE`/`READ_ONCE`、无屏障**。
   `hmbird_sched_stats_init()` 逐个核拿 rq 锁初始化 srq，然后才置 1；理论上别的 CPU 可能先看到 `slim_walt_ctrl=1` 再看到自己那份 `prev_window_size`（arm64 弱序）。实践概率极低，但**若将来把 enable 提前/并发化，这里会变成真实除零**。
   建议改成 `smp_store_release(&slim_walt_ctrl, 1)` + 读侧 `smp_load_acquire`（或至少 WRITE_ONCE + 保留现有 guard）。
3. 另注：`slim_walt_cpu_util()` 返回 **u16**，`prev_runnable_sum/7812` 直接截断，没有 clamp；`t140.log:13-30` 里 `lmax/bmax` 最高到 100（经 `get_cpus_max_util` 的 `ratio=util*100/cap` 归一化），所以目前看不出溢出，但这是同一个"缺防护"家族的第三个点。
