## Q1 补丁是否安全？——**是（不会崩），但功能面比它自己声称的大得多**

- 改动确认（`git diff b92e70f^ b92e70f`）：唯一代码改动是在 `get_cpus_max_util()` 的 `u64 max = 0;`（`hmbird.c:916`）之后插入注释 + `return 0;`（`hmbird.c:918-928`），原函数体（NULL 掩码兜底 931-941、`for_each_cpu` 循环 944-970）保留但不可达。**+13 行，无其它改动**；`scripts/setlocalversion` 只改版本串。
- 安全性：`max` 有初值、`mask` 参数不再使用（不告警）、无新增解引用/无新增锁。**这段代码不可能自己引发 panic/死锁**；它只会让 hmbird "更保守"。
- ★但"关掉 rescue"的**实际作用域**（这是补丁注释没说的）：

  1. `get_cpus_max_util()` 返回 0 ⇒ `lmax=bmax=0` ⇒ `l_over=b_over=false`（`hmbird.c:992/996`）、`l_under/b_under=true`（比值默认 `parctrl_low_ratio_l=50`/`parctrl_low_ratio=40`，定义在**参与编译的** `kernel/sched/hmbird_sched_proc_main.c:51-56`）。
  2. `partial_dynamic_ctrl()`（`hmbird.c:978-1020`）三个 `set_partial_rescue()` 调用点（999/1002/1004）**全部门控失败** ⇒ `set_partial_status()`（`hmbird.c:619-624`）不再被调用。
  3. ⇒ `partial_enable` **恒为 0**（定义 `kernel/sched/hmbird_export.c:48`，BSS 初值 0；内核侧唯一写入点就是 `hmbird.c:621`）⇒ `is_partial_enabled()` **整轮测试恒 false**。
  4. ⇒ `l_need_rescue/b_need_rescue` 恒 false、`free_isocpu()`（`hmbird.c:873-878`）永不调用 ⇒ `isolate_ctrl`（iso_free）**恒 0**。

## Q3 能否有效区分"util 统计"与"rescue 触发"？——**不能，只能给一个更粗的集合**（本审核的主要问题）

- 补丁注释写的判据（`hmbird.c:925-926`）：`"若本版仍 running=48 并硬挂 ⇒ 元凶在 util 统计热路径；若稳定 ⇒ 元凶在 rescue 路径"`。
- **前半句错**：本版**已经关掉了 `partial_dynamic_ctrl()` 里的 util 采样**（4 个 `get_cpus_max_util()` 恒 0 ⇒ `slim_get_cpu_util()` 不再被调用），所以"仍挂"**推不出**"元凶在 util 统计热路径"，只能推出"元凶在 `slim_walt_ctrl=1` 剩下的那些分支里"（ravg 记账 2448/2904/2935/3485 + misfit/RT 决策 2593/3077 + 2875）。
- **后半句也错**：本版稳定时，被排除的**不是** "rescue 路径"这一条，而是 **{set_partial_rescue/rescue 触发} ∪ {partial 簇参与调度（13 处）} ∪ {partial 的 util 采样}** 这个并集。
  其中"partial 簇参与调度"是**独立的一大类行为**（尤其 `3881`/`ext.c:2505` 把 PARTIAL 当 EXCLUSIVE、`1386` 跨簇消费、`3062` misfit 迁移），它与"rescue 触发"**不是同一件事**。
- 直接后果：如果 opt142 稳定，你会得出"rescue 是元凶"这个**未经区分**的结论，而真正被排除的是三件事的并集；如果 opt142 仍挂，你也只能说"不在这个并集里"。
- **建议（不改也行，但要改判读；要真区分需再加一档）**：
  - **最小改法（零编译）**：把结论改成集合表述 —— "稳定 ⇒ 元凶在 {rescue 触发 ∪ partial 簇启用 ∪ partial util 采样}"，并在报告里显式列出上面 13 处。
  - **真区分的变体（建议 B2/B3，各只动一个变量）**：
    - **B2**：在 opt142 基础上强制 `partial_enable = 1`（把 `set_partial_status()` `hmbird.c:621` 改成 `WRITE_ONCE(partial_enable, true);`，仍让 util 恒 0 不驱动 rescue）。B2 挂 ⇒ 元凶是 **partial 簇启用本身**；B2 稳 ⇒ 元凶在 rescue 触发（`set_partial_rescue`/`update_cpus_idle`）。
    - **B3**：opt141 + 只让 `free_isocpu()` 恒不执行（`hmbird.c:1012-1018` 短路）⇒ 分离 `iso_free/update_cpus_idle(ex_free)` 与 partial rescue。
  - 前提：`slim_walt_ctrl=1` 打开的分支**不止** task_tick（`2448/2593/2875/2904/2935/3077/3485/4424`，见 `核验-事实.md` §3.3），opt142 一个都没关；所以"仍挂"的结论不要写死到某一条热路径。
