# 2026-10-11 夜间工作纪要：hmbird 放置根因修复（opt139 → opt141）

## 一、今晚确认并修掉的根因（3 处，全部有上机证据）

### 缺陷 1：init_isolate_cpus() 的 CPU 分组被改错（已修，已证实）
`kernel/sched/hmbird/hmbird.c:669`

- Stage R 注释已按真机拓扑定成 `big={2,3,4}`、`exclusive={7}`；
- Stage AR 却拿 SM8750 参考实现覆盖为 `big={2,3}`、`exclusive={4,7}`，
  把同属 policy2（3148MHz）的 CPU4 误划入"独占/隔离"组。
- **上机证据（opt139 dmesg）**：
  ```
  hmbird-dbg: BB masks little=0-1  big=2-4  partial=5-6  exclusive=7  ex_free=7
  [scx_gov] cluster id=0 cpumask=0-1 capacity=379
  [scx_gov] cluster id=1 cpumask=2-4 capacity=923   ← CPU4 确与 2/3 同簇
  [scx_gov] cluster id=2 cpumask=5-6 capacity=867
  [scx_gov] cluster id=3 cpumask=7   capacity=1024
  ```
- 修法：`cpumask_set_cpu(4, iso_masks.big)`（opt139 起）。

### 缺陷 2：get_hmbird_cpu_util() 恒返回 0 ⇒ rescue 永不触发（已修，已证实）
- 该函数读 `get_hmbird_rq(rq)->prev_runnable_sum_fixed`，而这个指针**唯一的写入者**
  是厂商 `sched_walt.ko` 的 `init_hmbird_rq_wrq_variables()`（vendor-src/kernel-walt/walt.h:650），
  它只在 `get_hmbird_version_type() == HMBIRD_OGKI_VERSION` 时被调用。
  本机 DT 无 `/soc/oplus,hmbird` 节点 ⇒ version_type = UNKNOWN ⇒ 不调用 ⇒ 指针恒 NULL。
- 后果链：util 恒 0 ⇒ `l_over/b_over` 恒假 ⇒ `set_partial_rescue()` 永不调用
  ⇒ partial{5,6} 与 exclusive{7} 永远闲置 ⇒ 8 核占用 `91 91 32 51 0 0 0 0`。
- 修法：`slim_walt_enable(1)` 里置 `slim_walt_ctrl = 1`，改用 hmbird 自带的
  `hmbird_util_track` 统计（`srq->prev_runnable_sum`），不再依赖厂商模块桥接。
- **上机证据（opt139/opt140）**：util 由 0 → 85/86 → 99，`p_en=1 iso_free=1`，
  8 核占用变成 `96 96 99 95 94 100 99 99`。

### 缺陷 3（已修，但**不是**崩溃原因）：slim_walt_irq_work 的全局锁风暴
- 该函数每 ~8ms（125Hz）**一次性锁住全部 8 个核的 rq->__lock** 再逐个更新窗口。
- opt140 把其中"持锁调用 cpufreq"移到锁外；**审核证明这是空操作**
  （cpufreq_uag 走 waltgov 框架，不注册 update-util hook；且 t139/t140 的 governor 是 performance）。
- opt141 干脆**不再排队该 irq_work**。

## 二、★仍未解决：hmbird 一开就崩★

三次开启 hmbird 的实测：

| 版本 | governor | 结果 |
|---|---|---|
| opt139 | performance | 8 线程满载时**硬挂复位** |
| opt140 | performance | 45 秒满载**通过**（但审核证明 opt140 的改动是 no-op，可能是运气）|
| opt141 | performance | **开启后立刻硬挂复位**（去掉 irq_work 也照样挂）|

**关键新证据（t141.log）**：
```
[02:06:03] scx=1 p0=performance
[02:06:03]   t=0s running=48 load1=8.76     ← 空闲手机 running 应该是 1~3
（随即挂死，无 done 标记）
```
**⇒ hmbird 一开启，可运行任务数暴增到 48 然后挂死。** 这不是 irq_work（opt141 已去掉）。

**⇒ 结论：opt139 引入的"打开 slim_walt_ctrl"这条链路（util tracking + rescue）本身不稳定。**
范围包括：`hmbird_update_task_ravg` 新开启的 4 个热路径调用点
（task_tick / set_next / put_prev / dequeue）、`set_partial_rescue` / `free_isocpu` /
`update_cpus_idle`、DSQ 跨簇 consume。

### 下次的二分方案（审核建议，按顺序）
| 实验 | 改法 | 区分什么 |
|---|---|---|
| A | 不排队 irq_work | 已做（opt141），**证明不是它** |
| B | `slim_walt_ctrl=1` 但 `get_cpus_max_util()` 返回常量 | tracking vs rescue 触发 |
| C | `set_partial_rescue()` / `free_isocpu()` 改成只打印不执行 | rescue 路径 |
| D | `slim_walt_ctrl=0`（退回 opt138 行为）但保留掩码修正 | 只验证掩码修正 |

**⇒ 建议从 B 或 C 开始**（最可能）。另注意：本机**没有 ftrace/kprobe**
（`available_tracers=[nop]`）、**没有 lockdep**，只能用 pr_info 打点 + 二分禁用。

## 三、审核对 opt140 的纠正（重要，勿再犯）
1. `cpufreq_update_util()` 在本机是**空操作**（无 hook 注册）。
2. "持全部 rq 锁进调速器"是**厂商量产设计**（vendor walt.c:4314-4430 明写），不是 AB-BA。
3. 把调用移出锁外**破坏 schedutil 的 fast-switch 串行化不变式** ⇒ 用未证实的死锁换了真实的窄竞态。
4. **方法论漏洞：opt139/opt140 各只有 1 次样本**，"通过"与"偶发"无法区分。

## 四、opt141 引入的两个待办（审核指出）
1. **`sched_ravg_window_change()` 失效** —— 它唯一的应用点在被删掉的那段里
   （用户态按帧率设窗口的功能没了）。需要在 opt142 里显式处理或明确放弃。
2. **无 hmbird 任务事件的 CPU 窗口永不滚动** ⇒ `slim_walt_cpu_util()` 变"峰值保持"
   ⇒ `get_cpus_max_util()` 高估 ⇒ rescue 一直开着（恰好达成目标，但属副作用）。

## 七、opt142（二分实验 B）判读更正 —— 2026-10-11 02:50（patcher，t10 repair）

**结论先行：opt142 一次性关掉了三件事，判据必须写成集合。**

`get_cpus_max_util()` 恒返回 0 之后（hmbird.c:913 起）：

1. **rescue 触发**：`lmax = bmax = 0` ⇒ `l_over/b_over` 恒假 ⇒
   `set_partial_rescue(true, …)` 永不发生（partial_dynamic_ctrl 里 1007/1009 两行不可达）。
2. **partial 簇启用**：`l_under/b_under` 恒真 ⇒ 若 partial 已开，每 tick 命中
   `else if (is_partial_enabled() && l_under && b_under) set_partial_rescue(false,false,false)`
   ⇒ `partial_enable` 被**主动清 0**。
   **静态证明（无需上机）**：`partial_enable` 的唯一写入者 `WRITE_ONCE(partial_enable, …)`
   在 hmbird.c:621（`set_partial_status()`）；`set_partial_status()` 的唯一调用者是
   `set_partial_rescue()`（:866）；`set_partial_rescue()` 的唯一调用者是
   `partial_dynamic_ctrl()`（:1007/1009/1011）——opt142 下 1007/1009 不可达，1011 传的是 false
   ⇒ **partial_enable ≡ 0**。（t106 快照里的 `/proc/hmbird_sched/partial_ctrl` 应恒为 0，可作上机确认。）
3. **partial 的 util 采样**：partial_dynamic_ctrl() 里 4 处 `get_cpus_max_util()` 恒 0，
   `slim_get_cpu_util()` 不再被调用。**反汇编复核（opt142 rev2 的 vmlinux）**：
   全 vmlinux 里 `bl slim_get_cpu_util` 计数 = **0**。

**⇒ 正确判据**：opt142 仍 running=48 并硬挂 ⇒ 元凶在
**{rescue ∪ partial 簇启用 ∪ partial util 采样}** 并集内；
opt142 稳定 ⇒ 只能排除该并集，**不能**单独归因于 rescue（rev1 的说法是错的）。
