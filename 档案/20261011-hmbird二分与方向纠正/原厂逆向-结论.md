## 0. 一句话结论（先说最重要的）

**`stock-kernel.bin` 里根本没有 `hmbird_update_task_ravg` —— 这台设备的原厂内核跑的不是我们移植的那套 hmbird。**

- 原厂内核的 hmbird = **基于 sched_ext 的 `hmbird_sched`（风驰）**：
  Image 里有 `enqueue_task_scx` / `pick_next_task_scx` / `__scx_notify_pick_next_task` /
  `scx_notify_sched_tick` / `scx_scheduler_tick` / `scx_switch_log` / `hmbird_stats_open/show` /
  `hmbird_panic_handler` / `scx_iso_masks`，以及 43 处 `<hmbird_sched>` 打印前缀。
- WALT 那一族（`hmbird_update_task_ravg` / `slim_walt_*` / `hmbird_sched_class` / `init_isolate_cpus`）
  **在 Image 里一个都没有**；它在**可加载厂商模块 `sched_walt`** 里
  （captain 的 `/proc/kallsyms` 已证实 `sched_walt` 模块在跑，且 `walt_lb_tick`/`walt_lb_pull_tasks` 已挂上）。
- ⇒ **Q1 无法从 stock-kernel.bin 回答**（函数不存在，见 §1.1）。
  但 §1.2 用**我们自己的 vmlinux**（真正会崩的那份二进制）给出了**指令级**答案，强度不低于原厂反汇编。

## 1. Q1 ★最高优先★ —— `hmbird_update_task_ravg()` 有没有 sched_class 保护

### 1.1 原厂 Image 侧：该函数在 stock-kernel.bin 中**不存在**（三条独立证据）

**证据 1 — BTF 函数表（最硬）**

`stock-kernel.bin` 内嵌一个**完整合法**的 `.BTF` 段，位于文件偏移 **0x16574c8**：

```
magic=0xeb9f  version=1  flags=0  hdr_len=24
type_off=0     type_len=3,449,616
str_off=3,449,616  str_len=2,338,679
=> 解析出 134,344 个 type，其中 FUNC=57,460、FUNC_PROTO=31,869、STRUCT=11,389、VAR=279
```

CONFIG_DEBUG_INFO_BTF=y 时 BTF 覆盖内核镜像里的**全部函数**（含 static），
所以"某函数不在 BTF FUNC 表里" = "该函数不在这个内核里"。

在 57,460 个 FUNC 里检索（全部 0 命中）：

| 名字 | stock-kernel.bin |
|---|---|
| `hmbird_update_task_ravg` | **0** |
| `slim_walt_ctrl` / `slim_walt_enable` / `slim_walt_cpu_util` | **0** |
| `hmbird_sched_class` / `enqueue_task_hmbird` / `pick_next_task_hmbird` / `init_sched_hmbird_class` | **0** |
| `init_isolate_cpus` / `set_cpu_isomask` | **0** |
| `get_hmbird_version_type` / `get_hmbird_cpu_util` | **0** |
| `hmbird_sched_rq_stats` / `prev_runnable_sum_fixed` / `curr_runnable_sum_fixed` | **0** |
| `walt_rq` / 任何 `walt_*` 函数 | **0** |

**证据 2 — 全镜像裸字符串检索**：上述名字在 35.7 MB 里 **0 命中**（`grep -c`）。
（对照：`iso_masks` 3 命中、`hmbird_sched` 43 命中、`scx_iso_masks` 1 命中 —— 说明检索方法有效，不是没搜到。）

**证据 3 — 493 个厂商 .ko 全量扫符号**：`nm -a` 遍历 `vendor-ko\` 下 493 个模块，
含 `hmbird|slim_walt|walt` 符号的只有 6 个，其中只有
**`vendor_dlkm/oplus_bsp_sched_ext.ko`**（md5 `38fa6c992d1621fe8a77fcca88a1bc83`，
与工作区里的 `_audit/scx_vendor.ko` **同一文件**）与调度有关，而它**也不定义**
`hmbird_update_task_ravg`（`grep -rl` 全目录 0 命中）。
⇒ 我们手上**没有任何**含 `hmbird_update_task_ravg` 的厂商二进制。

**证据 4 — 版本不一致（重要）**：`oplus_bsp_sched_ext.ko` 的 vermagic 是
`6.1.141-android14-11-o-g5de16d278e6c`，而 `stock-kernel.bin` 的 banner 是
`6.1.141-android14-11-o-g6ed3e67335d5`（`#1 SMP PREEMPT Mon Aug 10 17:46:19 UTC 2026`）。
两者**不是同一次构建**。⇒ `stock-kernel.bin` 与 `vendor-ko` 不能当作同一套 ROM 交叉引用，
引用时要标明来源。（`op_ace3pro_Image`=6.1.118、`natsu_Image`=6.6.143 是另外两台机器，已排除。）

### 1.2 我们侧：反汇编 `hmbird_update_task_ravg` —— **没有 class 保护**（指令级证据）

这份才是真正把设备搞挂的二进制。符号地址来自 `out-core/vmlinux`：

```
nm -n out-core/vmlinux | grep hmbird_update_task_ravg
ffffffc008142884 T hmbird_update_task_ravg
```

`llvm-objdump -d --start-address=0xffffffc008142884 out-core/vmlinux`：

```asm
ffffffc008142884 <hmbird_update_task_ravg>:
  ...2884  paciasp
  ...2888  sub   sp, sp, #0x180
  ...28a8  mrs   x8, SP_EL0
  ...28ac  adrp  x9, 0xffffffc00a5a3000          ; 页基址（slim_walt_ctrl 所在页）
  ...28b0  ldr   x8, [x8, #0x638]                ; 栈金丝雀
  ...28b4  stur  x8, [x29, #-0x10]
  ...28b8  ldr   w8, [x9, #0xd70]                ; w8 = slim_walt_ctrl
  ...28bc  cbz   w8, 0xffffffc008142f20          ; ★ if (!slim_walt_ctrl) return;  —— 开关判断在最前
  ...28c0  ldrsw x8, [x1, #0xbc0]                ; rq->cpu        (x1 = rq)
  ...28d4  mov   x21, x1
  ...28d8  ldr   x8, [x28, x8, lsl #3]           ; per_cpu 基址
  ...28dc  add   x27, x8, x25
  ...28e0  ldr   x19, [x27]                      ; srq->window_start
  ...28e4  cbz   x19, 0xffffffc008142f20
  ...28e8  ldr   x26, [x0, #0xde0]               ; ★★ x26 = p->android_oem_data1[1] == get_hmbird_ts(p)   (x0 = p)
  ...28f4  ldr   x8,  [x26, #0xc0]               ; ★★ 解引用 x26+0xc0 —— x26==NULL 时【数据异常，地址 0xc0】
  ...28f8  cmp   x8,  x3
```

**三条事实**：

1. **没有任何 `sched_class` 比较**。整个函数前 0x70 字节里不存在
   `ldr xN,[x0,#0x340]`（`p->sched_class`，本机 task_struct 偏移 **0x340**，由 `pahole -C task_struct` 取得）
   也没有与 `hmbird_sched_class` 的 `cmp`。**只有 `slim_walt_ctrl` 一个门**。
2. **偏移 0xde0 就是 `get_hmbird_ts(p)`**：`include/linux/sched/hmbird.h:12-17`
   ```c
   #define HMBIRD_TS_IDX 1
   #define get_hmbird_ts(p) ((struct hmbird_entity *)(p->android_oem_data1[HMBIRD_TS_IDX]))
   ```
   `pahole -C task_struct` 显示 `u64 android_oem_data1[6]` 在 **0xdd8**，
   ⇒ `android_oem_data1[1]` = 0xdd8+8 = **0xde0** ✔ 与 `ldr x26,[x0,#0xde0]` 完全吻合。
3. 编译器**把 `if (!slim_walt_ctrl) return;` 提到了最前面**（源码里它写在解引用之后，
   但 sts 只在后面用，early-exit 被上提）。所以：
   - `slim_walt_ctrl == 0` ⇒ 安全（这正是 opt139 之前一直没事的原因）；
   - **`slim_walt_ctrl == 1`（= 我们从 opt139 起的改动）⇒ 每个走到这里的任务都会执行
     `ldr x26,[p,#0xde0]` + `ldr x8,[x26,#0xc0]`。非 hmbird 任务该字段为 0 ⇒ 在
     `0xc0` 上取数异常 ⇒ 持 rq->lock 的调度器内部炸 ⇒ 无 panic、无转储、看门狗静默复位。**

**厂商自己的不变式恰恰是"非 hmbird 任务没有有效 hmbird 实体"**，同一个访问器厂商是**按 class 保护**的：

```c
/* _audit/vendor-src/kernel-hdr/hmbird.h:335  （与 _audit/opt139/vendor_hmbird_hdr.h:335 一致） */
static inline u16 hmbird_task_util(struct task_struct *p)
{
        return (p->sched_class == &hmbird_sched_class) ? get_hmbird_ts(p)->sts.demand_scaled : 0;
}
```

⇒ **"厂商是怎么让 hmbird 既启用又不崩的"（就我们这份移植而言）的二进制答案：
厂商从不让非 hmbird 任务抵达 hmbird 实体；我们的移植在热路径上丢了这个 `sched_class` 判据。**

### 1.3 ★必须更正团队假说★ 4 条热路径**不是**"对任何任务"调用

`研究-启用即硬挂-根因假说.md` 的"根因 1"前提是
"该函数被 4 条调度热路径对**任何任务**调用"。**源码级核对后这条不成立**：

| 调用点 | 所在函数 | 调用者身份 |
|---|---|---|
| `hmbird.c:2456` | `dequeue_task_hmbird()` | 只在 **hmbird_sched_class 的 dequeue 回调**里 ⇒ p 必为 hmbird 任务 |
| `hmbird.c:2912` | `set_next_task_hmbird()` | 同上（set_next 回调） |
| `hmbird.c:2943` | `put_prev_task_hmbird()` | 同上（put_prev 回调） |
| `hmbird.c:3492` | `task_tick_hmbird()` | 同上（tick 回调，curr 必为 hmbird 任务） |
| `hmbird_util_track.c:542` | `slim_walt_irq_work()` | **唯一真·any-task 调用点**：`for_each_cpu → hmbird_update_task_ravg(rq->curr, ...)` |

4 个 hmbird.c 调用点全部包在 `if (slim_walt_ctrl)` 且位于 hmbird 类回调内（原文已核），
所以它们**不会**踩野指针。**唯一的野指针路径是 `slim_walt_irq_work` 的 `rq->curr` 循环**，
而 opt141 已经**不再排队**这个 irq_work（`hmbird_util_track.c:457-467` 注释 + 代码已改为 `(void)result;`）。

⇒ **结论：opt141"开启即硬挂"的原因，很可能不是根因 1。**
根因 1 只在"irq_work 被排队"的版本（opt139 之前/opt139）成立。
建议把重心放回根因 2（`SCX_TASK_QUEUED` 位不一致 ⇒ `add_nr_running` 只加不减 ⇒
`procs_running=48` ⇒ LB 正反馈），这与 t141.log 的 `running=48` 现象直接对应。

> 仍未验证（本轮时间不够）：`hmbird.c` 4 个调用点所在回调是否**真的只会收到 hmbird 任务**
> （core 对 `set_next_task`/`put_prev_task` 的调用语义）。这一点建议由源码面复核。

## 3. Q3 `struct walt_rq` 布局（SM8650 原厂二进制核实）

**结论：在 `stock-kernel.bin` 上核实不了 `walt_rq`，因为该类型不在 Image 里。**
BTF 的 11,389 个 STRUCT 里没有任何名字含 `walt` 的类型（0 命中）；
`walt_rq` 是 `oplus_bsp_sched_ext.ko` 的**未定义导入符号**（`U walt_rq`），
⇒ 它由 `sched_walt.ko` 提供，而**我们没有 `sched_walt.ko`**（见 §6 卡点）。
所以 OnePlusOSS issue #21 的 "648 B / 40 成员 / `prev_runnable_sum_fixed`@152 / `curr_runnable_sum_fixed`@160"
**在 SM8650 上既证实不了也否证不了**。

**能核实的替代事实**：Image 里有一个 **`struct scx_sched_rq_stats`**，与 runnable_sum 记账直接相关：

```
struct scx_sched_rq_stats   size = 48 B   vlen = 6
  +0    window_start
  +16   prev_window_size
  +32   prev_runnable_sum      <-- 字节偏移 32
  +40   curr_runnable_sum      <-- 字节偏移 40
```

⇒ 原厂 SM8650 的 runnable_sum 记账在 `scx_sched_rq_stats` 的 **+32/+40**，
**不是** issue #21 说的 152/160。两者是不同的结构、不同的模块，不能混用。

### 3.1 ★补遗（2026-10-11 补）：原厂把 util 通过 `android_vh_get_util` 钩子暴露；并含一处更正★

**更正**：本报告先前追加的补遗里，我一度把读 `walt_rq+0x40/0xa0` 的函数写成
`android_vh_hmbird_update_load_handler`。**upstream 指出，我已用 nm 边界 + 全文反汇编复核：正确的是
`android_vh_get_util_handler`（0x28d0）。** 报告 §3 正文只写了偏移、未写函数名，故正文不受影响。

nm 边界（scx_vendor.ko）：
```
0x28b8 android_vh_hmbird_update_load_handler
0x28c0 android_vh_hmbird_init_task_handler
0x28c8 android_rvh_hmbird_update_load_enable_handler
0x28d0 android_vh_get_util_handler          <-- 就是它
0x292c check_non_ext_task
```

`llvm-objdump -d --start-address=0x28d0 --stop-address=0x2928 scx_vendor.ko`
（binutils objdump 对本 .ko 报 architecture UNKNOWN，**必须用 llvm-objdump**）：

```asm

  28d0: tbz  w1,#0x1f, 28dc   ; cpu >= 0 ?
  28d4: cbnz x2, 28dc         ; cpu<0 且 p!=NULL -> 28dc
  28d8: ret                   ; cpu<0 且 p==NULL -> 什么都不做（安全）
  28dc: cbz  x2, 28ec         ; p == NULL -> 走 CPU 分支

  28e4: str  x8,[x3] ; ret

  2908: add  x8,x8,x9          ; &per_cpu(walt_rq, cpu)

  2910: ldr  x8,[x8,#0xa0]     ; prev_runnable_sum_fixed (160, u64)
  2914: lsr  x9,x9,#10         ; >> SCHED_CAPACITY_SHIFT
```

**三条结论**

1. `walt_rq+0xa0` / `walt_rq+0x40` 就是 **`get_hmbird_cpu_util()` 的输入**，模块把它挂在
   `android_vh_get_util` 钩子上 ⇒ **"原厂 Image 里没有 SM8750 那代桥接" ≠ "本机拿不到 util"**：
   模块用另一种接口把同一份 walt_rq 数据暴露出来了。

2. `p+0xc76` 落在 `u64 android_vendor_data1[64]`（本机 task_struct 里在 **0xbd8**，size 0x200）内
   ⇒ 即数组内**字节偏移 158**（元素 19 的高 16 位）。
   **原厂的 per-task util 就放在 `android_vendor_data1` 的这个槽里。**
3. **全部 493 个厂商 .ko 中，`android_vh_get_util` 的唯一注册者就是 `oplus_bsp_sched_ext.ko` 自己**
   （`U __tracepoint_android_vh_get_util` + handler 0x28d0）。我们内核侧**无注册者**，
   唯一调用点是 `kernel/sched/ext.c:1762`（`debug_enabled()` 内的 systrace 打印，传 `(-1, p, &util)`）。
   ⇒ handler 对 (cpu≥0 / cpu<0) × (p 非空 / p==NULL) 四种组合都有分支，**没有任何 NULL 解引用**
   ⇒ **调用方传 `p == NULL` 是安全的**（这一条正是 upstream 列的"patcher 提交前唯一阻塞项"）。

## 4. Q4 原厂 `init_isolate_cpus()` 掩码

**结论：做不出来（卡点明确）。**

- `init_isolate_cpus` 在 Image 的 BTF FUNC 表里 **0 命中**，裸字符串也 **0 命中** ⇒ 函数不存在。
- Image 里确有导出符号 `iso_masks`（ksymtab 字符串 3 命中，其中
  `0x163fb54` 处上下文为 `...reboot_mode\0iso_masks\0try_wait_for_completion...` —— 典型 `__ksymtab_strings`）。
  但**没有符号表就没有 `iso_masks` 的运行时地址**，无法定位其初始化常量，
  也无法从 40 字节里猜出 little/big/partial/exclusive 的位模式。
- 唯一间接旁证：BTF 里 `struct scx_iso_masks` **size = 40 B，5 个成员**。
  本机 8 个 CPU ⇒ `cpumask` = 8 B ⇒ 5×8 = 40 B ✔
  ⇒ 结构形状（5 个 cpumask 成员）与我们的 `iso_masks` 一致，
  但**成员数值（= 我们改成 {0,1}/{2,3,4}/{5,6}/{7} 是否正确）无法从原厂二进制核实**。

**要解开需要**：`iso_masks` 在 Image 里的地址 ⇒ 即 **kallsyms 表**。
建议后续用 `vmlinux-to-elf`（WSL 里没有 pip，需先装）或自写 kallsyms 解压器从
`stock-kernel.bin` 提取 `kallsyms_offsets/names/token_table`，再按地址读 `.data`。

## 5. Q5 原厂怎么确定 `version_type` / 有没有 DT 之外的兜底

### 5.1 源码面（确定）

`wt-core/include/linux/sched/hmbird_version.h`：

```c
enum hmbird_version { HMBIRD_UNINIT, HMBIRD_GKI_VERSION, HMBIRD_OGKI_VERSION, HMBIRD_UNKNOW_VERSION };

#define HMBIRD_VERSION_TYPE_CONFIG_PATH "/soc/oplus,hmbird/version_type"

static enum hmbird_version hmbird_version_type = HMBIRD_UNINIT;   /* ← static，每个 TU 一份 */

static inline enum hmbird_version get_hmbird_version_type(void)   /* ← static inline，每个 TU 一份 */
{
        if (HMBIRD_UNINIT != hmbird_version_type) return hmbird_version_type;
        np = of_find_node_by_path("/soc/oplus,hmbird/version_type");
        if (np) { of_property_read_string(np, "type", &s);
                  "HMBIRD_OGKI*" -> OGKI ;  "HMBIRD_GKI*" -> GKI ;  其他 -> OGKI ;  return; }
        /* Stage K: 本机 DT 没有该节点 */
        hmbird_version_type = HMBIRD_OGKI_VERSION;   /* ← 已经是 OGKI 兜底，不是 UNKNOWN */
        return hmbird_version_type;
}
```

⇒ **来源 = DT `/soc/oplus,hmbird/version_type` 的 `type` 属性（纯 DT，无编译期常量、无全局变量注入）。**
⇒ **兜底默认值 = `HMBIRD_OGKI_VERSION`**（Stage K 已改；注释里写明"SM8650 本来就属 OGKI 档"）。
⇒ **枚举取值：UNINIT=0, GKI=1, OGKI=2, UNKNOW=3。**

### 5.2 ★给 captain 的两条更正（会影响新头号假说）★

**(a) "本机 `get_hmbird_version_type()` 返回 UNKNOWN" 对内核侧已经过期。**
当前 `wt-core` 的该函数在无 DT 节点时返回 **OGKI**（上面 §5.1 的 Stage K 分支）。
但树里**还有一个独立实现**保留着 UNKNOWN 语义：
`kernel/sched/hmbird_sched_proc_main.c:113-146` 的 `hmbird_read_version_type()`，
它的字符串 **`hmbird_sched: no /soc/oplus,hmbird node in DT; version_type stays %s (safe degrade)`**
**确实存在于 `Image.opt141` 里**（我在 opt141 的裸字符串里找到了它，还有 `HMBIRD_OGKI`、
`/soc/oplus,hmbird/version_type`、`HMBIRD_GKI`、`HMBIRD_GKI_VERSION`、`HMBIRD_OGKI_VERSION`）。
⇒ 树里**并存两套 version 判定**：`hmbird_version.h`（→OGKI）与
`hmbird_sched_proc_main.c`（→ 保持 UNKNOWN 的 "safe degrade"）。
**必须先确定 opt141 上 `hmbird_version_type` 到底是哪个值**，再谈那 15 处让路。
（建议：captain 在设备上读 `/proc/hmbird_sched/*` 或 dmesg 里这两条 pr_info 哪一条出现。）

**(b) 即便内核侧是 OGKI，厂商模块侧仍然是 UNKNOWN —— 这是新假说真正的机制。**
`hmbird_version_type` 是 **`static`**、`get_hmbird_version_type()` 是 **`static inline`**，
都在**头文件**里 ⇒ **每个编译单元一份私有副本**。
预编译的厂商模块（`sched_walt.ko`、`oplus_bsp_sched_ext.ko`）用的是**厂商原始头文件**编出来的副本，
**我们改 `hmbird_version.h` 对它完全无效**。
现成的同类证据：`oplus_bsp_sched_ext.ko` 里 **自己也定义了一份 `slim_walt_ctrl`**
（`nm` 显示 `0000000000000090 B slim_walt_ctrl`），与内核那份 `B slim_walt_ctrl` 是**两个不同的对象**
（captain 的 kallsyms 也看到两个同名符号）—— 同一套"头文件里的静态状态被每个模块各复制一份"的模式。

⇒ **新头号假说（15 处 `HMBIRD_GKI_VERSION == get_hmbird_version_type()` 让路不生效）在结论上仍然成立，
但机制要改写为"模块侧副本读到 UNKNOWN/OGKI，而我们的头文件补丁影响不到模块"。**
补充：厂商的 WALT 让路**确实全部是拿 GKI 比较**（`grep -c` 计数）：

| 文件 | `HMBIRD_GKI_VERSION` 出现次数 |
|---|---|
| `vendor-src/kernel-walt/walt.c` | 7（行 2160/2584/4884/4977/5163/5260/5325）|
| `vendor-src/kernel-walt/walt_cfs.c` | 4 |
| `vendor-src/kernel-walt/walt_lb.c` | 3（含 715、929、1158）|
| `vendor-src/kernel-walt/walt_rt.c` | 2 |
| `vendor-src/kernel-walt/sched_avg.c` | 1 |
| `vendor-src/vendor-sched_ext/main.c` | 2 |

**注意**：`oplus_bsp_sched_ext.ko` 里 **没有任何** `HMBIRD_OGKI`/`HMBIRD_GKI`/`version_type` 字符串，
也**不导入 `of_find_node_by_path`** ⇒ **该模块不做 version 判定**。
⇒ 做 version 判定的是 `sched_walt.ko`（我们没有），或者根本是 `hmbird_version.h` 被内联进各模块的
其它 .ko。**这条建议交给 upstream 复核。**

## 7. 给团队的 3 条可执行结论

1. **opt141 的挂死原因大概率不是根因 1**（野指针）：4 个热路径调用点都在 hmbird 类回调内，
   唯一 any-task 路径 `slim_walt_irq_work` 已被 opt141 停用。→ 优先查根因 2（`SCX_TASK_QUEUED` 泄漏 ⇒ `running=48`）。
2. **若要给 `hmbird_update_task_ravg` 加保护，正确的判据是 `p->sched_class == &hmbird_sched_class`**
   （厂商 `hmbird.h:335` 的不变式），而不是只看 `slim_walt_ctrl`。
   注意必须放在 `get_hmbird_ts(p)` **之前**（我们当前源码里它在之后，靠编译器上提才侥幸安全）。
3. **改 `hmbird_version.h` 影响不到预编译厂商模块**（`static` + `static inline` ⇒ 每 TU 一份副本；
   `oplus_bsp_sched_ext.ko` 自带一份 `slim_walt_ctrl` 即同类证据）。任何依赖 version_type 的让路，
   必须在**模块侧**解决，不能靠改内核头文件。

## 8. t18 追补（2026-10-11 03:10 收工前落盘）：sched-walt.ko 检索结论 + scx_vendor.ko 入口/前置条件链

### 8.1 任务 B 结论：**本机没有 sched-walt.ko，也没有任何 vendor_boot 镜像**（明确回报）

四条证据：

1. images/清单.txt（2026-10-09 生成，逐文件 md5）枚举了 images/ 下全部文件：只有
   boot_a.img（201,326,592 B，md5 a33ff9988e5ffa6a40a13b1c8dad4abb）、init_boot_a.img（8,388,608 B），
   其余全是我们自己的 boot-*-repacked.img / .gz。**清单里没有任何 vendor_boot*.img。**
2. 全盘按文件名搜 vendor_boot|vendor-boot|vendorboot|sched.?walt|sched_walt
   （F:\工作区、C:\Users\xutengfa\Desktop、Downloads）：唯一命中是
   F:\工作区\_scene-apk\x\assets\kr-script\img\vendor_boot_rec.sh —— **脚本名，不是镜像**。
3. boot_a.img 头部实测（header v4，page 固定 4096）：

       kernel_size    = 0x0220AA00 = 35,695,104   （= stock-kernel.bin 字节数，吻合）
       ramdisk_size   = 0                          <-- 关键
       header_version = 4

   ⇒ 该镜像是「原厂 kernel + **ramdisk 置 0**」的 repack（正是我们 repack 的特征），
     **其 ramdisk 里不可能有 sched-walt.ko**；紧随 kernel 之后的区域实测全 0。
4. 全盘 find -name "*.ko"（排除 gt5pro-kernel/vendor-ko）→ **0 个文件**；
   vendor-ko 下 493 个 .ko 中无一含 sched-walt / walt_lb_tick 字符串
   （唯一与调度相关的 oplus_bsp_sched_ext.ko 把 walt_rq / waltgov_cb_data / register_walt_ops 作为 **U 导入**）。

⇒ **结论：本机没有 sched-walt.ko，也没有 vendor_boot 镜像。**
   **需要 captain 从设备 dump /dev/block/by-name/vendor_boot_a，解包其 ramdisk 取出该 .ko。**
   （设备 dmesg 的 init: Loading module /lib/modules/sched-walt.ko 出现在 0.256s 的 initramfs 阶段，
     与「它来自 vendor_boot 的 ramdisk」一致。）

### 8.2 任务 A：scx_vendor.ko 的入口与前置条件链（机器码级）

#### A-1 ★该模块【没有】version 判定 —— 对任务书第 1) 条的直接否定答案★

- nm -a scx_vendor.ko | grep -c of_find_node_by_path = **0**；
  模块的 126 个导入里**没有任何 of_* 函数** ⇒ **它在结构上无法读 DT**。
- 模块内无 HMBIRD_GKI / HMBIRD_OGKI / version_type / get_hmbird_version_type 字符串或符号
  （upstream t6 独立复核，结论一致）。

   「version_type 决定模块行为」这条路径在 oplus_bsp_sched_ext.ko 上**不存在**；
   若那 15 处 GKI 让路真在设备上生效，只可能落在 **sched-walt.ko**（仍缺该文件）。

#### A-2 module_init / module_exit

    0000000000000024 T sched_ext_init      （module_init 实体）
    0000000000000024 T sched_ext_exit      （module_exit 实体）
        0x24: d65f03c0   ret               <-- exit 是空函数，无任何反注册

#### A-3 hmbird_misc_init @0x2650 —— 注册主体

- per-CPU 清零循环（0x2694-0x26c4）：

      ldr  w1,[x20]              ; nr_cpu_ids（全局）
      ldr  x9,[x21,w0,uxtw#3]    ; __per_cpu_offset[cpu]
      str  wzr,[x9,x22]          ; *(per_cpu_ptr + x22) = 0

  ⇒ 把所有 CPU 上某个 **per-CPU 变量**（模块自己的那份状态）置 0。
- __mutex_init（0x26d8: mov x2,xzr ; bl）。
- **连续注册 9 个 tracepoint**（relocation 0x2148 / 0x2164 / 0x2180 与 0x26c8 / 0x26e4 / 0x2700 / 0x271c / 0x2738；
  均为 __tracepoint_android_vh_* / __tracepoint_sched_*）。

- **scx_get_md_info**（R_AARCH64_CALL26 @0x27a4）。
- 另有 ext_module_loaded（ADR+LDR32 @0x4c/0x54，读一个 int/bool）
  与 __scx_ops_enabled（@0x2638，即 check_scx_enabled @0x2638 的实现）。

#### A-4 hmbird_sysctrl_init @0x2948 —— proc 节点注册

反复执行「读全局 hmbird_dir → 建节点」：

    ldr x2,[x20]        ; x2 = hmbird_dir   （reloc hmbird_dir+0，LDST64）
    mov w1,#0x1b6       ; 0x1b6 = 438 = 0o666  <-- proc 文件权限
    ... bl <proc create>

hmbird_dir 的 LDST64 relocation 共 6 处（0x2960 / 0x298c / 0x29ac / 0x29cc / 0x2a68 / 0x2ac4）
⇒ 模块在**我们的** hmbird_dir 下创建约 6 个 proc 节点。

⇒ **这从机器码侧证实 captain 的实测**：/proc/hmbird_sched/slim_walt/ 与 slim_freq_gov/ 这类子目录
   **来自 ROM 模块**（hmbird_dir 由我们内核导出，节点由模块创建），与 hmbird_sched_proc_main.c 无关；
   因此 /proc/hmbird_sched/slim_walt/slim_walt_ctrl 读写的是**模块自己那份 BSS**，
   与我们内核的 slim_walt_ctrl（hmbird_misc.c:34）互不影响。

#### A-5 符号契约：126 个导入中，我们内核【没有】的只有 7 个

    get_hmbird_cpu_exclusive      （树内 refs=0）
    register_hmbird_sched_ops     （树内 refs=2，不在我们的 Module.symvers）

其余 **119 个导入我们内核都已导出**（含 ext_module_loaded、hmbird_dir、__scx_ops_enabled、
scx_get_md_info、iso_masks、task_is_scx、balance_push_callback、cpufreq_register_governor、
gov_attr_set_init/get/put、__cpufreq_driver_target 等）。
判定方法：nm -u scx_vendor.ko（126 项） 与 我们 nm out-core/vmlinux 的 T/D/B/R/W 导出集做 comm -23。

#### A-6 判定：补齐后能不能在这个内核上跑起来？

- **能加载**：ABI 面只剩 6 个未满足（5 个 WALT/调度符号 + 1 个 minidump）；
  这 6 个里 5 个正好由 **sched-walt.ko** 提供 ⇒ 设备上它本来就在跑，vermagic/CRC 与本机内核一致。
- **能跑 ≠ 安全**：该模块**没有 version 判定、exit 为空**，且 scxgov_update_freq 以
  walt_rq+0xa0 为**唯一** util 输入（见本报告 §3.1）⇒ 若 walt_rq 未被初始化，
  governor 会以 util=0 把 4 个 cluster 压到最低频。
- **ABI 风险（明确）**：walt_rq 是 **percpu 结构**，0x40 / 0xa0 这两个偏移是**编译期常量**；
  只要我们的 struct walt_rq 与 ROM 布局不一致，读到的就是错字段（而不是报错）。
  这正是本报告 §3 想核实「648 B / 40 成员」的原因，而它**仍卡在 sched-walt.ko 上**。

### 9.2 任务 B（E5 核心）：register_hmbird_sched_ops 三判据

素材：oplus_bsp_sched_assist.ko（466,440 B，not stripped）。

#### ① 是否向内核注册一个 sched_class？→ **否。只注册一张回调表指针。**

     000000000001a00c <register_hmbird_sched_ops>:
       1a018: cbz  x0, 1a048        ; ops == NULL -> 直接返回
       1a020: adrp x8, <global>     ; &hmbird_sched_ops
       1a028: mov  x2, x0
       1a030: mov  x1, xzr
       1a038: casal x9, x2, [x8]    ; CAS：若 *x8==0 则 *x8 = ops
       1a044: cbnz x8, 1a080        ; 已被注册过 -> 走 printk 告警路径
       1a054: ldxr / stlxr ...      ; 同语义的 CAS 循环（另一条路径）
       1a080: adrp x0,<fmt> ; bl <printk> ; ret

nm -S 给出 `000000000000c0490 8 B hmbird_sched_ops` ⇒ **全局只有 8 字节 = 一个指针**，不是 ops 表本身。
`test_task_is_hmbird` @0x1a094：读该全局 → `ldr x8,[x8]`（取表的第 0 个字段）→ PAC 校验后 `blr`
⇒ **纯粹的转发调用**；对 p==NULL 与 ops==NULL 都有 `cbz` 早退（返回 0，安全）。

⇒ **没有任何 sched_class 注册**。`nm -a sched-walt.ko | grep -c sched_class` = 0；
  `oplus_bsp_sched_assist.ko` 里也没有 `sched_class` 符号。
⇒ **原厂三件套（sched_assist / sched-walt / sched_ext）都不注册 sched_class。**
  **`hmbird_sched_class` 是我们移植引入的、原厂没有的东西。**

#### ② 原厂那套是否自己负责 8 核铺开？→ **是，但不是通过 sched_class。**

⇒ **我们那套 little{0,1}/big{2,3,4}/partial{5,6}/exclusive{7} 掩码是被 ROM 核心读取并执行的** ——

### 9.2.1 判定（按 upstream 规则）

规则原文：「若 ① = 原厂核心不做放置 ⇒ 这条中间路线作废，回到 opt144。」
① 的两半必须分开答：

- ①a「注册 sched_class」= **否**
- ①b「原厂核心不做放置」= **否**（原厂做放置，只是不走 sched_class）

⇒ **规则的前提不成立 ⇒ 这条中间路线【不作废】。**

**但路线内容必须改写**（否则会被误读）：

1. 「隔离我们的 hmbird_sched_class、只保留 7 个 hub 符号让原厂核心工作」——
   原厂核心**本来就不需要 hmbird_sched_class**（三件套里一个 sched_class 都没有）。
2. 真正的障碍是：**ROM 的 hmbird core（sched_ext.ko）注册的是 sched_ext ops，而不是 sched_class**，
   而 upstream t17 已判「注册 scx 调度器 = opt43 实测硬挂」。
3. 所以中间路线的**现实形态** = 不注册 scx，只让 sched_assist + sched-walt 的 fair 钩子工作。
   此时 `register_hmbird_sched_ops` 不会被调用（调用者是 sched_ext.ko）
   ⇒ `hmbird_sched_ops` 恒 NULL ⇒ `test_task_is_hmbird()` 恒 false（有 NULL 检查，安全）
   ⇒ sched_assist 的 hmbird 分支全走「非 hmbird」路径 ⇒ **等于纯 WALT + sched_assist**。
4. 这个形态**不是原厂 ROM 的配置**（原厂 ROM 上 sched_ext.ko 是工作着的），是我们自造的新配置；
   已知收益 = 去掉我们的 hmbird_sched_class 与我们的 iso 掩码；
   未知风险 = sched_assist/WALT 的 fair 钩子在我们内核上是否本来就正常（它们现在也在跑）。
