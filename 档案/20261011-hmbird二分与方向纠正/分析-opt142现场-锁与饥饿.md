  _audit/scx_vendor.ko（设备模块，87840B）、vendor-src/vendor-sched_ext/、vendor-src/kernel-walt/

## 0. 三问三答（TL;DR）

**Q1 谁把 governor 切成 scx_gov？—— 没有任何一步。**
全内核树只有一处写 scaling_governor：`store_scaling_governor()`，出现在 **hmbird.c:4445**，位于
`hmbird_err_exit_workfn()`（hmbird.c:4429-4453）——那是**恢复** `saved_gov[cpu]` 的路径，不是切换。
树内没有任何 `cpufreq_register_governor("scx_gov")`（唯一的注册是 `cpufreq_uag_gov`，
kernel/oplus_cpu/uad/cpufreq_uag_main.c:2830）。模块在 **30.5s** 打印的 `[scx_gov][scx_cpufreq_init]`
是**注册**（`cpufreq_register_governor`）发生在**模块 init**，比 enable（60.55s）早 30 秒；注册 ≠ 选中。
⇒ 选中 scx_gov 的只能是**用户态**（fengchi-gov.sh / ROM 默认），而 **t142.sh 从头到尾没有记录 governor**
（它的 knobs() 只读 p_ctrl/iso/iso_free/wd/sw）⇒ captain 的「scx_enable 会切 governor」目前**没有证据**，必须先测。

**Q2 scx_gov 会卡在哪把锁？—— 模块自己的 `scx_irq_work()`：先锁住全部 8 个 rq 锁，再在持锁区内进 cpufreq。**
`vendor-src/vendor-sched_ext/cpufreq_scx_main.c:465-529`：
    479  cpumask_copy(&lock_cpus, cpu_possible_mask);
    481  for_each_cpu(cpu, &lock_cpus) {
    483      raw_spin_lock(&cpu_rq(cpu)->__lock);          <-- 全部 rq 锁同时持有
    485      raw_spin_lock_nested(&cpu_rq(cpu)->__lock, level);
    ...
    512      scx_gov_update_cpufreq(policy, prev_runnable_sum);  <-- 持锁进 cpufreq！
    515  spin_lock_irqsave(&new_sched_ravg_window_lock, flags);
    525  for_each_cpu(cpu, &lock_cpus) raw_spin_unlock(&cpu_rq(cpu)->__lock);
`scx_gov_update_cpufreq` 在设备模块里是**导出函数**（scx_vendor.ko `T scx_gov_update_cpufreq` @0x80），
最终到 `__cpufreq_driver_target`（模块导入表 `U __cpufreq_driver_target`）→ policy->rwsem + 固件/SMC。
**触发者是模块自己的窗口滚动**：`scx_util_track.c:505-523 scx_window_rollover_run_once()`（与我们 opt141 删掉的
`slim_walt_window_rollover_run_once()` 是**孪生代码**，连 `atomic64_cmpxchg` 门都一样）→ `:518 run_scx_irq_work_rollover()`
→ `cpufreq_scx_main.c:129-132` 排队 `scx_cpufreq_irq_work`。⇒ **与 governor 无关**，由 WALT 的任务事件钩子驱动
（模块导入 `U register_walt_ops`、`U walt_rq`、`U sched_ravg_window`、`U waltgov_cb_data`）。

**Q3 ux_page_pool_fi 为什么饿死 58s？—— 不是 `pick_next_task_hmbird` 找不到它，是被全系统停摆连累。**
它是内核线程，进的是**内置 DSQ**（见 §3 的 id 解码），消费者是 `balance_hmbird()`→`consume_*_dsq()`；
而现场所有 hung task 都卡在 `__scm_smc_call`/mutex/rwsem，**没有一条在调度器里**（captain 已核）⇒
CPU 根本进不了调度路径（全 rq 锁被模块的 `scx_irq_work` 持住 + cpufreq/SMC 很慢）⇒ 没有 CPU 去消费 DSQ。
58s 后 hmbird 自己的 watchdog 走 `HMBIRD_FATAL_INFO_FN`（hmbird.c:327-336）→ `queue_work(hmbird_err_exit_work)`
→ disable，日志 121.858 的 `slim_walt_enable(0) from kthread_worker_fn+0x110/0x278` 就是它。

## 2. Q1 详证：governor 是谁切的

1. 树内写 governor 的**唯一**位置：`hmbird.c:4443-4448`（`hmbird_err_exit_workfn`）
   `if (strlen(saved_gov[cpu])) WARN_ON(store_scaling_governor(policy, saved_gov[cpu], ...) <= 0);`
   —— 恢复路径。`saved_gov[]` 由 `hmbird_sched_proc.c:210`（`show_scaling_governor`）在 proc 写 "save_gov" 时保存。
2. 树内 governor 注册：只有 `cpufreq_uag_gov`（kernel/oplus_cpu/uad/cpufreq_uag_main.c:2830）。
3. 设备模块 `scx_vendor.ko`（= oplus_bsp_sched_ext）字符串里**没有** `HMBIRD_GKI`/`HMBIRD_OGKI`/`version_type`
   ⇒ 它的 init **不是** vendor-src/vendor-sched_ext/main.c:17-26 那个按版本分派的版本（或分派被编译掉）
   ⇒ 它在 **30.5s 无条件注册** scx_gov（`U cpufreq_register_governor` 是导入符号）。
4. 模块的 `scx_enable_proc_write`（vendor main.c:101-110）**只存值**，不碰 cpufreq。
5. `/proc/hmbird_sched/scx_gov_ctrl` 在**两边都存在**：我们 hmbird_sched_proc.c:513-516（默认 1）、模块 vendor main.c:368-371（它自己的副本）
   ⇒ 与两份 `slim_walt_ctrl` 同理，**proc 路径重名，后注册者失败** ⇒ 我们的写入可能到不了模块。

⇒ **结论**：没有内核/模块代码在 enable 时切 governor。要在 opt142 的现场下结论，必须先记录：
`for p in 0 2 5 7; do cat /sys/devices/system/cpu/cpufreq/policy$p/scaling_governor; done`（pre/post 各一次）。

## 3. Q3 详证：为什么是「全系统停摆」而不是「DSQ 没人消费」

**(a) 那条 watchdog 行的解码**
- `type(4)` = `HMBIRD_EXIT_ERROR_STALL`（include/linux/sched/hmbird.h:94-101：PROC=0, ERR_WDT=1, ERR_HB=2, ERR_DSQ=3, **EXIT_ERROR_STALL=4**）；
  格式来自 `hmbird.c:327-336 HMBIRD_FATAL_INFO_FN` → `hmbird_err(HMBIRD_OPS_ERR, "type(%d) %s\n", ...)`。
- `dsq=9223372036` 是**被截断的值**：`HMBIRD_DSQ_FLAG_BUILTIN = 1LLU<<63 = 9223372036854775808`（hmbird.h:84），
  任何内置 DSQ 的 id 都以 `9223372036` 开头；而 `kernel/sched/hmbird/hmbird_trace.h:15 #define MAX_FATAL_INFO (64)`
  让 `scnprintf(buf, 64, ...)` 只写 63 字符 —— 实测这一行正好 **63 字符**，`mask=` 字段整段丢失。
  ⇒ 从日志**无法**判断它是 `gdsqs[i]`、`pcp_ldsq[cpu]` 还是 `HMBIRD_DSQ_LOCAL`。
  **一行修复**：把 `MAX_FATAL_INFO` 提到 128（trace.h:37/44 的数组同步变大），或把 `dsq=`/`mask=` 前移。

**(b) 它进哪个类 / 谁会消费它**
- 任务名 `ux_page_pool_fi`（截断自 ux_page_pool_fi...）是内核线程；`find_idx_from_task()`（hmbird.c:776-830 区段）决定 DSQ：
  `nr_cpus_allowed==1 || is_migration_disabled` ⇒ **PCP DSQ**（`pcp_ldsq[cpu]`）；
  `is_critical_system_task`（prio<50 且 sp_dl<LEVEL3）⇒ `SCHED_PROP_DEADLINE_LEVEL0`；
  RT ⇒ LEVEL3；否则 cgroup 表 / `DEFAULT_CGROUP_DL_IDX(=8)`（hmbird.h:291-292）。
- 消费者是 `balance_hmbird()`→`balance_one()`→`consume_*_dsq()`（另外 core.c:6203-6206 的 Stage BN 兜底也会调它）。
- **只要没有任何 CPU 走到 `pick_next_task`/`balance_hmbird`，DSQ 就没有消费者** —— 而这正是「全 rq 锁被模块持住 + SMC 慢」的结果。

**(c) 现场证据（支持「停摆」而非「调度器 bug」）**
- dmesg 18505-18648 的 hung task 栈**全部**在 `__scm_smc_call`/`mutex_lock`/`down_read`（captain 已核，我抽查一致）：
  `kworker/u16:2 → qcom_scm_dcvs_reset → __scm_smc_call → mutex_lock`；`TP:2151_2 → max_freq_show → mutex_lock`（cpufreq sysfs！）
  ⇒ **cpufreq 的锁（policy->rwsem / 调速器 work_lock）被长期持有**，而唯一「持 rq 锁进 cpufreq」的代码就是模块的 `scx_irq_work`。
- `blocked=0`（没有 D 状态堆积）、`waltbug=0`、`psi=0` ⇒ 不是我们已知的那几种故障。
- 58s 后是 **hmbird 自己的 watchdog 主动禁用**（不是 panic、不是复位）⇒ 与 t142.log 里 `dis=1` 一致。

## 4. 对 captain 二分实验的修正（重要）

原判据：「切回 uag 后稳定 ⇒ 元凶是 scx_gov」。**需要细化**，因为切走 scx_gov 会做两件事、不做两件事：
- 会：① governor stop 把 `gov_flag[cluster_id]` 置 0（cpufreq_scx_main.c:1014），于是 `scx_irq_work` 里的 cpufreq 段被跳过（495 的 `if (gov_flag[...] == 0) continue;`）；
  ② 不再注册 `scxgov_update_freq`（986 `waltgov_add_callback`）。
- **不会**：① 停止 `scx_irq_work` 本身（它由 `scx_window_rollover_run_once` 排队，不由 governor 排队）；
  ② 停止「同时锁住 8 把 rq 锁」这件事（481-487 无条件执行）。

⇒ **修正后的判据**：
- 切回 uag 后**稳定** ⇒ 元凶是**模块的 cpufreq-in-rq-locks 路径**（512 → `__cpufreq_driver_target` → SMC）；
- 切回 uag 后**仍挂** ⇒ 元凶是**「全 rq 锁窗口」本身**（或另有其人），governor 无罪。

**更省事的替代实验（如果允许）**：先确认 **`walt_disabled`** 的值。整条链的起点是 WALT 的任务事件钩子
（模块导入 `register_walt_ops`，`scx_update_task_ravg` 由 WALT 调）⇒ **`walt_disabled == 1` 时模块的 rollover 根本不触发，整条链不成立**。
这条比切 governor 更接近根，而且零风险。

### 设备侧最该做的 5 个检查（按决定性排序）
1. `ls /proc/device-tree/soc/ | grep -i hmbird` + `cat /proc/device-tree/soc/oplus,hmbird/version_type/type`
   —— 决定 **sched_walt.ko 与 oplus_bsp_sched_ext.ko 各自那份 header 的门**（若节点存在且 type=HMBIRD_OGKI ⇒ `init_hmbird_rq_wrq_variables()` 会填 util 指针！）
2. `walt_disabled` 的值（决定模块 rollover 链是否触发）
3. `cat /sys/devices/system/cpu/cpufreq/policy*/scaling_governor`（pre/post 各一次；t142.sh 缺这项）
4. `grep -c scx_gov_ctrl /proc/kallsyms`（是否两份、谁是 B/b ⇒ 我们的 proc 写能否到达模块）
5. `dmesg | grep -A2 "failed to run for"` 的完整行（修 `MAX_FATAL_INFO` 后再取）

## 5. 与 t1/t2 结论的关系（订正）

- **t1 §4.2(i)**（partial 消费者消失 ⇒ 滞留 ⇒ running 暴增）：**降级为次要**。opt142 已经把 partial 全关，仍然出现 58s 饥饿，
  且现场没有一条 hung task 在调度器里 ⇒ 饥饿是「全系统停摆」的下游现象，不是 DSQ 消费逻辑本身。
  （但 R1/R2 的 partial 安全化仍然值得做，见 t2 §4——它解决的是另一类风险。）
- **t1 C1**（ROM WALT 的 tick LB 未被绕过）与本次 Q2 链条**同源**（都由 ROM WALT 驱动），但 Q2 更贴近证据（cpufreq 锁 + SMC 现场）。
  ⇒ opt144 之后若仍挂，**下一个该测的是 ROM 侧的 util/rollover 链**（`scx_window_rollover_run_once` → `scx_irq_work`），其开关在 `walt_disabled`。
- **t2 附录 A**（android_vh_get_util 可作 util 源）：与本次结论不冲突；但要注意模块的 util 记账链（`scx_util_track.c`）**本身就是那条会锁 8 把 rq 锁的链**，
  所以「让模块继续做 util」在稳定性上是有代价的。
