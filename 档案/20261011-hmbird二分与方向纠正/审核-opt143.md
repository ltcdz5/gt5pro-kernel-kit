## Q1 守卫条件是否正确？会不会在合法场景误杀？

**结论：条件正确、不误杀、也不漏记账；但正因为"永远为真"，它是 no-op。**

### 1.1 语法与短路顺序（`hmbird_util_track.c:501`）

```c
if (!slim_walt_ctrl || !p || p->sched_class != &hmbird_sched_class)
        return;
```
`!p` 在解引用之前，短路顺序正确；`hmbird_sched_class` 是 `DEFINE_SCHED_CLASS(hmbird)` 定义的对象（`hmbird.c:3937`），
比较的是**同一个对象地址**（`p->sched_class = &hmbird_sched_class` 的赋值点：`core.c:4883`、`core.c:7279`、`hmbird.c:4049/4053`；另 `hmbird.c:3515` 是 entity 的字段）。
⇒ **语义正确，不存在"本机任务挂在 fair 类上"导致的误伤**（依赖说明里的那个担心可以排除：`hmbird.c:4049/4053` 与 `core.c:4883/7279` 四处都显式赋值）。

### 1.2 四个活调用点收到的**必然**是 hmbird 类任务（关键）

`hmbird_update_task_ravg()` 的全部调用者（`git grep hmbird_update_task_ravg` @ e2ec8157c870）：

| 调用点 | 所在函数 | 为什么必然是 hmbird 类任务 |
|---|---|---|
| `hmbird.c:2437` | `dequeue_task_hmbird()` | 经 `hmbird.c:3939` `.dequeue_task` 注册，由 core 按 `p->sched_class->dequeue_task` 分派 |
| `hmbird.c:2893` | `set_next_task_hmbird()` | `hmbird.c:3948` `.set_next_task`，同上分派 |
| `hmbird.c:2924` | `put_prev_task_hmbird()` | `hmbird.c:3947` `.put_prev_task`，同上分派 |
| `hmbird.c:3473` | `task_tick_hmbird()` | `hmbird.c:3955` `.task_tick`；`core.c:5794 scheduler_tick()` 里是 `curr->sched_class->task_tick(rq, curr, 0)` ⇒ 只有 `curr` 属 hmbird 类才会进来 |
| `hmbird_util_track.c:552` | `slim_walt_irq_work()` | ★唯一会收到**任意类**任务的调用点（`rq->curr`）—— 但见 1.4：**不可达** |

⇒ 前四个调用点上 `p->sched_class == &hmbird_sched_class` **恒成立** ⇒ 守卫恒真 ⇒ **不改任何行为**。

### 1.3 切类过渡期（任务正在换类）会不会被误杀 / 漏记账？

**都不会。** 证据：
- `check_class_changed()`（`core.c:2307-2318`）在 `p->sched_class` **已被更新为新类**之后才被调用（`core.c:8077`），但它只调
  `prev_class->switched_from()` 与 `p->sched_class->switched_to()` —— **不调用 `dequeue_task`**，而 hmbird 的 `.switched_from` 根本没实现（`hmbird.c:3935` 注释："task_woken, switched_from: Unnecessary"）⇒ 过渡期不经过本函数。
- 切类时的 `dequeue_task()` 发生在 `__setscheduler` 改 `p->sched_class` **之前**（`__sched_setscheduler` 里先 `dequeue_task(rq,p,DEQUEUE_NOCLOCK)`，再 `check_class_changed` 于 `core.c:8077`）⇒ 那一刻 `p->sched_class` 仍是 hmbird，守卫通过。
- 新任务 fork 时（`core.c:4883`）只赋 `p->sched_class`，不调用 ravg 记账。
⇒ **不存在"过渡期被守卫跳过 ⇒ util 失真"的路径**；也就谈不上"漏记账"。

### 1.4 唯一真正会被守卫改变行为的路径是**死代码**

`hmbird_util_track.c:552` 的 `hmbird_update_task_ravg(rq->curr, rq, TASK_UPDATE, wc)` 传的是 `rq->curr`（可能是 fair/idle/rt 任务）——
**这正是假说所指的野指针场景**。但它在 `slim_walt_irq_work()` 里，而该 irq_work **在本树从未被排队**：
- `hmbird_slim_walt_irq_work` 是 `static`（`util_track.c:37`），本树只有两处引用：声明 `util_track.c:37` 与 `init_irq_work()` `util_track.c:607`；
- 全树 `git grep queue_irq_work` 只命中 `drivers/vdpa/...`（与调度无关）⇒ **没有 `irq_work_queue()`**；
- 这是 opt141 提交本身做的（"去掉 slim_walt_irq_work 的排队"），我上一轮已在 t5 独立复核过。

⇒ **opt143 与 opt141 在可达代码上行为等价**（守卫恒真 + 危险路径不可达）。

## Q3 这个实验能否验证"野指针"假说？opt143 稳定能否排除其它解释？

**不能验证。** 逐条回答任务里的两问：

1. **假说的前提不成立**。提交信息写"本函数被 task_tick / set_next / put_prev / dequeue 四条热路径对【任何任务】调用"——

   真正"对任何任务调用"的只有 irq_work 里的那一处，而它是死代码（1.4）。
   ⇒ **守卫对活代码恒真、零作用**；`opt143 ≡ opt141`。
2. **因此 opt143 的任何结果都不能归因于这个守卫**：
   - 若挂（按 opt141 的表现，大概率）⇒ 只说明"opt141 那条链没被这个守卫影响"，对野指针假说**零信息**；

   ⇒ 可当作**上机自检点**：8 核占用应仍是 `96 96 99 95 94 100 99 99`；**若观察到差异，说明本审核的"恒真"推断有误，请立刻回报**（那会是重要新证据）。
4. 若确实想测"非 hmbird 任务走到 ravg 记账"这个假说，正确的实验是**让危险调用点可达**（例如恢复 irq_work 排队）或**直接给 `get_hmbird_ts(p)` 的取用加判空**，而不是在恒真的分支上加守卫。

## R4 ★旁证核实（t12 提出、需要 captain 定案）：vermagic 矛盾 —— 这条影响 opt144 的立论基础★

t12 指出 `_audit/scx_vendor.ko` 的 vermagic 与我们内核不匹配。我独立复核并把它推到底：

| 项 | 值 | 来源 |
|---|---|---|
| 模块 vermagic | `6.1.141-android14-11-o-g5de16d278e6c SMP preempt mod_unload modversions aarch64` | `strings _audit/scx_vendor.ko`（我复核） |
| 我们内核 UTS_RELEASE | `6.1.141-android14-11-o-ltcdz5-v1.1-opt142` | `out-core/include/generated/utsrelease.h` |
| localversion 何时变成 ltcdz5 | **从第一个自定义内核起就是**（`git log -S ltcdz5 -- scripts/setlocalversion` → `372750608ecd GT5 Pro: ... opt1/opt2 ...`） | git |
| vermagic 检查是否被改 | **没有**：`kernel/module/main.c:1997-2010` 是标准 `check_modinfo()`（`same_magic()` 不等就 `-ENOEXEC`）；`git log -S vermagic -- kernel/module/main.c` 只有一条无关 revert | git |
| 是否允许强载 | `out-core/.config:816 # CONFIG_MODULE_FORCE_LOAD is not set` ⇒ `try_to_force_load()` 会失败 | .config |

⇒ **这份 `scx_vendor.ko` 无法载入我们任何一版内核（opt1…opt142 全部是 ltcdz5 localversion）。**

⇒ 因此下面两者**不可能同时为真**：
- (A) 设备 `/proc/kallsyms` 里出现 `[sched_walt]` / `[oplus_bsp_sched_ext]` 符号（captain 提供）；
- (B) 那些符号来自 `_audit/scx_vendor.ko` 这份文件。

可能的解释（需要设备侧一条命令定案）：
1. kallsyms 是在**非我们的内核**（stock 引导，或刷我们镜像之前）上读的；或
2. 设备上真正加载的 `.ko` 与 `_audit` 这份**不是同一个文件**（provenance 不同）；或
3. 设备的模块加载路径做了我们没看到的旁路（但 `.config` 与 `check_modinfo` 都不支持）。

**为什么这条重要**：opt144（`core.c:5848` tick 守卫）的立论前提是"**ROM sched_walt.ko 注册了 `android_vh_scheduler_tick`**"。
若那份模块根本进不了我们的内核，则**这条前提是【证据不足】**，opt144 会变成又一个"守一个没有注册者的 hook"。
（顺带：HANDOFF 里 opt120 崩溃栈含 `[sched_walt]`，与"无法载入"同样矛盾 ⇒ 说明历史上某段时间它**确实**载入过，或者那条栈也来自 stock。两种可能必须用同一把尺子重新量。）

**一条设备侧命令即可定案（captain 执行，我不碰设备）**：
```
adb shell 'uname -r; cat /proc/version; lsmod | grep -E "sched_walt|oplus_bsp_sched_ext"; \
           cat /sys/module/oplus_bsp_sched_ext/vermagic 2>/dev/null; \
           dmesg | grep -iE "version magic|disagrees about version" | head'
# 再比对设备上真实文件与 _audit 副本：
adb shell 'md5sum /vendor/lib/modules/oplus_bsp_sched_ext.ko /vendor/lib/modules/sched_walt.ko'
```
若 `lsmod` 里没有这两个模块 ⇒ 结论 1 成立，**opt144 的前提必须重写**（先把"谁注册了 `android_vh_scheduler_tick`"用设备侧证据定下来）。
