# 研究结论：hmbird 启用即硬挂 —— 三条根因假说（2026-10-11 02:40）

来源：研究子代理（带 URL 引用的完整版见其会话）。本文件是**可执行的提炼版**。

## 0. 最重要的四条结论

1. **社区没有同款报告** —— 这不是"照抄补丁"能解决的问题，是我们这份移植自身的缺陷。
   但 **OnePlusOSS issue #21** 证实了 ABI 问题：出厂 `struct walt_rq` 是 **648 字节 / 40 成员**，
   比公开源码多 `curr_runnable_sum_fixed`(偏移152) 与 `prev_runnable_sum_fixed`(偏移160)。
2. **PSI 记账在 core 里做，不在 sched_class 里做。** 上游 `dequeue_task_scx` **没有任何 PSI 处理**。
   ⇒ "自定义 sched_class 需要补 PSI"这个方向是**错的**；正确方向是
   **"谁绕过了 core 的 enqueue/dequeue 配对，谁就制造了双计数"**。
3. **`slim_walt_ctrl` 不是可选调试开关** —— LSE（LunarKernel）原话：
   "启用 Slim WALT 负载跟踪，**别随便关不然没法调频**"。它是调频/负载链路的地基。
4. **`psi: inconsistent task state!` 每次开机只报一次**（`psi_bug` 是全局一次性开关），
   所以很容易被忽略。位定义：`TSK_RUNNING = 4`（v6.1）。
   - `psi_flags=4 clear=0 set=4` ⇒ **重复入队**
   - `psi_flags=0 clear=4 set=0` ⇒ **重复出队**
   **⇒ 抓到这一行的完整数值 = 零成本的黄金证据，直接判定方向。**

## ★根因 1（最可能）：`hmbird_update_task_ravg()` 对【非 hmbird 任务】解引用 `get_hmbird_ts(p)`

### 证据
```c
/* hmbird_util_track.c:466 起（厂商与我们同款） */
void hmbird_update_task_ravg(struct task_struct *p, struct rq *rq, int event, u64 wallclock)
{
        struct hmbird_sched_task_stats *sts = &(get_hmbird_ts(p)->sts);   /* ← 先解引用！ */
        struct hmbird_sched_rq_stats *srq = &per_cpu(hmbird_sched_rq_stats, cpu_of(rq));
        u64 old_window_start;

        if (!slim_walt_ctrl)        /* ← 开关判断在解引用【之后】 */
                return;
        ...
}
```
- 该函数被 **4 条调度热路径**调用（task_tick / set_next / put_prev / dequeue），
  而这些路径**对任何任务都生效**（不只 hmbird 类任务）。
- **厂商自己在别处是按 class 保护的** —— `vendor-src/kernel-hdr/hmbird.h:335`：
  ```c
  return (p->sched_class == &hmbird_sched_class) ? get_hmbird_ts(p)->sts.demand_scaled : 0;
  ```
  ⇒ 说明"非 hmbird 任务没有有效的 hmbird 实体"是**厂商自己的前提**。
  同一个访问器，一处有 class 保护、热路径处没有。
- **症状完全吻合**：往野指针写 ⇒ 立即硬挂、**无 panic、无转储、硬件看门狗无声复位**；
  且"关掉 `slim_walt_ctrl` 就稳定"（整条路径被关掉）。

### 验证（改动最小、最先做）
把 `hmbird_update_task_ravg()` 开头改成：
```c
if (!slim_walt_ctrl || !p || p->sched_class != &hmbird_sched_class)
        return;
/* get_hmbird_ts(p) 必须在上面判断【之后】才求值 */
```
判据：`slim_walt_ctrl=1` + 满载 10 分钟不挂，且 `procs_running` 稳定在 1~4。

## ★根因 2（很可能）：`rq->nr_running` 泄漏/双计数 → 负载均衡正反馈 → 挂死

### 证据
```c
/* ext.c:1749-1757 入队 */
if (test_bit(SCX_TASK_QUEUED, &p->scx->flags)) { WARN_ON_ONCE(...); return; }  /* 已置位就返回 */
set_bit(SCX_TASK_QUEUED, ...); add_nr_running(rq, 1);

/* ext.c:1810-1828 出队 */
if (!test_bit(SCX_TASK_QUEUED, &p->scx->flags)) { WARN_ON_ONCE(...); return; } /* 未置位就返回 */
clear_bit(...); sub_nr_running(rq, 1);
```
逻辑本身对称，**但完全依赖 `SCX_TASK_QUEUED` 这一个 bit 的一致性**。
任何一条路径在这个 bit 之外改变任务状态，就会"加了 1 却减不掉" ⇒ **永久泄漏**。

而厂商 WALT 的负载均衡**两个保护都没有**：
```c
/* walt_lb.c _walt_can_migrate_task()：没有 task_on_rq_queued()，没有 sched_class 判断 */
/* walt_detach_task(): deactivate_task(src_rq, p, 0);      ← flags=0 ⇒ on_rq = TASK_ON_RQ_MIGRATING */
/* walt_attach_task(): activate_task(rq, p, 0);            ← core 的 activate_task() 无 on_rq 保护 */
/* 而且 detach 与 attach 之间【放开了 rq 锁】—— 窗口里若发生唤醒就会双入队 */
```

### 现象吻合
- `procs_running` 从 1~3 **暴增到 48** ⇒ `nr_running` 被**虚增**，不是真有 48 个任务
- `nr_running` 同时是负载均衡的输入 ⇒ 形成正反馈：
  ```
  虚高 → 被判"最忙" → 反复 pull → 每次 pull 又可能多计一次 → 更高 → ... → 48 → LB 风暴
       → PSI 记账彻底错乱（那条告警）→ 最终死锁/硬挂
  ```
- 上游对同类失败模式的定性：**"任务分布被搞歪 → 队列排不空 → RCU stall / hung task"**

### 验证
1. 在 `_walt_can_migrate_task()` 开头加
   `if (!task_on_rq_queued(p) || p->sched_class != &fair_sched_class) return false;`
2. 在 `dequeue_task_scx` 的 early-return 分支打点，看是否有任务在 `SCX_TASK_QUEUED` 已清时被 dequeue
3. 打点 `add_nr_running/sub_nr_running` 的净变化，确认 `Σ rq->nr_running` 是否单调上升
4. 交叉证据：抓 PSI 那行的完整数值（`set=4` ⇒ 双入队）

## 根因 3（已被部分排除，但同类缺陷要再审计）：持全部 rq 锁 / 跨 CPU 加锁顺序

- `slim_walt_irq_work()` 在 hard-IRQ 上下文按 CPU 升序**一次性持全部 rq 锁**，
  与 `double_lock_balance`（先 busiest 再 this_rq）不构成全序 ⇒ AB-BA 可能
- 但 **opt141 已经不再排队它，却仍然"开启后立刻硬挂"** ⇒ **它不是当前这版的直接原因**，排第三

## 建议的实验顺序（研究子代理给的，比我们的更准）

| 顺序 | 实验 | 判据 |
|---|---|---|
| **0** | **先抓 PSI 那行的完整数值** | `clear=`/`set=` 直接判定双入队还是双出队，零成本 |
| **1** | **`get_hmbird_ts(p)` 加 `sched_class` 保护 + 把解引用挪到开关判断之后** | 改动最小、最可能一击命中 |
| 2 | `slim_walt_ctrl=1` 但 `get_cpus_max_util()` 返回常量（= 我们的 opt142） | 区分 tracking vs rescue |
| 3 | `set_partial_rescue()`/`free_isocpu()` 只打印（= 我们的 opt143） | rescue 路径 |
| 4 | `slim_walt_ctrl=0` 但保留掩码修正 | 验证掩码修正本身 |
| 5 | 在 `walt_detach_task()/walt_attach_task()` 前后加 `WARN_ON_ONCE` | 直接验证根因 2 |

## 取证手段（无 ftrace/kprobe/lockdep 时）

**第一优先级不是"观测"，而是"把静默挂变成有转储的 panic"**：
- `hardlockup_panic=1` / `softlockup_panic=1` / `hung_task_panic=1` / `watchdog_thresh=10`
- 确认 `CONFIG_PSTORE_RAM` 且 DT 有 ramoops 节点
- **hmbird 自带 minidump 设施**（`hmbird_ogki__scx_minidump.c`），接上比自造打点省事
- 用 `printk_deferred` 而不是 `printk`（调度器上下文里 printk 有锁风险）
- SysRq：`echo 1 > /proc/sys/kernel/sysrq` 后 D/T/W/L/M
- `/proc/sched_debug`（若开 CONFIG_SCHED_DEBUG）：`nr_running` / `cfs.h_nr_running` / `scx.nr_running` 三者不一致本身就是证据
- 缩小战场：`maxcpus=1` 或 `nr_cpus=2` 启动，若单核不挂则锁定跨 CPU 锁序类缺陷
