## 三砖机制（已结案，别再复现）

**凶手＝新增一行 `EXPORT_SYMBOL_GPL(test_task_ux)`。**

链条：新增导出 ⇒ 12 个厂商 `.ko` 里原本"符号取不到就走 weak-NULL 跳过"的分支，翻成**真调用** ⇒ 内核活锁 ⇒ PMIC 硬复位 ⇒ **pstore 零留痕**（所以看起来像"无缘无故重启/黑屏"）。

由此得到的闸门（唯一有效的静态闸）：

```
新增导出 ∩ 厂商 .ko 引用名  ==  空集
消失导出 ∩ 厂商 .ko 引用名  ==  空集      （符号消失同样致命）
```

- 基准文件：`kernel-kit/vendor-ko-symbols.txt`（199,295 个名字，由 `tools/rebuild_vko_baseline.sh` 从设备 `/vendor_dlkm` 重生成）
- 执行器：`tools/gate_new_exports.py`，回验 5/5（砖版全部拦下、能开版全部放行）
- 配套规则：**不新增导出 + 闭包裁剪**（搬上游补丁时，需要的符号必须已在本机导出集内；子串匹配，别用词边界）

3. **输入缺失 fail-open** —— 实测：不传参数 / **0 字节候选** / 截断候选，**三种都输出 PASS、rc=0**。

**⇒ 出件前必做**：补 `gone = base - cand`；基准换 vmlinux-only 且每版落盘；无参数/空文件 `exit 2`；所有调用点传候选 + 去 `| tail` + `|| exit 1`。

## 静态判定的边界（重要：别高估闸门）

- `verify_image.sh` 20 项全绿 **≠ 能开机**。opt6 / -a / -a2 三个版本闸门全绿，刷进去全部循环开机。
- BTF 全类型比对也判不出来：裸 Image 抠出的 BTF 全类型 153,099 行，**砖版与能开版差 0 行**。
- 编译器版本、config 差集、符号 CRC 都属"构建/内容层"，**运行时正确性只认真机**。
- ⇒ 所以流程固定为：**过闸 → `fastboot boot` RAM 引导（零写入）验运行时 → 才写真刷**。

## "改动进没进本机"的判据

**唯一判据：`ar t out/vmlinux.a` 里有该成员。**

- `out/.../<name>.o` 存在只证明**编过**；
- `=m` 的文件编成 `.ko`，而**只刷 boot_a 带不走 `.ko`** ⇒ 等于没进；
- 本机不编的文件（依赖的 config 没开）也不算；
- ⚠️ `ar` 传绝对路径时成员打印成**全路径** ⇒ 归一化要按 `/out/` 切；切错会得出"0 个进镜像"的假结论。

按这条重算后，名义文件数全线下修：opt9 13→8、opt10 10→7、opt11 6→4、opt12 115→97；28 个"白改"文件已退回基线（提交 `d9a3e7eab`）。

## ⭐ "这段代码本机走不走得到"的**三条判据**（缺一不可，2026-10-03 补齐第三条）

判一个缺陷/改动**值不值得做**，必须三条同时成立：

1. **`out/.config` 里那个开关是开的**
2. **`out/` 下有对应的 `.o`**（且调用点没被 `#ifdef` 排除）
3. **★ 用户态真的有那个工具、并且真的在用它** ← 2026-10-03 新增

### 为什么必须有第三条
- **先例 1（第 2 条）**：`mm/cont_pte_hugepage.c`（94 KB、被 `mm/vmscan.c` 引用）
  因 `CONFIG_CONT_PTE_HUGEPAGE=n` ⇒ **根本没编**，是死文件。
- **先例 2（第 3 条）**：`CONFIG_IP_SET=y` 且 netfilter 编入 117 个 `.o`（含全部 `ip_set_*`），
  但 `/system/bin/ipset`、`/vendor/bin/ipset` **都不存在**、`/proc/net/ip_set` 不存在、
  **`/proc/slabinfo` 里没有 `ip_set` 对象（从未分配过）** ⇒ **用户态从不用它**。
  ⇒ 针对 ipset 的修复（如 CVE-2026-64189 的 dump UAF）**代码是真的、修法是对的，但永远不被触发**。

⇒ **"编了" 和 "有人用" 是两件独立的事。**

### 第三条怎么查（照抄）
```sh
ls /system/bin/<tool> /vendor/bin/<tool> /system_ext/bin/<tool> /odm/bin/<tool>   # 工具在不在
ls /proc/<对应节点>                                   # 例 /proc/net/ip_set
grep -i '<对象名>' /proc/slabinfo                     # 对象从未分配 ⇒ 从未用过
ps -A | grep <相关进程>
cat /proc/sys/net/netfilter/nf_conntrack_count        # 例：535 条 ⇒ conntrack 真在用
```
**本机已确认"真在用"的**：conntrack（535 条）、TCP/SACK（28 条连接）、f2fs（`/data`）、
UFS、SSG、qcom_geni 串口、zram、binder、ashmem、dma-buf。
**已确认"装了但没人用"的**：**ipset**（无用户态工具、零 set）。

### ⚠️ 配套教训：`dmesg` 类计数必须在**刚开机**时采
opt37 记 `WARNING = 0`（运行 4h37m 后采，**环形缓冲已绕圈、开机日志已丢**），
opt38 记 `WARNING = 10`（开机 72 秒采）⇒ **两次不可比**。
⇒ 要比较就**都刚开机采**；晚采会得到**假 0**。
📌 基线（2026-10-03 17:0x）：`WARNING = 10`（proc_register 重名 7 + sysfs 重名 1 + eBPF 提示 1，全属厂商模块，非我们引入）

## "要不要重刷"的判据

退掉**没进镜像**的文件后，若代码本身未变 ⇒ **不用重刷**。证法（三条同时成立）：

1. 重编后 `System.map` 差 **0 行**；
2. Image **同尺寸**；
3. 字节差只有 **32 处**，且逐处身份可定：banner 6 + `UTS_VERSION` 6 + ELF build-id 20（`GNU\0` + SHA-1，紧挨 BTF magic `9f eb 01 00`）。BTF 头三字段相同 ⇒ 布局未动。

⚠️ 重编产物 md5 变了 ≠ 代码变了。必须用 `cmp -l` + 按块 `strings` 给每个差异字节定身份，不能靠"我觉得没链接进去"。

## ABI / 兼容性已知事实

- `struct eventpoll` **192→216**（多了 `callback_head rcu`）：相对原厂是真实布局变化。判低风险的理由：它定义在 `fs/eventpoll.c` 内部、对外不透明，且厂商符号全集里 `eventpoll` 命中 0。⚠️ 但"opt9 ABI 同原厂"这个旧说法已作废。
- 厂商 `.ko` 的 `vermagic` 不阻止装载：本机横幅早已与原厂不同（含 `ltcdz5-optNN`），621 个厂商 `.ko` 全部正常装载 ⇒ 改 `LOCALVERSION` 不会因 vermagic 失败（但仍不建议，见"构建身份"）。
- 装载失败基线：`dmesg | grep "disagrees about version"` 应为 **5 条，全是 `bluetooth: … sk_filter_trim_cap`**（2026-10-02 在 P5/P11/P13/P16/P19 上多次实测；旧记录写 6 条，以 5 为准）。蓝牙功能实测正常（走厂商用户态栈）⇒ **不修**。非蓝牙装载失败必须为 0。
- `oplus_bsp_sched_ext.ko`（原厂 hmbird/风驰真身）需 126 符号缺 19，`register_hmbird_sched_ops` 只能由内核导出提供 ⇒ 正面撞砖闸 ⇒ **原厂 scx/风驰搬不回来**（三条独立死证，见 `gt5pro-scx-hmbird-verdict`）。

- ⛔⛔ **"原厂 config"只有一个真件：`refs/stock_config.gz`。**
  `（他人内核 config 原件·已移入非本项目归档·见规范 §八）` **不是原厂** —— 它是**第三方 cctv18 内核**的 config

  真原厂的证据：`CONFIG_HMBIRD_SCHED=y`、`CLANG_VERSION=170002`（clang 17.0.2、`-mlgo`）、
  `UNUSED_KSYMS_WHITELIST="/work/000f/workspace/Build_S_Vendor/…"`（OEM 构建路径）。
  差异规模：**我们 vs 真原厂 = 93 行；我们 vs cctv18 = 82 行**。
  ⇒ 凡写"与原厂全同/不同"的结论，**必须注明参照物是哪一份**；
  此前"133 项开销 config 与原厂全同（无白捡）"就是**拿 cctv18 当原厂**比出来的，已作废。
- ⛔ **config 改动必须三处同写**：`out/.config` + `arch/arm64/configs/gki_defconfig` + `my_opts.conf`。
  理由：`builder_6.1.141.sh` 走 `make … gki_defconfig all`，而 `build_opt*.sh` 走 `cp $BASE/config out/.config`
  ⇒ **两个真值源已不一致**（实例：`SLAB_MERGE_DEFAULT` 在 `gki_defconfig` 是 `n`、在 `out/.config` 是 `y`）。
  **只写一处 = 下次重跑就丢** —— "减脂三项"丢失 2 项就是这么发生的（详见 `更改` 记录与
  `kernel-kit/更正-MGLRU与减脂三项-20261003.md`）。
- config 一律以**上一版实测 `out/.config`** 走 `olddefconfig`；⛔ 不要信 `defconfig`（构建脚本会反复 append，`gki_defconfig` 曾堆到 859 行、31 个重复键，已清到 826/0）。
- `olddefconfig` 会**静默丢掉**树里没有的符号（如 `OPLUS_FEATURE_SCHED_DDL`）⇒ 别以为写了就生效。
- 查内核语义**先读树内 `Documentation/*.rj`/`Kconfig` help**，网页搜索只给内容农场；`WebFetch` 甚至可能返回域名不符的假出处。
- 构建身份不用新增机制：`include/generated/compile.h` 的 `UTS_VERSION` 随 `linux_banner` 编译期内嵌进 Image，`uname -a` 免 root 可读，`#N` 在同一 localversion 下单调递增 ⇒ 兼作"改了到底重编没有"的对照面。⛔ 别用 `KBUILD_BUILD_TIMESTAMP` 钉死时间（同秒两次构建字节相同 ⇒ 抢走 build-id 差异源）。

## 判"有没有压力"的纪律

⛔ **不许用 `MemAvailable` 瞬时快照**。Android 上可用内存高，正是回收/换出/杀后台**维持出来的结果**。
改用累积量 + `/proc/uptime` 换算每秒：PSI（`/proc/pressure/memory` 的 some/full）、`pgscan_direct` 占 `pgscan_kswapd` 比例、`allocstall_normal`、`pgmajfault`、`workingset_refault_{file,anon}`、`pswpin/out`。

 **sysfs 显示值要先读源码确认语义**：`/sys/kernel/mm/lru_gen/enabled` 是**能力位图**不是开关；debugfs 节点是 `late_initcall` 无条件建的（存在 ≠ 有人在用）。

⛔ **`/proc/sys/*` 的"生效值"≠"本软件造成的效应"**：那是运行时状态，换内核 Image 碰不到它。版本差异只有两种可能——编译期默认值、节点存在与否。所以**别把 `/proc/sys/vm/*` 现值（swappiness 150、watermark 50、page-cluster 0…）归因给内核版本**；要做同口径对照只能 `fastboot boot` 原厂件。

# ⭐⭐⭐ 2026-10-02 追加：两道 CRC 闸门才是装载判据的正主

> **下面 §三砖机制 里的导出集合闸门，看不见「符号还在、CRC 变了」这种情况。**
> opt15 就是这么翻车的：闸门全绿（新��=0、消失=0），刷进去 **9 个模块挂掉、
> `lsmod` 621→607、WiFi/蓝牙/网络加速全废**。
> **⇒ 导出集合闸门只是必要条件，不是充分条件。**

## 一、机理（`CONFIG_MODVERSIONS=y`）

`kernel/module/version.c:80 same_magic()`：模块带 `__versions` 段时，
**跳过第一个空格之前的部分** ⇒ **vermagic 里的内核版本串被完全忽略**
（所以改 `LOCALVERSION` 不会导致拒载）。真正决定能不能装载的是：

```
模块 __versions 里的 CRC  ==  内核 __kcrctab 里同名符号的 CRC   ?   相等才装载
```

而 **genksyms 的 CRC 只由「声明」算出**：

| 改什么 | CRC 动不动 |
|---|---|
| 函数体 | **不动** |
| 头文件里被导出原型引用到的任何类型 | **动** |
| 编译选项 / 优化等级 | **不动** |

`__versions` 条目 = **64 字节**：`u32 crc`(LE) + 4 字节填充 + `char name[56]`。

## 二、**两道闸门（每次刷机前必跑，缺一不可）**

| 工具 | 判据 | 覆盖能力 |
|---|---|---|
| `tools/gate_new_exports.py` | 导出集合：新增 ∩ **真厂商引用名**、**消失** ∩ 真厂商引用名 | ⚠️ 只抓"符号增减"，**抓不到 CRC 漂移**；基准见 §五 |
| **`tools/gate_vko_crc.py`** | **真值**：解析 493 个厂商 `.ko` 的 `__versions`，逐符号比 CRC | ✅ **这才是装载判据**（4 次真救场全部是它拦下的） |
| `tools/gate_crc_drift.py` | 本地预警：候选 CRC vs 能开机基准 ∩ 旧 `vko_syms.txt` | ⚠️ 旧名表 98% 噪声，**只当预警，不可作判据** |

**⛔ 闸门1 的权威基准是 `vko_syms_real.txt`（4754 条，真 ELF 解析）**，
不是 `vko_syms.txt`（199295 条，`strings` 转储）—— 详见下面 **§五**（这是 2026-10-03 修正的一处**根本性错误**）。

**闸门1 判据**（2026-10-03 权威口径，机主确认）：

```
闸门1 PASS  ⟺  vmlinux.symvers 的导出集差异 ∩ 厂商 .ko 引用名集合 = ∅
              即：命中厂商  新增=0  且  消失=0
```

- `新增=N 消失=M` 是**导出集差值的原始计数，不要求为 0** —— 内核导出集本来就会变
  （上游加 tracepoint / 加导出 / 删没人用的导出）；**只有"被厂商 `.ko` 引用的名字"出现在差异里才会出砖**。
  ⇒ 判据是**交集**，不是原始计数。
- ⚠️ 早期文档写的"**新增=0 消失=0**"是 `gate_new_exports.py` **早期版本的严格模式**
  （要求导出集完全不变，只对**未动导出集的 opt5 基线**成立），对后续版本**过于严格且会误报**，**已作废**。
- **P28 实例**：`新增=50`（全是 tracepoint / `sm4_expandkey` / `xz_dec_microlzma_*` 之类）
  + `消失=1`（`ufshcd_dealloc_host`）—— 逐个比对厂商表**全不命中** ⇒ 正确判 **PASS**。

**通过标准（闸门2）**：`gate_vko_crc.py` 输出 `会拒绝装载的模块 = 1`，且那 1 个是
`system_dlkm/bluetooth.ko`（`sk_filter_trim_cap`，**基线就不符**）。
**任何大于 1 的数字都算不合规，一律不许刷。**

退出码：`0` = 通过 / `1` = 会挂模块 / `2` = 输入错误。
⚠️ **调用方必须传候选 `vmlinux.symvers`、必须看退出码、必须 `|| exit 1`**
（旧脚本 `gate_new_exports.py 2>&1 | tail -5` 不传参且不看 rc，那是空过）。

# 补丁应用纪律（2026-10-02，两条都是踩过坑才写下的）

### 1. 必须按**提交日期**排序应用，不能按 sha

round 2 的 `classify.tsv` 是按 sha 排序的产物 ⇒ **补丁链被打乱** ⇒ 大量假冲突
（104 条 CONFLICT 里，真正需要人工解的只是其中一小部分）。
按 `committer date` 重排后，104 条里有 45 条能干净应用。

### 2. **成对改动必须成对应用，或成对放弃**

实测 stable 6.1.147 对一个 bug 的修复是**一对**：

```c
// kernel/sched/sched.h   :  unsigned int  nr_uninterruptible  ->  unsigned long
// kernel/sched/loadavg.c :  (int)this_rq->nr_uninterruptible  ->  (long)...
```

**只应用 `.c` 那半边**（`.h` 半边被我单独归进了"头文件池"）⇒
**`/proc/loadavg` 爆到 1.7e10 且持续上涨**（P13 事故，P16 修）。

定量指纹：`4 × (2^32 − 1) = 17179869180`，实测坏值 `17179868226`（只差 954）。
根因：`unsigned int` 存 −1 是 `0xFFFFFFFF`，`(int)` 截回 −1（正常），
`(long)` 变成 +4294967295（爆炸），四个 cluster 的 rq 合计 1.72e10。

**⇒ 症状 → 诊断的通用套路**：看到不可能的数值，先算「4 × (2^32−1)」这类
「N × (2^k − 1)」指纹，往往一步定位。

**⇒ 纪律：一条 `.c` 改动若上下文里出现「本树没有的类型/宏/函数」，
先怀疑它的 `.h` 半边被放进了另一个桶。**

# ⭐ 2026-10-02 深夜追加：头文件安不安全，看它在不在【导出表】里

**判据一句话**：头文件改动安不安全，**不看它是 inline 还是全局函数，看它在不在导出表里**。

- 只有进了 `__kcrctab`（即 `vmlinux.symvers` 里有该符号）的原型，genksyms 才会算 CRC；
  厂商 `.ko` 的 `__versions` 也只比对**它自己引用的那批符号**。
- 没进导出表的符号 ⇒ **不进 `__kcrctab`** ⇒ 对 493 个厂商模块**零影响**。

**实例**：`kernel/sched/sched.h` 的 `to_ratio` 从 `unsigned long` 改 `u64` ——
它是**普通全局函数**（不是 inline），看起来"改了中枢调度头、危险"，实际：

| 检查 | 结果 |
|---|---|
| `EXPORT_SYMBOL(to_ratio)` | **不存在** |
| `vmlinux.symvers` 全文 `to_ratio` | **0 命中** |
| ⇒ 进 `__kcrctab`？ | **否** ⇒ 对 493 个厂商模块**零影响** |
| arm64 上 `unsigned long` / `u64` | **都是 64 位** ⇒ 连二进制 ABI 都没变 |

⇒ **纪律**：想改一个头文件/结构体又拿不准，先做上面两查（有没有 `EXPORT_SYMBOL`、`vmlinux.symvers` 有没有命中），
再跑 `gate_vko_crc.py` 确认。**别拿"inline 与否"当判据 —— 那是错的判据。**

# ⛔ 应用与撤销的第三条纪律：整补丁原子性（2026-10-02 深夜）

### 1. "补丁打不上"有三种原因，处置完全不同

| 现象 | 原因 | 处置 |
|---|---|---|
| 上下文对不上 | **真冲突**（上游改了同一段） | 只能**人工**解 |
| 报缺类型/宏/函数，且正反都打不上 | **成对缺失**（另一半在别的桶里） | 补另一半（见上"成对改动"） |
| **反向能打**（`git apply -R --check` 通过） | **已经在了**（厂商早已 backport） | **什么都不做** ← 最常见，也最容易误判成"缺失" |

⇒ **判别顺序：先试反向。** 反向能打就是"已经在了"，这一步能省掉大批无用工。
⛔ 实测踩过：把"已经在了"误判成"缺失"，打上去就是语义重复（`dst.h` 966 个错误那类）。

### 2. 撤销必须按【提交】整组撤，**按文件撤是错的**

同文件的不同 hunk 来自**不同提交**，其中只有一部分依赖缺失的前置 ⇒ 按文件撤会误伤无关修复。

**实测**：撤 `9c22234529a8` 时，把 SSG 依赖的 `container_of_safe` 一起撤了 ⇒ **20 个错误**。

（历史同类事故：误撤 `945be0af8244` 的 posix-cpu-timers UAF。）

### 3. 按 `(sha, file)` 逐块应用会造成"半应用" ← 本轮 4 次构建破坏的共同根因

一个多文件补丁只应用了其中几个文件块 ⇒ 一半新一半旧。实测中招的四处：

- `kernel/sched/core.c` 应用了、`kernel/sched/sched.h` 没应用
- `net/packet/af_packet.c` 应用了、`net/packet/internal.h` 没应用
- `diag.c` 漏改
- 另有 11 个其它块

**修法（必做）**：对每个多文件补丁做**"整补丁原子性检查"**——
列出该提交改的全部文件块，检查是否"部分文件已应用 + 部分未应用"；
一旦出现 ⇒ **必须补齐，或整体回退**，不许留在半应用状态。

### 4. 新失败模式：**补丁的 context 行被当成新增行插进来**（P28 实测）

**判据（一句话）**：**只有 `+` 行允许"出现在本树"；context 行必须"本树早已有"。**

- 打完一个 hunk 后，逐条检查它的 **context（空格前缀）行**：这些行在打之前就应存在于目标文件里；
  如果某条 context 行是"打完才第一次出现"的 ⇒ **打歪了**（内容被重复插入）。
- **实测（P28 第 3 轮，hunk 级回退）**：`drivers/usb/gadget/udc/core.c` **删掉 1 行** 即修好。
  ⇒ 只回退这一个 hunk，**没有整文件撤**（整文件撤会误伤同文件的其它提交，见 §2）。

⇒ 与 §3 合起来的完整做法：**逐块应用 → 整补丁原子性检查 → 只 `+` 行校验 → 失败只做 hunk 级回退**。

### ⚠️ 导出表判据的**两个方向**（补实例）

| 符号 | 位置 | 在导出表？ | 结论 |
|---|---|---|---|
| `to_ratio` | `kernel/sched/sched.h`（普通全局函数，非 inline） | **否**（无 `EXPORT_SYMBOL`，`vmlinux.symvers` 0 命中） | **随便改**，对 493 个厂商模块零影响 |
| `prep_new_page` | `mm/page_alloc.c` | **一导出就进 `__kcrctab`** | **判砖**：翻厂商弱引用 ⇒ 活锁 → PMIC 复位 |

⇒ 这就是"**头文件安不安全看导出表，不看 inline**"的正反两个实证。

# ⛔ 报错 ≠ 功能坏（2026-10-03 P28，必须查功能状态）

**纪律**：**先查功能状态（`dumpsys` / `/proc/modules` / 服务状态），再看日志。** 不许只凭 dmesg 判功能坏。

P28 当天犯了**两次同类错误**：

| 误判 | 真相 |
|---|---|
| `grep 'ssg.*error'` 命中 36 行 ⇒ 判"SSG 有错" | 实际是 `libproce`**`ssg`**`roup` 的**子串误匹配** |
| dmesg 报 `bluetooth: disagrees about version of symbol sk_filter_trim_cap` 且**没有 `hci0`** ⇒ 判"蓝牙坏了" | **蓝牙正常工作**：`dumpsys bluetooth_manager` 显示 `state: ON`、`crashed 0 times` |

**本机蓝牙为什么无害（这次有功能级证据）**：蓝牙走**高通厂商用户态栈** ——
`android.hardware.bluetooth@1.1-service-qti` + `/dev/btpower` + `/dev/btfmslim` + `qbt_handler` + `bt_fm_slim`，
**内核的 `bluetooth.ko` 根本没被使用** ⇒ 它的 CRC 不符确实无害。
（与 opt8 那次"已结案无害项"结论一致，这次补上了功能级证据。）
⇒ 因此 `gate_vko_crc.py` 的通过标准仍是"**= 1 且那 1 个是 `system_dlkm/bluetooth.ko`**"。
