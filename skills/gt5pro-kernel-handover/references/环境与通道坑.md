# 环境与通道坑（每条都是踩过一次才写下来的）

## Bash/命令行通道（最容易让人误判"事实"的一类）

1. ⛔ **经工具送进 `wsl` / `adb` 的命令行里，`$var`、`$(…)`、`$?` 会被参数层展开成空**——**单引号也救不了**。
   症状举例：`for f in *.ko; do readelf '' …; done`、`grep -ac ""` 报出等于总行数的假计数、`su -c 'echo $(…)'` 输出空白。
   ⇒ **凡带变量，一律写成脚本文件再执行**。这条能制造"组件不存在"的假阴性，务必先怀疑通道再怀疑事实。
2. ⛔ **`命令 | tail` 会把失败退出码洗成 0**（推送超时曾被误报成功）。⇒ 判成败只认现场回读（如 `git status -sb`、`md5sum`、`ls -l`），不认管道后的 exit code。
3. 路径以 `\` 收尾会让 Git Bash 引号失配 ⇒ 一律写正斜杠。
4. Windows 本地文件给**盘符形式**（`C:/Users/...`），远端/WSL 内路径给 `/mnt/c/...`；含 `//` 或 `\x` 的参数会被静态判成 UNC 而拒执行。
5. `MSYS2_ARG_CONV_EXCL='*'` 可挡住 MSYS 的路径转换——但**加了它，本地路径就不能写 `/c/...` 形式**（adb 会报 cannot stat）。
6. Git Bash 的 `timeout` 杀不掉 Windows 进程；停后台任务不会杀它的子进程 ⇒ 会留残留 `grep`/`find` 在设备上跑（曾把 loadavg 顶到 74.44）。
7. PowerShell 的 `>` 重定向会把 native 命令的 exe **清成 0 字节**（`adb.exe` 实测被清空）⇒ 别在 PS 里对 native 命令用 `>`；重定向交给 Git Bash 或 `su -c '… > 设备侧文件'`。
8. `.ps1` 必须纯 ASCII；GBK 控制台会毁掉 Python 的中文输出 ⇒ 让脚本写文件，再读文件。

## adb / 设备侧 shell

9. Android 16 上 `cat /proc/sys/kernel/osrelease` **非 root 被拒** ⇒ 判内核横幅用 `uname -r` / `uname -a`。
10. ⛔ 别在 PowerShell 里 `adb … | find /c /v ""` 数行数（会崩管道）⇒ 计数放设备侧：`su -c 'lsmod | wc -l'`。
11. **二进制必须 `adb pull`**（`adb shell cat` 会 CRLF 损坏）；`/vendor_dlkm` 的 `.ko` 走 `base64` 拉。
12. 刷机后 adb 常掉线 ⇒ 先查线 / USB 调试 / 授权弹窗，再怀疑系统起不来。
13. adb 送进设备的正则**别写 `\.` 和 `\(`**（静默零输出或语法错）；"无输出"要先证明 glob 真展开了。
14. Android mksh 的 `<(...)` 不可靠；手机端（MT 管理器终端）里 `su -c '带管道的整串'` 不成立（整串被当命令名）⇒ 先 `su` 再直接敲，工具写绝对路径 `/system/bin/…`。
15. **dmesg 环形缓冲约 100 秒绕一圈**（2 MB、开机约 73 s 满）⇒ 要完整开机日志必须 adb 抢抓：`wait-for-disconnect` → `wait-for-device` → 立即抓。
16. **debugfs 每次开机换挂载名**（本次 `/dev/xswbvgtq/lqsgnfxl`、上次 `/dev/katdfnna/oavmjb`）⇒ 先 `grep -m1 debugfs /proc/mounts | cut -d' ' -f2` 再 `ls`；`/sys/kernel/debug/` 是**空挂载点**，在那儿查会得到假的"不存在"。
17. `.ko` 的未定义符号在 `.symtab` ⇒ 用 `nm -u`；`readelf --dyn-syms` 会给假阴性 0。
18. 设备侧操作要轻量：⛔ 目录级 `grep -r`（先 `ls` 到单文件再 `cat`）；批量任务按**总字节数**预算（512 MB×48 曾把 loadavg 打到 21.68）；测前读 `loadavg` 判机器是否真安静，测完回读被改过的 sysfs。
19. KSU 模块的 `disable` 文件：`touch` 能禁、`rm -f` 也能放开（"删不掉"是循环里变量被吞的假象）⇒ 一律写字面完整路径 + `rm -v` 看回显。但**别把它当随手可逆开关**，尤其涉及启动链的模块。
20. 模块安装脚本里 `set_perm_recursive` 对**不存在的路径**返回非零，若它串在 `&&` 的 `if` 里就会走"安装失败 exit 1" ⇒ 写"目录存在才处理"。

## WSL

21. 装：`--unregister` + `--import`。联网：NAT + Clash「允许局域网」+ 动态网关 `:7897`（mirrored 模式已证伪）。
22. 要 root 用 `wsl -u root`——但**编内核时绝对不要用 `-u root`**（会静默换成 clang18，与主构建的 clang 17.0.2 不同 ⇒ 产物差异无法解释）。
23. PATH 首位残留目录会遮蔽系统工具；别把 `echo $PATH` 写进 `.bashrc`；`df` 显示的是虚拟上限。
24. 起长任务用 `setsid`（`nohup` 会 SIGHUP / Error 129）；`pkill` 的括号技巧防不住命令里出现的真实文件名。
25. `/tmp` 会被 WSL 重启清空 ⇒ 清单类中间产物一律落 `~/opt-prune/` 之类持久目录。
26. WSL 依赖 BIOS 的 **SVM**（虚拟化开关）。
27. **Clock skew**：PC 改过时间后，树里会出现大量"未来时间戳"⇒ make 静默跳过重编。判据 `find . -newermt $(date)`；处置＝重编两遍直到 skew=0。

## Git / GitHub

28. 直连 GitHub 时好时坏（家宽）⇒ **先原样重试一次**再谈代理；`api.github.com` 比 `github.com` 更易不通。
29. 推送成败只认 `git status -sb`（带 `| tail` 的 exit code 是假的）。
30. 推送姿势：WSL 推要用 Windows `gh` 当凭据助手，且**推前临时移除 `insteadOf`**（否则被改写到只读 gh-proxy）；浅克隆推不上去 ⇒ 用孤儿单提交快照。
31. 新仓加 `.gitattributes` 里 `* -text`，防 CRLF 毁掉 patch 文件。
32. 本机仓：`kernel-kit` 分支是 **`master`**（不是 main）；源码仓机主不推。

## 网络下载（本机实测）

33. 校园网下载仅约 400 KB/s；大文件走手机热点 `yuzusoft 14`（172.18.98.x，**别拿网段判断是不是热点**），热点国内直连 11–41 MB/s，走节点只有 20–316 KB/s（瓶颈在节点）。
34. gh-proxy 约 6.2 MB/s 但单文件 512 MB 上限且**不认 Range**；GitHub 归档 zip **不含 LFS 内容**（拿到的是指针文本）；阿里云 android 镜像给真文件但要 `-e robots=off`。
35. 源码归档体积 ≈ 仓库 size 的 1/10~1/15；大依赖先问"能不能用 apt 系统包替代"。

## 打补丁（2026-10-03 新增，两条都是踩过的）

36. ⚠️ **`has type 100755, expected 100644` 只是 `warning`，不是根因 —— 别被它带偏**
    （本条 2026-10-03 先写错过一次，经受控实验更正）

    症状（`git apply --check`）：
    ```
    warning: net/ipv4/ip_output.c has type 100755, expected 100644
    error: patch failed: net/ipv4/ip_output.c:1463     ← 真正的错在这行
    error: net/ipv4/ip_output.c: patch does not apply
    ```
    **本机 git 2.43.0 实测（受控实验，git 二进制里根本不存在带冒号的 `error:` 版本）**：
    - mode 不匹配 **不阻塞** `git apply`：内容能匹配时 `--check` 与真实 `apply` **都 exit 0**，内容正常写入
    - 真正失败的是 **`error: patch failed: <file>:<line>`** ⇒ **上下文冲突**，与 mode 无关
    ⇒ **判"补丁打不上"时，要读到最后一条 `error:`，不要抓第一行 warning 就下结论。**
      （这正是"报错 ≠ 根因"，与第 15 条同族）

    本机现状（2026-10-03 实测清点）：**281 个 `.c/.h` 是 100755**（索引与 HEAD 一致，
    来自提交里的 mode），其中 **34 个**被已抓补丁碰过；**108/1935 个补丁**（5.6%）会打印这条 warning。
    碰得最多的：`drivers/android/vendor_hooks.c`(46)、`include/trace/hooks/mm.h`(30)、`mm/page_alloc.c`(11)。

    ⛔ **绝对不要"只 `chmod 644`"** —— 工作区 644 / 索引 100755 的**撕裂**会让
    `git apply --index` / `--3way`（即 `git am` 路径）从 exit 0 变成
    `error: <file>: does not match index`（exit 1）。**制造的问题比解决的严重。**

    想消除这条 warning，只有两个安全办法：
    - **B（零文件改动，推荐）**：`git config core.filemode false`（本树配置级，不动任何文件）
    - **A（永久干净）**：对目标文件 `chmod 644` + `git update-index --chmod=-x`，**然后提交一次纯 mode 变更**
      （实测：只 chmod → ` M`；只 update-index → `MM`；两者一起 → `M `（已暂存）；两者+提交 → 干净）
    - C：补丁里自带 `old mode 100755` / `new mode 100644`（实测可 apply 并改成 644）

37. ⛔ **同一个文件里两处 `if` 文本完全相同时，不能用字符串 replace 打补丁。**
    实例：`fs/f2fs/compress.c` 的 340 行与 2316 行都是
    `if (f2fs_compress_layout(dic->inode) == COMPRESS_FIXED_INPUT)`，
    但**只有 340 该改**（解压路径），**2316 绝对不能改**（在 `f2fs_alloc_dic` 内部，
    改了会在赋值前引用缓存 ⇒ 真 bug）。
    ⇒ **按行号索引替换 + 逐行断言**；改完必须逐条核对"该改的改了、不该改的没动"。
