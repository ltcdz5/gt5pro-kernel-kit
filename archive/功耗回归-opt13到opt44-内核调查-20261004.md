## 一、最可疑的改动清单（按可能性排序）

### 1. ⚠️ 最可能的真实原因：**不是内核改动，而是 cpufreq 下限被抬到厂商默认值**

**证据（硬）：**

- opt13 那次的实测频率**下限**是 `364 / 499 / 480 MHz`。
- `kernel/oplus_cpu/uad/cpufreq_uag_main.c` 所在树的 Scene 配置
  `gt5pro-kernel/lse-module/lse_sched/scene_profile.orig.json` 里，
  `presets.common_inactive` 写着：
  ```
  ["@cpu_freqs_min", "307200", "499200", "499200", "480000"]
  ```
  ⇒ **307200/499200/499200/480000 与 opt13 实测的 364/499/480 逐项吻合**
  （307200 不在频率 LUT 上，cpufreq 向上取到 **364800** = 场景里的 364）。
- opt44 那三次实测（00:25 / 00:45 / 01:00）的**下限是 1248 / 1286 / 1248**，
  **正好是厂商默认下限**。旁证：`lse-module/lse_sched/README.md:14`
  明确写「最低频率被拉低到 ~0.5GHz（**原厂 1.25GHz**）」。

⇒ 结论：**10-04 的测量是在"Scene 的 `@cpu_freqs_min` 没生效 / 厂商 perfmgr 把下限顶在 1.25GHz"
的状态下跑的；09-30 那次是 Scene 的 `common_inactive` 真正生效的状态。**
两者不可比。频率下限从 0.36~0.5 GHz 抬到 1.25 GHz，在"抖音"这种**突发 + 长尾轻载**场景里
把每个空闲间隙的静态功耗都抬上去 —— 这正是 +0.7 W 量级，且**与 CPU% 不变但 M Cycles 翻倍**
（同忙闲比、更高时钟）的观测完全自洽。

**为什么这不是内核改动的结果（可验证的否证）：**

```bash
cd /home/builder/kwork/cctv18/repo/local/kernel_workspace/common
git log --oneline 4e03a7d25409..HEAD -- kernel/oplus_cpu/     # → 空：uag 调速器一行没动
git diff --stat 4e03a7d25409 66b2bf8c4fdc -- drivers/cpufreq/ # → 只有 cpufreq.c 19 行（opt44 的 gov_override）
```
- 实际生效的调速器是 **`uag`，源码在 `kernel/oplus_cpu/uad/cpufreq_uag_main.c`（本树内）**，
  在 opt13→opt44 之间**零改动**。
- `drivers/cpufreq/` 在同期**只多了一个 opt44 的 `gov_override` sysfs 别名属性**
  —— 不写它就不产生任何行为。
- `drivers/thermal/`（P25 只改了 sysfs 生命周期，不动任何 trip/governor）、
  `drivers/devfreq/`、`drivers/opp/`、`drivers/gpu/msm` 在同期**没有功耗策略改动**。

### 2. 次可疑：**`CONFIG_MQ_IOSCHED_SSG` 由 n 变 y（opt15-P21）**

- 提交 `e17ad23693ab`（10-02 21:24），只改 `arch/arm64/configs/gki_defconfig` 两行。
- 但 `block/elevator.c:643-652` 里是**硬编码**：
  ```c
  #ifdef CONFIG_MQ_IOSCHED_SSG
          return elevator_get(q, "ssg", false);
  #else
          return elevator_get(q, "mq-deadline", false);
  #endif
  ```
  ⇒ 打开这个 config，就把**所有单队列块设备的默认电梯从 `mq-deadline` 换成 `ssg`**。
  项目文档也实测到 `sda`~`sdf` 六个 UFS LUN 自动切成 `ssg`。
- 机制上"可能影响功耗"（电梯决定 I/O 合并与唤醒模式），但抖音的 I/O 量小，
  **项目从未测过它的功耗效应**，量级无法支撑 0.7 W。**列为第二嫌疑，但不是主因。**

### 3. `CONFIG_HZ` 250 → 300（opt15-P5，提交 `1df7a34f6453`）

- 这是 opt13→opt44 之间**唯一的、能穿透到"实际在跑的调速器"里的 config 改动**：
  `kernel/oplus_cpu/uad/cpufreq_uag_main.c` 用了 `TICK_NSEC`（=NSEC_PER_SEC/HZ）：
  ```
  :868  unsigned int ticks = TICK_NSEC;
  :871  ticks = sysctl_iowait_reset_ticks * TICK_NSEC;
  :877  if (delta_ns <= TICK_NSEC) return false;
  :977  ... (sysctl_iowait_apply_ticks * TICK_NSEC) ...
  ```
  `TICK_NSEC`：250Hz = 4.000 ms → 300Hz = 3.333 ms（**−17%**）。
- **但方向是"对功耗有利"**：`uag_gov_iowait_reset()` 是
  `delta_ns <= TICK_NSEC ⇒ return false ⇒ 保留 iowait 频率 boost`。
  300Hz 使这个门槛变小 ⇒ boost **衰减更快** ⇒ 频率更低 ⇒ 功耗更低。
  同理 boost 的"每 tick 至少请求一次才翻倍"也变得更难 ⇒ 升频更保守。
- 量级：个位数 ~ 数十 mW，**撑不起 735 mW**。
- 附带：HZ 还影响本树 OPLUS 子系统的窗口常量
  （`task_cpustats.h:MAX_CTP_WINDOW`、`sched_info/osi_base.h:JANK_WIN_TICKS`、
  `power_diag.c:cputime_one_jiffy`），均为二阶效应。

### 4. 同一提交 `1df7a34f6453` 的另外两项 config

- `CONFIG_LTO_CLANG_THIN=y`（原 `LTO_NONE`）：项目自己实测"镜像大 3%，体感用不出来"；
  代码生成变化，**未测出功耗效应**。
- `CONFIG_RCU_NOCB_CPU_CB_BOOST=y`（**原厂是 n**，我们多开的）：
  它把 RCU 回调 kthread 优先级提升。⚠️ 但 opt37（10-03 04:06）已把
  `CONFIG_RCU_NOCB_CPU_DEFAULT_ALL` 关回 n（原厂值），此时 rcuo kthread 默认不存在
  ⇒ **在 opt44 上这项实际是空转的**，且它在 10-03 白天之前就已如此。

### 5. opt37 的"四项 config 减法"（提交 `48e095183986`）—— 方向是**省电**，不是耗电

关掉 `UBSAN` / `INIT_ON_ALLOC_DEFAULT_ON` / `INIT_STACK_ALL_ZERO` / `ZRAM_MEMORY_TRACKING`，
并把 `RCU_NOCB_CPU_DEFAULT_ALL` 关回原厂值。全是**减开销**。
⇒ opt44 在 config 上比 opt13 **更省**，不是更耗。

## 三、能直接验证的方法（按性价比排序）

### ① 一条命令做内核侧 A/B（最干净）
在 opt13 与 opt44 各自开机后：
```sh
zcat /proc/config.gz | grep -E 'CONFIG_HZ=|CONFIG_LTO_CLANG_THIN|CONFIG_MQ_IOSCHED_SSG=|CONFIG_RCU_NOCB_CPU_DEFAULT_ALL|CONFIG_RCU_NOCB_CPU_CB_BOOST|CONFIG_ZRAM_MEMORY_TRACKING|CONFIG_UBSAN=|CONFIG_INIT_STACK'
uname -r
```
预期差异**只有**下面 5 项（这就是内核侧全部的"改动集"）：
```
CONFIG_HZ                    250 → 300            (opt15-P5, 1df7a34f6453)
CONFIG_LTO_CLANG_THIN        n   → y              (同上)
CONFIG_RCU_NOCB_CPU_CB_BOOST n   → y              (同上，原厂 n)
CONFIG_MQ_IOSCHED_SSG(+CGROUP) n → y              (opt15-P21, e17ad23693ab)
CONFIG_UBSAN/INIT_ON_ALLOC/INIT_STACK/ZRAM_TRACKING/RCU_NOCB_DEFAULT_ALL  y→n  (opt37, 48e095183986，省电向)
```
如果两边差出**别的**项，那才是新线索。

### ② 直接验证"频率下限"这条主因（最有价值）
**在同一颗内核（opt44 或 opt13 都行）上，只改用户态状态，配对测：**

```sh
# 测前
for p in 0 2 5 7; do echo "policy$p min=$(cat /sys/devices/system/cpu/cpufreq/policy$p/scaling_min_freq) max=$(cat /sys/devices/system/cpu/cpufreq/policy$p/scaling_max_freq) gov=$(cat /sys/devices/system/cpu/cpufreq/policy$p/scaling_governor)"; done
cat /sys/module/perfmgr/parameters/perfmgr_enable      # 0 = Scene 已关掉厂商 perfmgr
cat /sys/module/migt/parameters/glk_disable
cat /proc/sys/kernel/sched_schedstats                  # 应为 0
ls -l /sys/block/sd?/queue/scheduler; for d in /sys/block/sd?; do cat $d/queue/scheduler; done
```
**判据（这是本次调查的核心预言）：**
- A 组（复现 opt13 低功耗态）：`scaling_min_freq` = **307200 / 499200 / 499200 / 480000**
- B 组（复现 opt44 高功耗态）：`scaling_min_freq` = **1248000 / 1286400 / 1248000**
- 用 `cat /sys/devices/system/cpu/cpufreq/policy0/stats/time_in_state` 的
  **364800 / 460800 / 556800 三档计数**当客观判据：A 组非零，B 组这三个档**恒为 0**。

如果 B 组确实恒为 0，就**已经复现了这次的"回归"**，而且它**只由用户态写入决定**，
和 opt13/opt44 的内核差异无关。

### ③ 排除 SSG 与 HZ
```sh
# SSG：把六个 LUN 切回 mq-deadline，同口径再测一次
for d in /sys/block/sd?; do echo mq-deadline > $d/queue/scheduler; done
# HZ：内核侧无法运行期改，只能在 opt13/opt44 上各测一组配对读数
```

### ④ 正确测功耗的做法（现有数据 CV=41%~51%，单轮无效）
- **必须同内核配对 A/B**（`fastboot boot` RAM 引导两件、交替 ≥3 轮），
  否则 5 分钟单轮的散布（CV 41%）比待测效应大一个数量级。
- 固定：同一个离线视频循环、亮度分两段、离机（不插 USB）、电量 ≥40%、常温起测、同网络。
- 先算同状态重复轮的散布，**差 < 散布就报"测不出"** —— 这是项目自己已经写死的判定规则。

## 四、回退方法

**没有任何内核提交指向这次功耗差，所以"回退内核"不是对症的处置。**
按优先级：

1. **先回退用户态（零风险、一条命令级）** —— 这是真正的病根所在：
   ```sh
   # 让 Scene 的 cpufreq 预设重新生效
   # 1) 解除 LSE 模块对 Scene profile.json 的只读锁（模块的 action.sh 会做）
   # 2) 重启 Scene，确认它重新写入 @cpu_freqs_min
   # 3) 重启后复验 scaling_min_freq 是否为 307200/499200/499200/480000
   ```
2. **卸载 LSE Magisk 模块**（`uninstall.sh` 会切回 `uag` + 还原 `scene_profile.orig.json` + 重启 Scene）。
3. **若一定要回退内核**：opt42 的镜像 md5 `4bd362b0a17513474de217ea9beb8ae3`
   （`images/boot-v1.1-opt42-repacked.img`），或 opt36 `6610944ca925083835e2b5763c92f3f6`。
   要退回 **opt13** 则用 `images/boot-opt13-repacked.img.gz`（md5 `e80378a6b6895afdc3d5c443e529094d`，树 `4e03a7d25`）。
4. **若确认 SSG 是嫌疑**：`CONFIG_MQ_IOSCHED_SSG` 由 y 改回 n（一行 config，纯减法），
   等价于 `e17ad23693ab` 的反向操作 —— 但注意它的 CRC 门是干净的，回退无风险。
5. **HZ=300 → 250**：改 `gki_defconfig` 里 `CONFIG_HZ=300/CONFIG_HZ_300=y`
   为 `CONFIG_HZ=250/CONFIG_HZ_250=y`（⚠️ **不要在树里跑 `olddefconfig`**，
   会让 493 个厂商模块全废 —— 见 opt37 文档）。但按上面的机制分析，这个方向是**反的**。

| devfreq / DDR / GPU 被改 | `drivers/devfreq/`、`drivers/gpu/msm`、`drivers/opp/` 同期无改动 |
| 编译器 flag（-O3/LTO/PGO/BOLT）变了 | 构建命令逐版比对完全一致（都是 `KCFLAGS+=-O2 -Wno-error`）；只有 config 层的 `LTO_NONE→LTO_CLANG_THIN` |
| `EAS_OPT` 被关导致放置变差 | 曾疑似（`CONFIG_OPLUS_FEATURE_EAS_OPT: y→n`），但树内 `kernel/oplus_cpu/sched/Kconfig:189` 是 **`default n`**、且 `gki_defconfig` 从未包含它 ⇒ 从 opt7-clean（09-29 18:42，**远早于 opt13**）起就已是 n，**不在 opt13→opt44 窗口内** |
| opt43 的 `scx_switch_all_req` 改动 | 无 scx 调度器加载时两条路径等价；它反而是**修**了硬挂死 |
| opt44 的 `gov_override` | 纯新增，不写零行为 |
| opt13 的"减脂三项"差异 | opt13 那次的 `.config` 里 UBSAN 已是 n（见 `opt15c.config`），opt44 又关了 INIT_STACK 等 ⇒ opt44 更省 |
| `sched_schedstats` | 它是**运行期 sysctl**（树内 `sysctl_schedstats` CFTL，默认 0），不是内核版本差异；但要确认测时它=0（实验脚本 `set_stock.sh` 会把它写成 1！） |

## 六、必须同时指出的两条元证据（这会改变处置方向）

1. **10-01 21:29 就已经测到 AVG 3.72 W**（`档案/性能功耗/抖音功耗对照-口径与步骤-20261001.md:9`）。
   而 **opt14 是 10-02 00:39 才构建的** —— 也就是说，**"3.5~3.7 W 这一档读数在 opt14 存在之前
   就已经出现过"**。把它归因给 opt14~opt44 的改动，时间线上不成立。
2. **opt13 那次的 2733 mW 是在 31% 电量 + CPU 峰值 72℃ 下测的**，
   项目自己的文档就写明"低电+高温时机身的功耗/调度本身就偏保守，别把这种单轮的绝对值当依据"。
   而且它的 **CV = 41%，p90 = 4242 mW** —— 单轮均值本身就在噪声带里。

⇒ 综合判断：**"opt13 → opt44 有 +735 mW 内核回归"这个命题，现有证据不支持。**
现有数据支持的是：**10-04 的三次测量处于"厂商默认频率下限(1.25GHz)生效"的状态，
09-30 那次处于"Scene 把下限放到 0.36~0.5GHz"的状态**，二者条件不同，
且这个差异由**用户态**（Scene 预设 / 厂商 perfmgr / LSE 模块对 Scene 配置的改动）决定，
内核侧没有任何对应改动。
